## 项目定位与整体架构

### 你这个项目是为谁做的，最终部署上线了吗？

项目面向**有频繁查数需求但 SQL 门槛较高的业务人员**（运营、产品、分析师），以及需要承接大量临时取数需求的数据团队。

项目目前是本地 Docker Compose 一体化部署（FastAPI 后端 + Milvus + PostgreSQL + Redis + etcd + MinIO 六容器编排），完成了功能验证、Spider 开放域评测和 36 项离线回归测试。如果要上生产，需要补的是 K8s 编排、向量库集群化、Prometheus/Jaeger 标准可观测性和密钥管理——这些我有清晰的方案，但当前版本的定位是完整验证技术链路。

### 项目的数据从哪来？为什么选这两个数据集？

项目内置两个公开数据集：**Olist 巴西电商**（14,747 笔真实订单、9 张表、8.9MB，含订单 / 支付 / 物流 / 评价完整链路）和 **Chinook 数字媒体**（11 张表，发票 / 曲目 / 流派 / 艺术家）。选它们的原因：Olist 是真实业务数据（有脏数据、有 NULL、有一对多关联陷阱），能暴露真实的口径问题；Chinook 的表结构风格（PascalCase、schema 前缀）与 Olist（蛇形命名）完全不同，正好用来验证跨库和命名风格鲁棒性。开放域泛化能力则用 Yale 的 Spider 学术基准（20 个异构数据库）验证。

### 你的用户体量/并发量大概是多少？

当前是个人项目的本地部署形态，使用场景以单用户深度分析为主，并发量很低。架构上并发瓶颈主要在 LLM 推理延迟而非系统设计——语义层编译路径不依赖 LLM、毫秒级返回，可以承载高并发；LLM fallback 路径的并发取决于模型服务的承载力。如果面向生产扩容，优先级是：无状态后端水平扩副本 → Redis/PostgreSQL 承载会话状态 → 模型服务独立伸缩。

### 一次问答的处理速度大概在什么水平？

命中语义层的问题（编译路径）**秒级甚至毫秒级**，因为不需要 LLM 生成 SQL，只有一次 Schema Linking 和确定性编译；LLM fallback 路径取决于模型响应，一般 **5-15 秒**；根因分析类问题涉及多条取证查询，会到 **30 秒以上**。项目做过一次专门的编排延迟优化（从 29s 优化到约 10s），手段是靠 Span 追踪定位冗余调用、并行化独立节点。瓶颈主要在 LLM 的推理延迟。

### 模型选型是怎么考虑的？

**分层选型，不为所有任务用同一个模型**：

- **主对话/生成模型**（flash 级）：负责高频、低决策密度的任务——SQL fallback 生成、问答汇总。这类任务量大，成本和延迟敏感；

- **SOTA 模型**：只花在刀刃上——Advisor 诊断、Plan 拆解这类高价值决策。通过 `SOTA_MODEL` 环境变量配置，这就是 Advisor / Plan with SOTA 的成本分级设计；

- **轻量模型**：上下文压缩的摘要生成用轻量模型（`SUMMARIZATION_MODEL`），摘要任务不需要强推理能力；

- **Embedding/Rerank**：选 bge-m3（中文效果好、1024 维与现有 schema 匹配、SiliconFlow 免费额度），多厂商解耦用抽象工厂隔离——对话层兼容任意 OpenAI 协议服务（DeepSeek/Moonshot/OpenAI/SiliconFlow），Embedding 层支持 SiliconFlow/DashScope/Ollama，Rerank 兼容 DashScope 和 SiliconFlow 两种响应格式。

### 你这个项目是单智能体还是多智能体，每个智能体的作用/必要性是什么？

项目是**多智能体**架构，LangGraph StateGraph 上共 14 个节点，按问题复杂度分层：

- **Supervisor（路由智能体）：**首层分发，简单查询走快速路径，控制延迟和成本；

- **ReAct 智能体：**复合工具需求（一句话里多个诉求）进入"思考→调工具→观察→再思考"循环，带防重复调用签名去重和迭代上限强制总结；

- **Coordinator（协调智能体）：**跨模块任务（同时涉及业务数据、知识库、历史记忆）拆解为独立子任务，asyncio.gather 并行派发给专职 Worker；

- **Reflection + Advisor（质量智能体）：**对低质量答案先向强模型请教改进方向，定向重试而不是盲目重试。

必要性在于：单 Agent 处理复杂任务会出现无谓循环、上下文膨胀和工具选择混乱，分层后每一层的职责和成本都可控。

### 属于哪一种 Agent 范式，为什么这么设计？

ChatBI 主链路属于**路由 + 编译**范式，严格说不是纯 Agent——已治理指标走确定性编译，根本不经过模型推理，这是有意为之：业务口径要求**可复现、可审计**，同一个问题今天和明天的答案必须一致。

开放性问题和跨模块任务才是 Agent 范式（ReAct / Plan-and-Execute + Reflection）。整体是一个 **Agentic Workflow**：主流程固定（Schema Linking → 路由 → 编译/生成 → 守卫 → 执行 → 汇总），保证稳定性；每个节点内部保留模型灵活性，兼顾开放性。

### 你问数的流程是 Workflow 还是 Agent？

**主链路是 Workflow 思想，节点内是 Agent 能力。**问数流程固定为 Schema Linking → 路由决策 → 语义编译/LLM 生成 → SQL Guard → 执行 → 汇总，步骤不是模型自由决定的；但 Schema Linking 的指标抽取、自修复的 SQL 改写、根因分析的假设拆解都是模型在节点内自主完成的。这样设计是因为问数场景对**稳定性和可审计性**的要求高于对灵活性的要求。

### 这个功能不能直接由 Claude Code / GPT 来实现吗？

> 通用 Agent 解决的是"通用任务能力"，我们的项目解决的是"**特定业务场景下的可信问数能力**"。
>
>



通用 Agent 接入数据库后确实也能写 SQL，但核心问题是业务适配和结果可信度不够：

**口径不稳定：**它默认不了解内部指标口径、JOIN 约定和维度含义，同一个"销售额"每次生成的聚合方式可能不同，今天和明天的答案可能对不上。

**静默错误无感知：**SQL 能执行但结果是错的（空结果、比率超 100%、TopN 忘加 LIMIT），通用 Agent 没有结果合理性检查这一层。

**过程不可审计：**企业场景要求每个数字能回答"口径是什么、SQL 是什么、为什么这么路由"，我们的 IR、Metric Plan、Trace 全链路留痕，通用 Agent 是一次性黑盒。

因此通用 Agent 能完成单次任务，我们的系统是把业务口径和问数流程沉淀成稳定、可控、可复用的能力。

### 全链路到底是怎么做的（给一个具体的案例进行分析）

比如用户问：**"Olist 各品类的销售额排名"**。

首先 SchemaLinker 抽取 IR：`metrics=[sales_revenue]`、`dimensions=[product_category_name]`、`sort={by: sales_revenue, order: DESC}`。因为命中单一已治理指标、维度与指标同属 Olist 数据集、无根因类推理词，路由判定为 `semantic_compile`，理由是"单一已治理指标，维度数据集一致，可确定性编译"。

然后 MetricPlanCompiler 取出 `sales_revenue` 的指标定义：主事实表 `olist_order_items_dataset`、聚合 `SUM(price)`，维度 `product_category_name` 的 JOIN 路径（order_items → products → category_translation），编译出带 GROUP BY + ORDER BY + ROUND 的 SQL。

SQL 进入 Guard：sqlglot AST 校验只读与表列存在性 → 执行 → 结果合理性检查（无空结果、比率越界等告警）。

最终 Synthesize 节点输出数据表格 + 口径说明（"销售额 = SUM(order_items.price)，避免支付拆分重复计数"），同时整条链路（IR、SQL、耗时、告警）写入 TraceStore，可复核。

如果用户问的是开放问题（比如 Spider 库上的陌生 Schema），则走 LLM fallback：DDL + 外键 + 每表 3 行样本构造 prompt 生成 SQL，但同样要过 SQL Guard 三层校验。

**再补一个异常分支的例子**（同样是"各品类销售额排名"，但模型生成时误用了方言函数）：

```text
模型初版 SQL：SELECT LEFT(customer_state, 2), ...   ← SQLite 不支持 LEFT()
  ↓
静态校验：命中方言函数黑名单 → 拦截
  ↓
自修复：错误信息 + Schema 反馈给修复模型
  → 产出 substr(customer_state, 1, 2)
  ↓
重新过校验 → 执行成功 → 合理性检查通过 → 正常输出
```

这个分支的价值：方言错误是 LLM 生成 SQL 最高频的失败类型之一，没有自修复层这类问题直接以报错告终；有了之后，实测中 `LEFT()` → `substr()` 的自动改写已被独立集成验证过。面试官如果追问"你们的系统出错了怎么办"，这个案例就是答案。

## ChatBI 核心链路

### 什么是语义层，为什么要做语义层？

**语义层是把业务指标的定义（事实表、聚合方式、过滤条件、可用维度、JOIN 路径）从模型概率生成中剥离出来、固化为可审计代码的治理层。**

动机来自真实失败案例：比如"回头客户数"，模型误用 `customer_id`（每订单唯一）而非 `customer_unique_id`（回头客共享）——这不是模型能力问题，是**业务口径没有被显式定义**的问题。语义层把 14 个核心指标和 18 个维度的口径固化后，这类错误从根上消失。业界同思路的实践是 dbt MetricFlow 和 WrenAI 的 MDL。

一个指标定义的实际形态：

```python
"sales_revenue": MetricDefinition(
    display_name="销售额",
    description="商品成交额合计，基于订单明细 price；按品类分析时避免支付拆分重复计数",
    dataset="olist",
    table="olist_order_items_dataset",
    aggregation="SUM",
    measure_column="price",
    dimensions=["customer_state", "seller_state", "payment_type", "product_category_name"],
)
```

注意 description 里那句"避免支付拆分导致重复计数"——这是真实踩坑后写进口径定义的：订单和支付是一对多，用支付表算销售额会因多单支付拆分而虚增。语义层沉淀的不只是"怎么算"，还有"为什么不能那么算"。

### NL → IR → SQL 两阶段编译的好处是什么？

**核心好处：中间表示可审查，错误归因才有抓手。**

先理解一阶段方案的问题：模型直接从自然语言生成 SQL，出错时你无法区分错在哪一环——是没听懂问题（把"差评率"理解成了"好评率"），还是听懂了但 SQL 写错了（JOIN 路径连错）？两种错误的修复方式完全不同，但从错误结果上看不出来。

两阶段把"理解"和"生成"拆开：第一阶段产出结构化的 IR（中间表示），明确写出"识别到的指标是 sales_revenue、维度是 product_category_name、路由决策是 semantic_compile、理由是单一已治理指标"；第二阶段只负责按 IR 确定性组装 SQL。

调试 bad case 时的动线就清晰了：**先看 IR 对不对**——IR 错（指标识别错、维度漏了）是 Schema Linking 的问题，去优化检索和抽取；IR 对而 SQL 错（JOIN 错、聚合错）是编译器的问题，去修模板。Spider 失败分析就是靠这个拆出"类型 A：业务理解偏差"和"类型 B：字段选择错误"两类失败的。

第二个好处是**路由决策显式化**：IR 里记录"为什么不能编译"（比如"维度跨数据集，降级 LLM 规划"），"不能编译"也是一种明确的、可审计的结果，比强行生成一条错误 SQL 好得多。

### Schema 三级检索具体是怎么做的？

按信息密度逐步收敛：**Level 1 数据域**（订单域 / 支付域 / 商品域 / 评价域 / 媒体销售域，每个域带别名和业务描述）→ **Level 2 表与已验证的 JOIN 关系**（避免模型凭猜测连表）→ **Level 3 字段**（只在命中表内输出字段，避免全库字段噪声）。

**追问防御：为什么是三级不是一级？**直接把全库 Schema 给模型，在小库（20 张表）上问题不大，但库里表一多，上下文噪声会让模型选错表的概率显著上升；三级的本质是"先收敛范围、再精细匹配"，和搜索引擎先粗排再精排是一个思想。反过来如果只做到表级（两级），同一张大表的几十个字段全塞进去依然有噪声——字段级收敛才能保证模型看到的是最小充分 Schema。

与把全部 Schema 注入 Prompt 相比，模型只看到当前问题的**最小充分 Schema**，上下文噪声显著降低。检索结果本身可解释——每个命中都带所属层级和得分，调试时能看清"为什么选了这张表"。

### 动态 Few-shot 知识库是怎么做的？

`SQLExampleStore` 把成功 SQL 和 Bad Case 修复记录统一维护为可版本化的 JSON 知识库，检索时按问题语义匹配 Top-3 示例注入 Prompt。两个关键设计：**示例带要点说明**（不只是 SQL，还有"为什么这么写"，比如"订单量必须 COUNT DISTINCT order_id"）；**注入时明确指示"仅参考 Join / 方言，不复制无关过滤条件"**——防止模型照抄示例里的过滤条件答非所问。Bad Case 修复成功的 SQL 会自动回写知识库，形成"错一次、永久免疫"的积累。

### 复合指标计划是什么？为什么不能直接编译多指标？

复合计划是针对**多指标 + 派生比率**类问题的确定性 SQL 模板（共 6 类：支付方式统计、跨库订单发票对比、品类差评拆解、流派收入效率、卖家延迟率 TOP5、流派收入驱动）。这类问题的难点是分子分母口径必须一致（比如延迟率 = 延迟单量 / 总单量，WHERE 不能提前过滤掉分母），模板里固化了正确的聚合结构。命中复合计划时整个 Plan 由模板生成，不走单指标拼接——因为两个独立编译的指标 SQL 拼在一起，口径几乎必然出错。

### 维度跨数据集是怎么处理的？

每个指标定义里标注了所属数据集（olist / chinook），SchemaLinker 会校验识别出的维度是否与指标同域：**跨域直接判定不可编译，降级 LLM 并在 IR 里记录原因。**"不能编译"也是一种需要明确表达的结果，比强行生成一条错误 SQL 好得多。这个约束来自一次真实回归：跨域误路由曾导致评测准确率大幅下跌，修复后固化了回归测试。

### "最近三个月"这种相对时间怎么解析？

这是 Text2SQL 里很实际的问题。本项目的处理分两层：

- **语义层路径**：相对时间表达式（最近三个月 / 本月 / 今年）在 Schema Linking 阶段被归一化为结构化过滤条件（`filters: {last_3_months: true}`），编译器翻译成方言正确的日期函数（SQLite 用 `strftime('%Y-%m', ...)` 提取月份、用日期偏移计算窗口）——不让模型自己写日期计算，因为日期函数是方言错误的高发区；

- **LLM fallback 路径**：Prompt 中给出当前日期和方言日期函数示例，生成后由 SQL Guard 的方言校验兜底。

核心原则：**相对时间的"相对"在系统侧锚定（当前日期由系统提供），模型只负责表达窗口，不负责猜今天是几号**——模型不知道今天日期，让它自己算相对时间必然出错。

### SQL Guard 的三层分别防什么？

- **静态校验（防危险、防方言错误）**：sqlglot AST 解析语句类型，写操作（INSERT/UPDATE/DELETE/DROP/ALTER/CREATE/TRUNCATE/PRAGMA/ATTACH）一律拦截，多语句注入同样拦截；方言函数黑名单（SQLite 不支持 LEFT()、DATE_DIFF() 等）；表名存在性校验。

- **执行自修复（防执行失败）**：数据库报错时，把错误信息 + Schema 节选反馈给修复模型，最多两轮。修复提示词内置方言规则和口径规则（"比率要核对分子分母同一口径""TopN 必须 LIMIT N"）。

- **结果合理性检查（防静默错误）**：空结果、结果过大未 LIMIT、TopN 无 LIMIT、列 NULL 占比 ≥50%、比率列 >100%。其中空结果和 TopN 无 LIMIT 视为可修复失败回送模型；NULL 和比率告警只提示不改口径——**不为了"看起来正常"而盲改业务语义**。

**追问防御：三层为什么不能只做一层？**静态校验拦不住"语法对但执行错"（字段类型不匹配要执行才知道），执行成功不代表结果对（空结果、比率越界都是静默错误），三层分别覆盖**危险操作、执行失败、静默错误**三类完全不同的故障模式。实际事故里三类都真实出现过。

### 为什么用 sqlglot AST 而不是正则做只读校验？

正则方案有两个真实缺陷：**误伤**——`REPLACE()` 是 SQLite 合法函数、字符串字面量里出现 'update' 也是合法的，正则会把它们误判为写操作；**绕过**——"SELECT 1; DROP TABLE x" 首句是 SELECT 就能绕过开头校验。AST 按语句类型判定，只拦截真正的写操作节点，同时检测多语句。正则现在仅作为 sqlglot 不可用时的兜底，这两个 case 都已固化进回归测试。

### 自修复会不会越修越偏？怎么兜底？

两个机制：**轮次上限**（最多 2 轮，修不好就把告警抛给上层展示，不无限循环）；**意图保持约束**（修复提示词明确要求"保持原查询意图不变"，且修复后的 SQL 仍要重新过静态校验）。工程记录里有过反例：AST 误拦截合法 SQL 触发自修复，模型反而生成了跨域错误 SQL——这说明**自修复的质量取决于前置校验的准确性**，所以 AST 校验器本身的正确性优先级最高。

### 根因分析是怎么做的？为什么不让大模型直接回答"为什么"？

直接回答"为什么"本质是让模型编造因果——它没有任何数据支撑。项目的做法是**假设拆解 → 并行取证 → 证据归因**：先把异动拆成可验证的假设维度（时间、品类、客群、渠道），每个假设生成一条取证查询，要求每条证据查询返回非空结果，最后基于真实数据汇总归因，标注主因和次因。

实测案例："11 月销售额为什么暴增"完成 4/4 条非空证据查询，正确定位黑五大促为主因、高客单品类结构变化为次因。核心价值是**每个结论背后都有可复核的取证 SQL 和数据**。

**追问防御：如果所有假设的取证查询都是空结果怎么办？**这正是要求"非空"的原因——空结果的假设在归因报告里明确标注"未找到数据支持"，而不是让模型含糊带过。全部为空时系统如实回答"现有数据维度无法解释该异动，建议补充 XX 维度数据"，而不是硬编一个原因。**承认不知道，是可信系统的一部分。**

### 数据质量对账是干什么的？

`DataQualityAgent` 内置 7 条 DQ 规则（金额非负、外键完整性、状态枚举合法等），主动扫描数据集本身的质量问题。实测定位 Olist 4 项真实告警（如部分订单缺支付记录）、Chinook 0 异常。它的价值在于**区分"系统算错了"和"数据本来就脏"**——比如 Spider 评测里 flight_2 库的失败主因是 AirportCode 尾部空格的脏数据，不是 SQL 逻辑问题。没有这个视角，所有失败都会被误判为模型能力问题。

### 回归测试是怎么做的？

36 项离线回归测试（`tests/test_chatbi.py`），**完全不调用外部 LLM、只用本地 SQLite**，保证 CI 环境可跑、结果可复现。覆盖五类：语义层编译（指标编译正确性 + 可执行性）、Schema 检索（复合查询召回正确表）、SQL 守卫（方言拦截 / 写操作拦截 / 误伤防御 / 多语句注入）、字段级评测（别名归一化 / 行召回归因 / 单元格归因）、历史 bug 固化（AST 误拦截、跨域误路由、HAVING 保留、ROUND 精度等）。

设计原则：**每一个修过的 bug 都要变成一条回归测试**——不然同一个坑会踩两次。

### 项目如果换个数据集能直接用吗？泛化能力怎么样？

分两层如实回答：

- **开放域泛化**：LLM fallback 链路（DDL + 外键 + 样本行 prompt + Guard）不依赖任何定制，Spider 20 个异构数据库 zero-shot 78.8% 就是泛化证据；

- **语义层泛化**：14 指标 × 18 维度是针对 Olist/Chinook 定制的，换业务需要重新治理指标——但治理过程本身是可复制的工程方法（评测驱动、Bad Case 归因、口径沉淀），不是一次性手工劳动。

这个边界我们在文档里明确写出来，不宣称语义层在任何陌生库上都有效。

## 多智能体编排

### 为什么选 LangGraph 而不是自己写 if-else？

**先看 if-else 方案会在哪里崩：**刚开始只有三四个节点时，if-else 确实简单直接。但节点一多问题就来了——每个节点需要的中间结果（意图、检索证据、SQL、工具调用记录）要在函数参数里手动传递；每加一个新节点，要回头改所有下游的 if 判断；"执行完 A 之后，如果结果 X 走 B、结果 Y 走 C、失败了走 D"这种条件分支写多了就是意大利面条。

**LangGraph 的 StateGraph 把这三件事都结构化了：**

- **状态集中管理**：所有中间结果存在一个共享的 `AgentState` 对象里，节点只读写自己关心的字段（意图识别节点写 `intent` 字段、SQL 节点读 `intent` 写 `sql` 字段），不用手动传参；

- **编排声明式**：加节点就是 `add_node` + `add_edge` 两行配置，不影响任何既有节点的代码；"根据中间结果决定下一步"是条件边配置，而不是嵌套 if；

- **持久化开箱即用**：检查点（checkpointer）机制让长对话的状态保存/恢复不用自己造轮子。

本质是把"流程控制"从命令式代码变成声明式配置——图的结构一目了然，改流程改的是图配置而不是散落各处的判断逻辑。项目里 14 个节点的编排图，如果手写 if-else 维护成本是不可接受的。

### 意图识别是怎么做的？为什么用三路融合？

**怎么做：**三路并行 + 加权投票——**规则通道**（正则 / 关键词，零成本零延迟，权重 0.3）、**LLM 通道**（语义理解，覆盖口语化模糊表述，权重 0.5）、**历史通道**（用户近期会话的意图模式，处理依赖上下文的表述，权重 0.2）。`WeightedVoter` 按权重融合，加权分数低于阈值时返回澄清问题而不是强行路由。

**为什么融合：**单通道都有明显短板——规则通道快但僵化（"为什么 A 比 B 少"这种比较句式正则覆盖不全），LLM 通道准但慢且偶发解析失败，历史通道只在有上下文时有效。融合后规则命中可短路（满置信度直接出结果），LLM 失效时规则和历史兜底。

**权重不是静态的：**Monitor 按各通道历史准确率在线归一化调整——某通道准确率下降，权重自然降低，其他通道接管。这里修过一个阈值悖论 bug：融合阈值 0.6 高于 LLM 单通道理论上限（0.5 × 1.0 = 0.5），导致 LLM 再有把握也永远被拦截，修正为 0.4 并固化了回归测试。

### Supervisor 快速路由是怎么做的，有什么用？

**怎么做：**Supervisor 是 StateGraph 的首层节点，对问题做意图分发——直接查询走快速链路，一次路由一次执行，不进入任何循环；复合查询和跨模块任务才分流到 ReAct 或 Coordinator。

**有什么用：**大部分用户问题其实是简单问题，如果所有问题都进 ReAct 循环，每次都要多轮 LLM 调用，延迟和 token 成本成倍浪费。快速路径用最低成本解决最高频问题，这是系统的"经济舱通道"——**不是所有问题都值得让 Agent 思考五轮。**

**追问防御：路由会不会分错？**会，所以有两个保护：意图识别是三通道加权投票（规则/LLM/历史），低置信度时不强行路由而是发起澄清；另外路由只决定"进哪条链路"，各链路的底线能力有重叠（比如 ReAct 链路也能处理简单查询，只是贵一点）——分错的代价是成本而非正确性，这是设计路由边界时刻意保证的。

### ReAct 循环是怎么做的，怎么防止失控？

**怎么做：**核心是一个事件驱动的 while loop——用户消息（user_message）、模型发起工具调用（tool_use）、工具返回结果（tool_result），每类事件推动循环进入下一轮。模型在循环中"理解上下文 → 思考下一步 → 调工具 → 观察结果 → 再思考"，直到自主判断信息足够，按 JSON action 协议（tool / final）输出最终答案。两个保护机制：**签名去重**——相同工具 + 相同参数的重复调用被识别，并在系统提示中反馈"该工具已调用过且结果是 X"；**迭代上限**——默认 5 轮，到达上限强制总结输出。

**有什么用：**复合查询（一句话里多个诉求，比如"查一下月度销售趋势，顺便对比下各品类的差评率"）无法一次路由完成，必须让模型根据中间结果决定下一步。事件驱动 + JSON 协议让"思考—行动—观察—再思考"形成自主决策闭环，不需要人类逐步指导；签名去重和迭代上限解决的是 ReAct 范式最常见的两个工程事故：**重复调用烧钱**和**无限循环不返回**。

### Coordinator 是怎么做跨模块协作的，有什么用？

**怎么做：**当问题同时涉及多个独立模块（业务数据 + 知识库规则 + 个人历史记忆），Coordinator 用强模型把问题拆成 2-4 个独立子查询，按类型分派给专职 Worker（data_worker / schema_worker / memory_worker），通过 `asyncio.gather` 并行执行，各子任务结果分流到既有 state 字段，下游汇总节点完全无感知。拆解输出会过白名单校验，非法 Worker 类型直接过滤，防止模型编造不存在的执行器。

**有什么用：**串行执行多个独立子任务是纯粹的延迟浪费，并行拆解把总耗时从"各子任务之和"降为"最慢子任务的耗时"。同时这是**强弱模型分工**的实践：拆解这种高价值决策交给强模型，执行交给专职 Worker，成本和质量兼顾。

### Reflection 的重试和普通重试有什么区别？

**怎么做：**Reflection 节点对最终答案做质量审查，判定不通过时**不是直接重试**，而是先调用 Advisor（SOTA 强模型）——Advisor 拿到主 Agent 的完整上下文（用户问题、已调用工具及结果、当前困惑），输出三段式诊断：【问题诊断】【方向建议】【注意事项】，注入重试上下文做"有指导的重试"。Advisor 不允许使用任何工具，只给判断；Advisor 不可用时自动降级为普通重试。

**有什么用：**盲目重试的期望收益很低——同样的输入大概率得到同样的坏结果。Advisor 把"再试一次"变成"带着诊断意见再试一次"，重试命中率显著提高。这个设计的本质是**把重试从"碰运气"变成"针对性修复"**，同时是成本分级：便宜的 flash 模型干执行，贵的 SOTA 模型只花在诊断这个刀刃上。

### Plan with SOTA 是什么场景用的？

复杂任务先自动切换到 SOTA 模型做 Plan：拆解步骤、标注每步所需能力（tool / rag / memory）、标注依赖关系（可并行 / 必须串行）和风险点（大数据量 / 复杂聚合步骤标 [耗时] 并给兜底动作），再把 Plan 派发给 flash 模型执行。弥补 flash 级模型在方案设计和前置推理上的短板，成本只增加一次 Plan 调用。和 Advisor 的区别：Plan with SOTA 是**事前规划**（执行前），Advisor 是**事中求助**（卡点时）。

### 多 Agent 协作会不会引入更多不稳定？怎么做工程兜底？

会，所以每层都有降级设计：Advisor 失败降级普通重试；MCP 外部服务失败降级仅内部工具；混合检索失败降级稠密检索；Rerank 失败回退 RRF 结果。**每个增强组件都假设自己会挂，系统的底线能力不依赖任何一个增强组件。**这也是多组件系统能跑稳的关键——不是每个组件都完美，而是每个组件的故障都有出口。

## 检索与混合召回

### 你们的混合检索完整链路是什么？每个环节有什么用？

**父子块切分：**文档切成细粒度子块用于精确召回，召回后取回父块恢复完整上下文。解决"切小块召回准但上下文残缺，切大块上下文全但召回糙"的矛盾。入库时用 sha256 内容哈希去重，同一文档重复入库不会产生重复块。

**稠密检索（Milvus 向量，bge-m3）：**处理语义改写——用户说"卖得最好"，能召回"销售额排名"相关的 Schema / 文档。

**稀疏检索（BM25 关键词）：**保住精确术语——表名、字段名、枚举值这类"一字之差就错"的内容，向量检索对它们召回不稳定。

**RRF 融合：**按 `1/(60+rank)` 对两路结果的排名加权求和。稠密分数和 BM25 分数量纲不同，直接加权需要归一化且对分布敏感，RRF 只用排名，工程上更稳定。

**Rerank 精排：**双塔检索是粗排（分别编码，快但精度有限），Rerank 交叉编码（query 和候选一起进模型，慢但准），在候选集合中筛出最相关证据。

**降级路径：**混合检索失败降级稠密检索，Rerank 失败回退 RRF 结果——优先可用性，再追求精确性。

**追问防御：每个环节拿掉会怎样？**拿掉 BM25："olist""customer_unique_id"这类精确术语召回率下降；拿掉稠密：口语化表达漏召回；拿掉 Rerank：语义相近但业务无关的字段（"到账金额"vs"预算金额"）混进上下文；拿掉降级路径：任何一个外部服务抖动都会直接表现为系统故障。每个环节都是被具体的 Bad Case 证明过价值的。

### 为什么不是只做向量检索？

因为两路检索各有各的盲区，而真实 Query 会同时踩中两边：

- **向量检索擅长语义泛化，但对精确术语召回不稳。**用户说"卖得最好"，向量能理解它等价于"销售额排名"——这是它的价值。但对 `customer_unique_id`、`olist_order_items_dataset` 这种表名字段名，向量空间里它们和`customer_id`、其他表名距离很近，**一字之差的术语在语义空间里几乎无法区分**；数字、枚举值（"SP""RJ"）同理。

- **关键词检索（BM25）正好相反。**`customer_unique_id` 出现就是出现、没出现就是没出现，精确匹配不会错；但用户说"卖得最好"而文档写的是"销售额排名"，词面上一个共同词都没有，BM25 一条都召不回。

真实用户 Query 通常**同时包含精准业务术语和模糊口语表达**——"olist 的差评率"里"差评率"需要语义理解（文档可能写的是"review_score ≤ 2 的占比"），"olist"需要精确匹配（是库名，错一个字母就错库）。只做向量检索会丢精确术语，只做关键词检索会漏口语表达，混合检索是在召回率和精确性之间不妥协的方案——这也是 Schema 检索在开放域达到 97.0% 表命中率的工程基础。

### BM25 的原理能讲一下吗？

BM25 是经典的关键词相关性评分，核心思想是**词项越稀有、在文档中出现越多，越相关，同时惩罚长文档**：

```text
score = Σ idf(t) × tf(t)×(k1+1) / (tf(t) + k1×(1-b+b×|d|/avg_len))
idf(t) = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))
```

k1=1.5 控制词频饱和度（出现 10 次不比出现 3 次重要太多），b=0.75 控制长度惩罚强度。项目里中文分词同时保留词串和 2-gram——保证"差评率"这类中文术语和 `product_category_name` 这类字段名都能被精确命中。

### RRF 相比分数加权有什么优势？

**问题出在分数的量纲上。**稠密向量的分数是余弦相似度（0-1 之间），BM25 的分数没有上界（可能是 5 也可能是 50）——两路分数直接相加，BM25 路天然碾压向量路。要做加权就得先归一化，而归一化对分数分布非常敏感：某一路这次查询分数整体偏高（比如 BM25 对短 Query 打分普遍低），归一化参数就得跟着变，工程上很难调稳。

**RRF 的思路是干脆抛弃分数、只用排名**：一个文档在向量路排第几、BM25 路排第几，按 `1/(k+rank)` 加权求和（k=60 是平滑常数，防止第一名权重过大）。排名是天然的"归一化"——不管分数绝对值多大，第一名就是第一名。

一个具体的融合例子：文档 X 在向量路排第 1、BM25 路排第 8；文档 Y 在两路都排第 3。RRF 得分 X = 1/61 + 1/68 ≈ 0.0311，Y = 1/63 × 2 ≈ 0.0317——**Y 胜出**。X 虽然向量路第一，但 BM25 第 8 说明关键词匹配弱；Y 两路都靠前，是更稳健的候选。RRF 天然奖励"两路都认可"的文档，这正是混合检索想要的效果。

工程收益：不依赖分数量纲、不需要归一化、任何一路检索器替换（比如 BM25 换成 SPLADE）都不影响融合逻辑。是业界融合检索的标准做法之一。

### 检索的 Top-K 设置为多少，为什么这么设计？

知识库检索 Top-6、Few-shot SQL 示例 Top-3、记忆召回按类型各取 Top-K 再融合。设计原则是**宁多勿漏 + 精排收敛**：召回阶段放大 K 保证覆盖率（漏了就没机会了），再由 Rerank / 融合排序把噪声压下去。K 太大会把弱相关内容塞进上下文稀释注意力，太小会漏关键证据——这个值是按 Bad Case 归因调出来的，不是拍的。

### 文档入库的流程是怎样的？

文档加载（PDF 等格式）→ 父子块两级切分 → 子块元数据增强（父块 ID、内容 hash）→ sha256 哈希去重（过滤已入库的重复块）→ Embedding 编码 → 写入 Milvus（稠密向量 + BM25 稀疏向量同时维护）→ 父块文本和元数据存 PostgreSQL。整个入库链路是增量的，重复跑不会产生重复数据。

### Embedding 模型是怎么选型的？

选型维度：**中文效果**（业务术语理解）、**向量维度**（与现有集合 schema 匹配，换模型维度变了要重建索引）、**成本**（SiliconFlow 的 bge-m3 免费且中文效果好）、**部署形态**（Ollama 本地跑占用内存大，不适合放进容器）。

最终选 bge-m3（1024 维，多语言，支持稠密+稀疏双输出）。工程上做了多厂商解耦：Embedding 层抽象工厂支持 SiliconFlow / DashScope / Ollama / 任意 OpenAI 兼容服务，换模型只改配置不改代码。

### Milvus 的 Lite 和完整版有什么区别？怎么做的兼容？

Lite 是本地文件形态、零依赖，适合原型；standalone 是完整集群，适合生产。真实差异包括：Lite 不支持 `wait_for_creating_index` 等管理 RPC（需要补丁跳过）、分词器只支持 `jieba` 不支持 `chinese`。项目通过连接地址形态自动识别模式——本地文件路径走 Lite 快速路径，TCP 地址走完整版原生逻辑，**一套代码同时覆盖原型和生产**。

### Rerank 踩过什么坑？

不同厂商的 Rerank 响应格式不一致：DashScope 返回 `document: {text}`，SiliconFlow 可能返回 `document: null`。原代码用 `if "document" in item` 判断格式，对 `None` 下标操作直接崩溃——修复为判断 `document` 非空。**这类多厂商兼容 bug 的教训是：对第三方响应的格式假设必须做防御性判断，且每种格式都要有测试用例。**

### 为什么需要查询改写？指代消解是怎么做的？

**先理解为什么需要改写：**用户在多轮对话里经常用指代和省略——"它多少钱""再把圣保罗州拆一下""顺便对比下差评率"。直接拿这种原始 Query 去检索，召回质量必然很差，因为检索器看不到上下文里"它""圣保罗州"指代什么。

本项目的 `QueryRewriter` 做两件事：

- **指代消解**：把"它""那个""上面说的"这类代词替换成上下文里明确的实体。比如"它多少钱"→"Olist 本月销售额是多少"；

- **省略补全**：用户说"再按品类拆一下"，QueryRewriter 补全成"再按 product_category_name 拆分 Olist 本月销售额"。

改写后的 Query 再进检索链路，召回的相关性和准确率都显著提高。这是多轮对话场景下 RAG 能跑稳的前置条件——不做改写，第一轮之后的检索质量会断崖式下降。

### 什么是 RAG 的 Lost in the Middle 问题？怎么解决？

**Lost in the Middle** 指的是大模型在长上下文里对中间位置信息的关注度下降——模型对上下文开头和结尾的内容记忆较好，但对中间段的内容容易"忽略"。

具体表现：检索回来的 10 条证据，开头和结尾的几条模型用得上，中间几条即使包含关键信息也可能被忽略。这不是模型 bug，而是注意力机制的特性。

本项目的应对：

- **精排收敛**：不堆量，召回多但注入只保留 Rerank 后的 Top-N，减少中间段长度；

- **关键内容前置/后置**：重要约束（口径定义、JOIN 路径）放上下文头尾而不是中间；

- **结构化标注**：用 `【Schema 证据】【相关记忆】`这类显式标记分段，帮助模型识别每段信息的角色，降低被淹没的概率。

### 什么是 Agentic RAG？它和传统 RAG 的区别是什么？

**传统 RAG 是一次性检索**：用户问一个问题 → 检索一次 → 把结果塞进 Prompt → 模型生成答案。不管检索结果够不够，都只有这一次机会。

**Agentic RAG 把检索变成 Agent 可反复调用的工具**：模型第一次检索后发现信息不足，可以自主决定再检索一次（换关键词、换检索范围、换检索类型），直到信息足够才输出最终答案。

核心区别是**检索的主动权从"流程固定"变成"模型自主决策"**：

- 传统 RAG：检索是前置步骤，模型只管最后的生成；
- Agentic RAG：检索是模型可调用的工具，模型根据中间结果决定是否再检索、检索什么。

本项目的 ReAct 循环 + `recall_context` 回忆机制就是 Agentic RAG 的实践——模型不只在开始检索一次，执行过程中需要历史细节时可以主动召回被压缩存档的内容。Schema 的"表间关联关系"本质也是一个小型图谱（表是节点、外键是边），具备 GraphRAG 的雏形。

### 什么是 GraphRAG？和普通 RAG 有什么区别？

**GraphRAG 用知识图谱组织文档实体和关系**，检索时沿图谱游走，适合跨文档的多跳推理。

- **普通 RAG**：文档切成块，基于向量相似度召回，块之间是独立的——跨文档推理（"A 公司的创始人和 B 公司的 CTO 是什么关系"）需要多次召回拼接，效果不稳定。

- **GraphRAG**：先把文档解析成实体和关系（节点和边），检索时沿图谱游走，天然支持多跳关系推理。代价是建图成本高、维护复杂。

本项目 Schema 的"表间关联关系"本质就是一个小型图谱（表是节点、外键是边），Schema 三级检索里的"已验证 JOIN 关系"就是图谱游走的体现——不让模型猜 JOIN 路径，而是按已治理的图谱边走。

## 记忆与上下文管理

### 什么是长期记忆，什么是短期记忆？

大模型本身是**无状态的**，每次生成回答只能看到当前输入的 Prompt，所谓记忆本质是把历史信息以某种方式重新提供给模型。

- **短期记忆：**当前会话的上下文。本项目用 Redis 会话快照实现——每轮对话后会话状态经 zlib 压缩存入 Redis，支持服务重启后 `--resume` 恢复；多轮连贯性由最近轮次上下文 + 检查点保证。

- **长期记忆：**跨会话持久化的记忆系统，不固定拼进 Prompt，需要时检索注入。

两者解决不同问题：短期记忆保证"这轮对话接得上"，长期记忆保证"上次说过的偏好还记得"。

### 三级分层记忆是怎么做的，为什么这么设计？

**怎么做：**借鉴认知心理学的长时记忆三分法，把长期信息分三类存入 Milvus 记忆集合：

- **语义记忆**存稳定事实（"用户关注的销售额口径是含税口径"）；

- **情节记忆**存事件序列（"上周三用户查过 11 月异动归因"）；

- **程序记忆**存技能习惯（"用户偏好带 SQL 和数据表格的回答"）。

存储上每条记忆带完整元数据：`memory_type`（三级分类）、`importance`（重要性评分）、`created_at` / `last_access_at`（时近性依据），并同时维护 HNSW 稠密向量索引和 BM25 稀疏向量索引。召回时按记忆类型并行双路检索，经 RRF 融合后，再按 **alpha × 语义相似度 + beta × 时近性（指数衰减）+ gamma × 重要性** 加权排序，只注入与当前问题相关的条目。

**有什么用：**如果不分级，过期事件会被当作事实引用——把"上周的临时查询条件"误认为长期偏好，回答被污染。三级分离后语义记忆补充知识、情节记忆保证连贯、程序记忆负责个性化，互不干扰。融合排序解决"召回的记忆太多、该信哪条"的问题：语义相近但半年前的事件，会输给语义稍弱但刚发生且重要的记忆。同时稳定的用户偏好跨会话复用，一次性的 SQL 结果不会无限占用上下文窗口。

### 记忆有冲突怎么办？比如用户之前说看含税口径，最近改口了

**先想清楚冲突不处理会怎样：**如果"销售额看含税口径"和"销售额看不含税口径"两条记忆共存，检索时两条都可能被召回并注入上下文，模型看到两个相反指令，随机选一条——同一个用户、同一个问题，今天答含税明天答不含税，回答完全不可控。

本项目的处理是**写入前冲突检测**：新记忆入库前，先和已有记忆做语义相似度比对——发现语义高度相似但内容矛盾的旧条目时，不是新增一条，而是**以时近性优先更新旧条目**（最新的声明覆盖旧的，同时保留更新时间戳）。背后的假设是：用户改口是正常行为，"最近说的"比"以前说的"更能代表当前偏好。

另外两个配套设计：**importance 评分**让重要的口径类记忆不容易被低价值新记忆误更新；**矛盾告警**——检测到口径级冲突时在 Trace 里留痕，复盘时能查到"什么时候、因为哪句话改了口径"。

### 记忆是什么时候写入的？写太频繁或太少会怎样？

两条写入路径：**实时写入**（对话中出现明确偏好声明或关键事实时，LLM 抽取为结构化条目直接写）+ **后台压缩**（长对话定期沉淀为摘要记忆）。

写入频率的权衡：

- **写太频繁**：噪声淹没信号——临时查询条件、一次性结论都入库，检索时干扰项变多，记忆库变成垃圾场；

- **写太少**：用户偏好丢失，跨会话复用能力形同虚设。

本项目的平衡：只写**稳定的事实与偏好**（语义记忆）、**有回顾价值的事件**（情节记忆）、**反复出现的行为模式**（程序记忆）；一次性的大查询结果只进 ContextStore（7 天过期），不进长期记忆。`importance` 评分由 LLM 在抽取时一并给出，作为后续融合排序的权重之一。

### 上下文组装是怎么做的？

**先理解为什么需要组装：**大模型每轮请求看到的只有一份消息列表，它自己不会"记得"任何事——所谓多轮对话，真相是系统每轮都把相关历史重新塞进 Prompt。所以每一轮请求前，系统都要把散落各处的信息重新整理成一份"可思考的材料"，这个动作就是上下文组装。

本项目按模板组装为三部分：

- **system prompt**：Agent 身份、能力描述、工具列表。永远不变、永不压缩——它是系统正常工作的基础；

- **context prompt**：记忆检索结果、Schema 召回、Skills 流程知识。**每轮动态生成**——同一用户连续问两个问题，注入的记忆和 Schema 证据是分别按当前问题重新检索的；

- **user/tool prompt**：当前问题与本轮工具结果。

组装后的实际形态举例（用户问"那把圣保罗州拆一下"的当轮请求）：

```text
[system] 你是 NexusMind 数据分析 Agent...可用工具：execute_sql_guarded...
[system] 【相关记忆】用户偏好：结果按降序表格展示（语义记忆，相似度0.88）
[system] 【Schema 证据】数据域 olist_order；表 olist_orders_dataset...
[system] 【历史对话摘要】用户在做 Olist 地域销售分析；已确认口径：订单量=COUNT(DISTINCT order_id)...
[user] 那把圣保罗州的品类拆一下
```

这样每一轮模型看到的都是"当前问题最相关"的上下文，而不是历史的简单堆叠——固定拼接的问题在于：对话越长，无关历史占比越高，关键信息被稀释，token 成本也线性膨胀。

### 上下文压缩是怎么做的？为什么不是简单保留最近 N 轮？

**怎么做：**当会话 Token 超过阈值（默认 6000）时自动触发压缩，有四个关键设计：

- **system 消息永远不压缩**——它包含 Agent 的身份定义、能力描述和工具列表，是系统正常工作的基础，压缩只针对对话历史；

- **切分点回溯**——保留最近若干条消息时，如果切分点刚好落在 tool 消息上，自动往前回溯到最近的 assistant 消息，避免把一组完整的 tool_use + tool_result 拆开，保证模型看到的上下文结构完整；

- **轻量模型生成结构化摘要**——保留关键问题、已确认事实、用户偏好和待办事项，省略寒暄与中间推理，压缩后消息列表变为 system + 摘要消息 + 最近保留消息；

- **压缩前完整 transcript 存档**——压缩是有损的，被压缩掉的历史带 ref_id 存档到 ContextStore，摘要消息里附引用，模型需要细节时可以回忆。

**为什么按 token 阈值触发而不是保留最近 N 轮：**保留 N 轮对长消息和短消息一视同仁——10 轮闲聊可能只占几百 token，3 轮带大查询结果的对话可能就超窗口了。按 token 阈值触发才是真正面向上下文窗口资源的管理。

### 动态上下文是怎么做的？为什么截断不够？

单纯截断是有损的——没有人能说明白截 30k 够还是 40k 够，关键信息可能恰好被截掉。项目的解法是**外置文件存储 + 按需回忆**：工具结果两级截断（先按 token 比例粗截、再逐行精修防截半行），被截断的完整内容以文件形式带 `ref_id` 存档到 ContextStore，运行时上下文里只保留占位符和引用地址；Agent 需要时通过 `recall_context` 工具按 **grep（正则过滤行）/ tail（末尾 N 行）/ full（完整内容）** 三种模式主动回忆。

**核心思想：把"截断丢信息"改造成"可检索的延迟加载"。**截断策略决定"现在看什么"，存档召回保证"需要的时候还能找到什么"。工程防护：ref_id 格式校验防路径穿越、单文件大小上限、7 天过期自动清理。

### Redis 会话快照具体怎么做的？踩过什么坑？

**怎么做：**每轮对话结束后把会话状态（消息历史、中间结果）序列化 + zlib 压缩，作为快照写入 Redis（24h TTL）；重启或新会话可通过 `--resume` 恢复最近快照；同时维护用户会话索引（ZSet 按时间排序），支持会话列表查询和删除。

**踩过的坑：**`zlib.compress()` 产出的二进制快照被 `decode_responses=True` 的 Redis 客户端强制 UTF-8 解码，直接 `UnicodeDecodeError`——修复方式是为二进制数据建独立的客户端连接，与文本客户端隔离。这个 bug 已固化进回归测试。

### 什么是上下文工程？它和 Prompt 工程的区别是什么？

**上下文工程（Context Engineering）是比 Prompt 工程更高一层的概念。**Prompt 工程关注"怎么把一条指令写好"，上下文工程关注"每轮请求时，模型应该看到哪些信息、以什么结构看到、多出来的信息放哪里"。

本质区别在于**系统是否主动管理模型看到的信息**：

- **Prompt 工程**：主要面向单轮交互——写好 system prompt、设计 few-shot 示例、调整措辞。模型看到的就是开发者一次性塞进去的内容。

- **上下文工程**：面向多轮、长链路的 Agent 系统。模型每轮看到的上下文都是系统**动态组装**出来的，包含系统提示、历史摘要、检索结果、记忆召回、工具结果、当前问题等多个来源。系统要决定每类信息放多少、按什么顺序、什么时候压缩、什么时候丢弃。

本项目就是典型的上下文工程实践：system 永不压缩、对话历史按 token 阈值自动压缩、记忆按需检索注入、工具结果带 ref_id 延迟加载。**Prompt 工程解决"怎么问得好"，上下文工程解决"怎么让模型每轮都看到当下最相关的信息"。**

## MCP 与 Skills

### MCP 是什么？

MCP（Model Context Protocol）是 Anthropic 推出的开放协议，定义了大模型与外部工具通信的统一规范——可以理解为 AI 世界的 USB-C 接口，基于 JSON-RPC 2.0，主流传输是 stdio（本地子进程）和 Streamable HTTP（远程服务化）。工程实现上直接用官方 mcp SDK：协议完整（版本协商、capabilities、标准错误码）、跟随规范演进，精力可以放在工具路由和业务逻辑上，而不是传输层。

### MCP 和 Function Calling 有什么区别？

Function Calling 是 LLM 模型本身的内部能力，定义模型如何识别意图并结构化输出调用参数；MCP 是与具体 LLM 无关的外部通信协议，定义这些调用请求如何在不同进程或网络节点间传输。**Function Calling 解决"想做什么"，MCP 解决"怎么连通去做"**——模型通过 Function Calling 决定调用某个函数，再通过 MCP 协议把请求发给远端的工具服务器。

### 你们的 MCP 工具层怎么实现的？

**协议接入：**外部 MCP Server 用官方 mcp SDK 的 `ClientSession` 接入——stdio 走 `StdioServerParameters + stdio_client`，远程走 `streamablehttp_client`；握手、协议版本协商、消息分帧全由 SDK 处理，连接失败降级为仅内部工具。

**工具路由：**`MCPToolRouter` 完整链路——QueryRewriter 对话感知改写（指代消解、省略补全，比如"它多少钱"先补全指代）→ tools/list 工具发现 → LLM 对候选工具 0-10 分相关性打分取 Top-K → 参数推断 → 执行。

**接入方式：**外部工具以 `server:tool` 命名空间注册，与内部工具（SQL 执行、知识库检索、记忆检索、上下文召回）无差别路由；`MCP_SERVERS` 环境变量配置，懒加载，失败降级仅内部工具。已用官方 SDK 示例 server 做过端到端验证（握手 / 发现 / 调用 / 断开）。

### 工具调用里 LLM 重排是怎么做的，有什么用？

工具发现（tools/list）可能返回几十个候选工具，全部塞给模型会分散注意力、提高选错概率。做法是：QueryRewriter 先对 Query 做对话感知改写，然后 LLM 对每个候选工具的描述与当前 Query 的相关性打 0-10 分，取 Top-K 进入参数推断。**本质是把"工具选择"从一次性的大选择题拆成"粗筛 + 精排"两步，和检索链路的召回 → Rerank 是同一个思想。**

### MCP 和 Skills 的分工是什么？

MCP 解决"**怎么接工具**"（协议与生命周期），Skills 解决"**调用工具时遵循什么流程**"（可复用的业务 SOP 与约束，检索后动态注入 Prompt）。Skill 相比 Prompt 的核心区别是**渐进式加载**：系统开始时只加载所有 Skill 的名称和描述用于匹配，命中后才读取完整流程，避免所有规则堆积在一个系统提示词中。新增工具不改主链路，新增业务流程只加一个 Skill 文件，模型能力与外部能力彻底解耦。

## 监控与治理

### Monitor 闭环监控是怎么做的，有什么实际效果？

**怎么做：**三层架构——采集层在每个 Agent 执行时记录延迟、token 消耗、成功/失败；聚合层用滑动时间窗口（最多 1000 条记录 / 5 分钟）算出每个 Agent 的 p99 延迟、成功率、平均 token；调整层按聚合指标在线调整路由权重：成功率 < 95% 权重减半，p99 > 3s 再减半，p99 > 5s 降为 0.1，持续稳定（成功率 > 99% 且 p99 < 1s）权重上浮 1.2 倍封顶。

**有什么用：**路由从静态配置变成在线自愈——某个 Agent 连续失败（比如 RAG 检索的向量库网络抖动），Monitor 实时把它的权重降到接近 0，Supervisor 转而路由到兜底 Agent，用户无感知。我们测试过故意让某个 Agent 超时，3 次失败后成功率降为 0、权重降到 0.1，系统自动切换路径——这是"降级自愈"而不是"系统崩溃"。坦白说单机环境下各 Agent 共享同一 LLM，效果差异不容易看出来，真正的价值在生产环境：依赖的某个外部服务突然变慢时，系统自己完成降级，不需要等人半夜起来改配置。

### 为什么用 p99 而不是平均延迟做降级依据？

平均延迟会被大量正常请求"稀释"——99 个 100ms 的请求加 1 个 10s 的请求，平均才 200ms，看起来一切正常，但那 1 个超时请求可能正是系统故障的早期信号。p99 关注的是"最差的 1% 体验"，对尾部恶化敏感得多。Agent 系统的故障往往不是全面崩溃而是局部劣化（某个依赖偶发超时），p99 能在成功率还没掉的时候就捕捉到这种劣化。

### Token 成本怎么治理？

token 是 Agent 系统的主要可变成本，本项目的治理手段按收益排序：

1. **路由分流**：简单问题走快速路径（一次 LLM 调用），不让所有问题都进 ReAct 多轮循环——这是最大的成本杠杆；

2. **语义层编译零 LLM 成本**：命中已治理指标的问题不调用生成模型；

3. **强弱模型分级**：诊断/规划给 SOTA，执行/摘要给 flash/轻量模型；

4. **上下文瘦身**：工具结果两级截断、自动压缩、Schema 三级收敛（不把全量 DDL 塞给模型）；

5. **缓存与复用**：语义层 SQL 天然可缓存（同一 Metric Plan 永远编译出同一 SQL），会话状态快照避免重建上下文。

Monitor 同时采集每个 Agent 的平均 token 消耗，成本异常会成为权重调整的信号之一。

### 全链路追踪是怎么做的？为什么不用现成的 OpenTelemetry？

**怎么做：**两层实现——`Tracer` 是 MTrace 风格的 Span 树（兼容 OpenTelemetry 概念：一次请求 = Trace，每个 Agent 节点 = Span，记录起止时间、耗时、状态、tags，支持父子关系与错误传播）；`TraceStore` 把每次请求的完整链路落 JSONL：问题、意图、路由决策与理由、Schema Linking IR、Metric Plan、最终 SQL、各 Span 耗时、重试次数、错误上下文。

**有什么用：**LangGraph 节点跳转的耗时拆解完全可视化，哪一跳慢了一目了然——编排延迟从 29s 优化到约 10s 就是靠这个定位到冗余调用和可并行的节点。不用原生 OpenTelemetry 是因为当前规模下一个 118 行的轻量实现就够用，且概念完全兼容，未来可直接替换为 OTel exporter。

### Bad Case 是怎么采集和流转的？

**采样策略：错误必采、慢查询（>15s，可配）必采、发生重试必采、正常请求 10% 随机采样。**采样结果自动进入在线 Bad Case 库，后续走自进化闭环：LLM 从 Bad Case 抽取可复用规则 → 置信度 ≥0.85 自动注册为 Skill，低置信度人工评审。这样"线上出问题 → 自动沉淀为流程知识"形成闭环，系统越用越聪明。

## 评测方法

### 你们在 Spider 上的评测是怎么做的，结果如何？

Spider 是 Yale 的跨域 Text2SQL 学术基准，我们使用其 dev 集全部 20 个异构数据库的官方真实 SQLite 数据，每库采样 5 题共 99 题。生成设定是 **zero-shot**（无 few-shot、无自我一致性投票）、温度 0.0，Prompt 为完整 DDL + 外键 + 每表 3 行样本数据。

**四项核心指标结果：**

| 指标 | 结果 | 衡量的问题 |
|---|---:|---|
| EX（执行准确率，严格判等） | **78.8%（78/99）** | 结果集与 Gold SQL 完全一致 |
| 表命中率（Schema Linking） | **97.0%（96/99）** | 是否选择了正确的表 |
| 行召回率（Row Recall） | **0.851** | Gold 中应返回的行是否被查全 |
| 字段准确率（Cell Accuracy） | **0.898** | 已匹配行中的单元格值是否正确 |

20 个库中 10 个达到 EX 满分（含 8 表复杂 Schema 的 dog_kennels），原始数据落盘在 `docs/eval_spider.json`，每题的 Gold SQL、Agent SQL、执行结果都可逐题复核。

**如果面试官追问"具体跑一道题是什么样"，可以拿出真实样例：**

```text
数据库：dog_kennels（8 表复杂 Schema）
问题：List the names of dogs that have charges.
Gold SQL：SELECT DISTINCT d.name FROM Dogs d JOIN Charges c ON d.id = c.dog_id ...
Agent SQL：SELECT name FROM Dogs WHERE id IN (SELECT dog_id FROM Charges)
两条 SQL 写法不同但执行结果集一致 → EX 判定通过（exact_match）
```

这个例子恰好能说明 EX 指标的合理性：EX 比较的是执行结果而非 SQL 字符串，等价写法不受影响。

**也能主动展示失败样例体现诚实**：orchestra 库有一题"按频率排序"，Agent 排序方向反了且多返回了未要求的列——行召回和字段准确都满分但 EX 失败。这类"行列都对但整体不匹配"的失败让我们发现了"只返回题目要求的列"这条生成约束的必要性。

### 为什么除了 EX 还要保留表命中率、行召回率、字段准确率？

EX 只回答"最终结果对不对"，无法定位错误发生在哪。四项指标构成诊断链：**选对表（97.0%）→ 查全行（0.851）→ 值准确（0.898）→ 整体对（78.8%）**。

这个诊断链直接揭示了优化方向：表命中率显著高于行召回率，说明瓶颈不在 Schema Linking 而在复杂过滤与 JOIN 完整性——后续优化应该围绕行召回展开（多阶段生成、执行反馈修复），而不是继续在选表上投入。**没有字段级指标，这个结论就得靠猜。**

### 你的 EX 是严格判等吗？口径具体怎么定义的？

**是严格判等：Agent SQL 与 Gold SQL 在同一数据库上的执行结果集完全一致（忽略行序）才计正确。**早期版本曾把 Jaccard≥0.8 也算通过（对应 81.8%），后来主动收紧——Jaccard≥0.8 的 3 题改记为"部分正确"参考项，不计入 EX，严格口径即 78.8%。口径收紧让分数降了 3 个百分点，但保证了与学术基准的语义对齐。

如实说明两点局限：一是 Spider dev 全集 1034 题，我们是每库采样 5 题共 99 题，存在采样偏差；二是 Spider dev 的 20 个库相对偏简单。所以 78.8% 刻画的是"采样子集上的 zero-shot 水平"，与 Spider test 集 SOTA（86-91%，且普遍使用 few-shot + 自我一致性）不直接可比。

## 自进化与可观测

### 自进化机制是怎么闭环的？

全自动：后台任务随应用启动，每 5 分钟（可配）轮询 Bad Case 库 → LLM 从低分样本抽取可复用规则（Jaccard 相似度去重）→ 置信度 ≥0.85 自动接受注册为 Skill，低置信度保持 pending 等人工评审。关键设计：**幂等**（已处理 ID 持久化防重复进化）、**双阈值**（高置信自动、低置信人工把关，防幻觉规则污染 Skill 库）、**可观测**（运行状态有 API 可查，可手动触发、可一键关闭）。

### 全链路可观测是怎么做的？

TraceStore 以 JSONL 记录每一次请求的完整链路：用户问题、Schema Linking 的 IR、路由决策与理由、最终 SQL、执行耗时、Guard 告警、错误上下文。慢查询和异常自动采样进 Bad Case 库，驱动离线归因和自进化。**每一次结论可复核、每一个线上问题可定位**——这是企业系统和小 demo 的关键区别。

# 基础知识回顾

## Text2SQL 专题

### 有没有了解过 Text2SQL？主要解决什么问题？

Text2SQL 本质上是**将自然语言问题自动转换为 SQL 查询语句**的技术，目标是让用户不需要直接编写 SQL，也能从数据库中获取想要的结果。核心价值：降低数据库使用门槛（业务人员直接提问）、提升查询效率（省去"提需求 → 写 SQL → 返结果"的长链路）、复杂查询自动化（多表 JOIN、分组统计）。

### EX 和 EM 指标的区别？业界的评测基准有哪些？

EM（Exact Match）比较 SQL 字符串是否完全一致，受等价写法干扰大（`a=b` 和 `b=a`、子查询 vs JOIN 都会被判错）；EX（Execution Accuracy）比较执行结果集，是业界主流。主流基准：**Spider**（Yale，跨域，dev 集 1034 题）和 **BIRD**（更接近真实业务，含脏数据、外部知识、执行效率要求）。Spider test 集 SOTA 约 86-91%（GPT-4 + few-shot + 自我一致性），GPT-4 zero-shot 约 60-75%。本项目在 Spider dev 采样 99 题上 zero-shot 严格口径 EX 78.8%，并如实标注了采样范围与口径。

### 你会如何设计一个 Text2SQL 智能体，讲讲思路

我会把 Text2SQL 拆成**意图理解、Schema 检索、SQL 生成、SQL 执行与校验**四个阶段，并且特别强调前置的口径治理：

**（前置条件）语义层与 Schema 管理：**先把表结构、字段含义、主外键关系、业务指标口径整理成可检索、可编译的治理资产。Text2SQL 最容易出错的不是 SQL 语法，而是选错表、选错字段、理解错业务口径。

1. **意图理解**：识别指标、维度、时间范围、过滤条件、排序要求，产出结构化 IR——中间结果可审查，是后续归因的抓手。

2. **Schema 检索**：不能把所有表结构都塞给模型（Token 成本高、干扰多），按 Domain → Table → Column 三级收敛，结合 DDL + 业务定义 + 历史 SQL 示例混合检索。

3. **SQL 生成**：已治理指标走语义层确定性编译（口径可审计）；开放问题才交给 LLM，复杂查询先生成查询计划再生成 SQL。

4. **执行与校验**：生成后不能直接执行——AST 静态校验（只读 / 方言 / 表列存在性）→ 执行失败自修复 → 结果合理性检查（空结果 / 截断 / NULL 占比 / 比率越界）。SQL 语法正确不代表结果正确，结果层的合理性检查是防静默错误的关键。

### Text2SQL 业界常用方案与技术框架你了解哪些？

1. **Prompt 直出 SQL**：适合小规模表和简单查询，实现简单但表多后受无关 Schema 干扰。

2. **RAG 增强 Text2SQL**：先检索 Schema / 历史 SQL 再生成，**Vanna** 是典型代表（DDL、文档、历史 SQL 训到向量库，按需召回）。

3. **语义层约束**：**WrenAI**（MDL 声明式语义建模）、dbt MetricFlow，把指标口径从模型生成中剥离，确定性编译。

4. **Agent 式 Text2SQL**：生成 → 执行 → 报错 → 修复的执行反馈循环，**DB-GPT**、LangChain SQLDatabaseToolkit 是这个思路。

**目前存在的难点：**

- **⭐Schema 召回与理解**：最核心的难点，模型最易错的不是语法而是选错表、选错字段、连错 JOIN 路径；

- **指标口径对齐**："销售额""活跃用户"背后可能对应不同字段和计算方式，需要语义层显式定义；

- **多表 JOIN**：需要主外键关系和 JOIN 路径约束，不能让模型自由拼接；

- **结果难以校验**：SQL 能执行不代表结果对，需要执行前校验 + 执行后合理性检查 + 评测归因闭环。

### 如何提升 Text2SQL 的准确率？

按本项目实测收益排序，五层手段各解决一类错误：

1. **口径治理（收益最大）**：语义层把指标定义固化为代码。解决的是"模型不知道销售额=SUM(price) 而不是 SUM(payment_value)"这类业务理解错误——这类错误靠换模型解决不了，因为模型根本没地方知道这个口径。

2. **约束生成**：方言规则（SQLite 不能用 LEFT()）、LIMIT 规则（TopN 必须加 LIMIT）、结果完整性约束（只返回题目要求的列）。解决的是模型生成的"习惯性错误"——这些规则写进 Prompt 和校验器，从"提醒"变成"强制"。

3. **Schema 增强**：表间关系图（不让模型猜 JOIN 路径）、字段语义标注（说明 customer_id 和 customer_unique_id 的区别）、每表 3 行样本数据（让模型看到字段真实长什么样，比如状态枚举是 'SP' 不是 'São Paulo'）。

4. **执行自修复**：报错信息 + Schema 反馈重试，最多两轮。解决方言细节和笔误类错误。

5. **评测归因**：字段级指标（表命中/行召回/字段准确）定位失败集中在哪个环节，再针对性优化——比如本项目发现表命中率 97% 但行召回只有 0.851，瓶颈在复杂过滤条件，后续优化就围绕行召回展开，而不是继续在选表上投入。

核心认知：**准确率提升的大头不在"换个更强的模型"，而在工程约束和评测闭环**。强模型在没有任何口径信息时一样会犯"支付拆分重复计数"这种错误——因为它错的原因不是笨，是不知道。

### Text2SQL 的难点有哪些？

Text2SQL 的难点不在于"模型会不会写 SQL"，而在于**自然语言的模糊性和数据库结构的严谨性之间的鸿沟**：

- **自然语言歧义**：同一个"销售额"在不同部门可能指不同口径（含税/不含税、下单口径/支付口径）。模型不知道业务约定，只能猜——猜错了 SQL 语法再对结果也是错的。解法是语义层把口径固化，让模型"查"而不是"猜"；

- **Schema 复杂性**：真实业务库几十上百张表、上千字段，全塞进 Prompt 既超 token 又让模型选错。解法是三级检索（域 → 表 → 字段）收敛到最小充分 Schema；

- **JOIN 路径**：多表关联的 JOIN 路径不唯一（A→B→C 还是 A→C 直连），模型自由拼接容易选错或重复计数。解法是已验证的 JOIN 关系图，不让模型猜；

- **方言差异**：SQLite、MySQL、PostgreSQL 的日期函数、字符串函数语法不同，模型经常混用。解法是方言函数黑名单 + 自修复；

- **静默错误**：SQL 能执行但结果错（空结果、比率越 100%、TopN 忘加 LIMIT）。这类错误最难发现——语法没错、执行没报错，但数字就是错的。解法是结果合理性检查；

- **相对时间**："最近三个月""上月"这类相对时间表达式，模型不知道今天日期就无法正确计算。解法是系统侧锚定当前日期。

### Text2SQL 的主流框架有哪些？

按技术路线分四类：

1. **Prompt 直出类**：直接把 DDL + 问题塞给 LLM 生成 SQL。简单但表多时受无关 Schema 干扰，适合小库简单查询。

2. **RAG 增强类**：先检索相关 Schema / 历史 SQL 再生成。代表是 **Vanna**——把 DDL、文档、成功 SQL 训到向量库，按 Query 召回相关 Schema 和 Few-shot 示例注入 Prompt。优势是能积累历史经验，越用越准。

3. **语义层约束类**：用建模语言显式定义指标口径，确定性编译 SQL。代表是 **WrenAI**（MDL 声明式语义建模）和 **dbt MetricFlow**。优势是口径可审计、结果可复现，适合企业 BI 场景。

4. **Agent 式**：生成 → 执行 → 报错 → 修复的执行反馈循环。代表是 **DB-GPT** 和 **LangChain SQLDatabaseToolkit**。优势是能根据执行反馈自修复，劣势是链路长、成本高。

本项目是 2+3+4 的融合：RAG 做 Schema 检索、语义层做口径编译、Agent 范式做自修复和根因分析——取各家之长。

### 什么是 DMS-SQL？多 Agent Text2SQL 了解吗？

**DMS-SQL** 是一种多 Agent 的 Text2SQL 框架思路，核心思想是**按 SQL 生成的不同阶段分派给专职 Agent**，而不是一个模型从头做到尾：

- **Selector Agent**：负责从全量 Schema 里选出与问题相关的表和字段；
- **Detector Agent**：负责识别问题里的实体和关系，做 Schema Linking；
- **Refiner Agent**：负责把自然语言问题改写得更清晰、消解歧义；
- **Writer Agent**：负责按选好的 Schema 和改写后的问题生成 SQL。

每个 Agent 专注一件事，能力边界清晰，也方便针对性优化。和单 Agent 相比，多 Agent 的优势是**每个阶段可以独立评测和改进**——Selector 选错了不影响 Detector 的能力评估，问题定位更精确。

本项目的 Schema 三级检索 + IR 抽取 + 编译/生成的链路也体现了类似的分工思想，只是用 Workflow 骨架固定步骤、节点内用 Agent 能力，而不是拆成四个独立 Agent。

### Text2SQL 怎么处理多表 JOIN？

多表 JOIN 是 Text2SQL 的高频错误点，模型自由拼接 JOIN 路径容易出错（选错关联字段、重复计数、漏 JOIN）。本项目的处理：

- **已验证 JOIN 关系图**：语义层里每个指标定义都标注了可用维度和对应的 JOIN 路径（比如 sales_revenue 按 product_category_name 分析时走 order_items → products → category_translation 三表 JOIN），模型不猜路径，按图走；

- **外键约束**：Schema 检索时输出表的外键关系，让模型知道"这两张表通过哪个字段关联"；

- **口径防重复计数**：指标定义的 description 里写明"避免支付拆分重复计数"——订单和支付是一对多，用支付表算销售额会虚增，这类陷阱写进口径；

- **复合计划模板**：多表关联的复杂查询（跨库对比、品类差评拆解）走复合模板，JOIN 结构整个由模板固化，不走单指标拼接。

核心思想：**JOIN 路径是业务约定，不是模型该猜的事**——把它从概率生成里剥离出来固化为代码。

### Text2SQL 怎么做执行反馈修复？

执行反馈修复是 Agent 式 Text2SQL 的核心能力——SQL 执行报错后，把错误信息反馈给模型重新生成。本项目的实现：

- **结构化错误反馈**：数据库报错时，不只返回原始错误信息，还附上 Schema 节选（相关表的 DDL）、方言规则提示（"SQLite 不支持 LEFT()，用 substr()"），让模型有依据地改；

- **轮次上限**：最多 2 轮，修不好就把告警抛给上层展示，不无限循环；

- **意图保持约束**：修复提示词明确要求"保持原查询意图不变"——防止模型把"查销售额"改成"查订单量"这种跑偏；

- **重新过校验**：修复后的 SQL 仍要重新过静态校验和合理性检查，不能因为"修复过"就放行。

工程记录里有过反例：AST 误拦截合法 SQL 触发自修复，模型反而生成了跨域错误 SQL——这说明自修复的质量取决于前置校验的准确性，所以校验器本身的正确性优先级最高。

### Text2SQL 怎么处理"口径漂移"问题？

口径漂移指**同一个业务概念在不同时间、不同人、不同上下文里被映射到不同字段或计算方式**。比如"销售额"：

- 有人指下单口径（order_items.price 求和）；
- 有人指支付口径（payments.payment_value 求和）；
- 有人要含税、有人要不含税。

模型每次生成 SQL 时可能选不同口径，导致**今天和明天的"销售额"对不上**。这是企业 BI 的致命问题——数字不可复现就不可信。

本项目的解法是**语义层把口径固化**：

- 每个指标有且只有一个确定的定义（事实表、聚合方式、过滤条件、可用维度）；
- 命中已治理指标的问题走确定性编译，口径由代码保证，不经过模型推理；
- 口径变更走版本化管理（改指标定义 = 改代码，有 diff、有 review），而不是"模型这次心情不一样"。

核心认知：**口径可信的前提是口径确定**——能确定的不交给概率。

### 什么是 BIRD 基准？和 Spider 有什么区别？

**BIRD**（Big Bench for Large Scale Database Grounded Text2SQL）是比 Spider 更接近真实业务的 Text2SQL 基准：

- **Spider**：Yale 出品，跨域（20 个异构数据库），主要考察 Schema 理解和 SQL 生成能力。dev 集 1034 题，test 集 隐藏。数据库相对干净、结构清晰。

- **BIRD**：更接近真实业务场景——**含脏数据**（值里有空格、NULL、格式不统一）、**需要外部知识**（"单价 = 价格 × 数量"这类业务常识不在 Schema 里）、**考察执行效率**（同一道题不同 SQL 执行时间差异大）。

区别总结：Spider 考"能不能写对"，BIRD 在此基础上还考"能不能在真实脏数据环境下写对、且写得高效"。

本项目选择 Spider 而不是 BIRD 做评测，是因为当前版本聚焦验证技术链路，BIRD 的脏数据场景需要额外的数据质量治理（本项目的 DataQualityAgent 已经在做这件事，但还没在 BIRD 上跑过完整评测）。

### Text2SQL 里怎么做 Schema Linking？

Schema Linking 指把自然语言问题里的实体映射到数据库的具体表和字段。这是 Text2SQL 最核心也最容易错的一步——选错表或选错字段，后面的 SQL 写得再漂亮结果也是错的。

本项目的做法：

- **三级检索收敛**：先选数据域（订单域 / 支付域 / 商品域），再选具体表，最后选字段。每一级缩小范围，避免全库 Schema 噪声干扰；

- **混合检索**：稠密向量召回语义相关（"销售额"→ sales_revenue），BM25 召回精确术语（表名、字段名），RRF 融合；

- **样本数据辅助**：每表 3 行样本数据让模型看到字段真实长什么样——比如状态枚举是 'SP' 不是 'São Paulo'，模型就不会在 WHERE 条件里写错值；

- **字段语义标注**：description 里说明 customer_id（每订单唯一）和 customer_unique_id（回头客共享）的区别，让模型选对字段。

本项目 Schema Linking 的表命中率 97.0%（96/99），说明这一层做得扎实——后续的失败主要在复杂过滤和 JOIN 完整性，不在选表。

### Text2SQL 怎么处理子查询和复杂聚合？

复杂聚合（多指标派生比率、嵌套子查询）是 Text2SQL 的难点——模型自由生成这类 SQL 几乎必然在口径上出错（分子分母不同口径、子查询的 GROUP BY 漏字段等）。

本项目的处理：

- **复合计划模板**：6 类高频复杂查询（支付方式统计、跨库订单发票对比、品类差评拆解、流派收入效率、卖家延迟率 TOP5、流派收入驱动）各有一个确定性模板。模板里固化了正确的聚合结构——比如延迟率 = 延迟单量 / 总单量，WHERE 不能提前过滤掉分母，整个 Plan 由模板生成；

- **不走单指标拼接**：两个独立编译的指标 SQL 拼在一起，口径几乎必然出错（过滤条件不一致、JOIN 路径不一致）。命中复合计划时整个 Plan 由模板生成，保证口径一致；

- **兜底给 LLM**：没命中任何复合模板的复杂查询走 LLM fallback，但同样要过 SQL Guard 三层校验，并且 Prompt 里给出方言规则和口径约束。

### Text2SQL 的评估为什么不能只看 EX？

EX（执行准确率）只回答"最终结果对不对"，但**答案错了你不知道错在哪**——是选错表、过滤条件漏了、JOIN 路径错了、还是聚合方式错了？这些错误的修复方式完全不同。

本项目用四项指标构成诊断链来定位：

- **表命中率**（97.0%）：选对表了吗？→ 考察 Schema Linking；
- **行召回率**（0.851）：该返回的行查全了吗？→ 考察过滤条件和 JOIN 完整性；
- **字段准确率**（0.898）：已匹配行里的值对吗？→ 考察字段选择和聚合；
- **EX**（78.8%）：整体对吗？→ 最终结果。

诊断链直接揭示优化方向：表命中率 97% 显著高于行召回 0.851，说明瓶颈不在选表而在复杂过滤——后续优化围绕行召回展开，而不是继续在选表上投入。**没有字段级指标，这个结论就得靠猜。**

## 记忆机制

### 什么是短期记忆和长期记忆？

大模型本身是**无状态的**，每次生成只能看到当前 Prompt。所谓"记忆"本质是把历史信息以某种方式重新提供给模型。

- **短期记忆**：当前会话的上下文，保证"这轮对话接得上"。一般用消息历史 + 检查点实现，生命周期和会话绑定；

- **长期记忆**：跨会话持久化，保证"上次说过的偏好还记得"。需要外部存储 + 检索注入。

两者解决不同问题：短期记忆保证对话连贯，长期记忆保证个性化和跨会话复用。

### 记忆有哪些类型？

借鉴认知心理学，长期记忆分三类：

- **语义记忆（Semantic Memory）**：稳定的事实和知识——"用户关注的销售额口径是含税口径""Olist 有 9 张表"。这类记忆持久不变，是系统知识的一部分；

- **情节记忆（Episodic Memory）**：事件序列——"上周三用户查过 11 月异动归因""用户刚把口径改成不含税"。这类记忆有时序性，用于保证对话连贯和回顾历史；

- **程序记忆（Procedural Memory）**：技能和习惯——"用户偏好带 SQL 和数据表格的回答""复杂查询要分步拆解"。这类记忆反映用户的行为模式，用于个性化。

三类记忆分开存储和检索，互不干扰——不分级的话，过期的事件会被当作事实引用，回答被污染。

### 记忆和 RAG 有什么区别？

| 维度 | RAG | 记忆 |
|---|---|---|
| 数据来源 | 外部文档、知识库、Schema | 用户历史对话、偏好、行为 |
| 时效性 | 相对稳定（文档更新频率低） | 动态变化（偏好会改、事件会过期） |
| 检索方式 | 按当前 Query 语义检索 | 按类型 + 时近性 + 重要性融合排序 |
| 冲突处理 | 文档矛盾以最新版本为准 | 写入前冲突检测，时近性优先 |
| 注入位置 | context prompt | context prompt（但带记忆类型标签） |

本质区别：RAG 检索的是**外部知识**，记忆检索的是**用户个人信息**。RAG 的内容相对稳定，记忆的内容动态变化且需要冲突处理。

### 记忆怎么存储和检索？

存储：每条记忆带完整元数据——`memory_type`（三级分类）、`importance`（重要性评分）、`created_at` / `last_access_at`（时近性依据），同时维护 HNSW 稠密向量索引和 BM25 稀疏向量索引。

检索：按记忆类型并行双路检索（稠密 + BM25），经 RRF 融合后，再按 **alpha × 语义相似度 + beta × 时近性（指数衰减）+ gamma × 重要性** 加权排序，只注入与当前问题相关的条目。

这套设计解决"召回的记忆太多、该信哪条"的问题：语义相近但半年前的事件，会输给语义稍弱但刚发生且重要的记忆。

### 记忆冲突怎么处理？

**写入前冲突检测**：新记忆入库前，先和已有记忆做语义相似度比对——发现语义高度相似但内容矛盾的旧条目时，不是新增一条，而是**以时近性优先更新旧条目**（最新的声明覆盖旧的，同时保留更新时间戳）。

背后的假设：用户改口是正常行为，"最近说的"比"以前说的"更能代表当前偏好。另外两个配套设计：**importance 评分**让重要的口径类记忆不容易被低价值新记忆误更新；**矛盾告警**——检测到口径级冲突时在 Trace 里留痕，复盘时能查到"什么时候、因为哪句话改了口径"。

### 记忆什么时候写入？

两条写入路径：

- **实时写入**：对话中出现明确偏好声明或关键事实时，LLM 抽取为结构化条目直接写。比如用户说"以后销售额都看含税口径"，系统立即抽成语义记忆入库；

- **后台压缩**：长对话定期沉淀为摘要记忆。比如 20 轮对话后，把关键问题、已确认事实、用户偏好压缩成情节记忆。

写入频率的权衡：写太频繁会让噪声淹没信号（临时查询条件都入库，检索时干扰项变多）；写太少会让用户偏好丢失。平衡点是只写**稳定的事实与偏好**、**有回顾价值的事件**、**反复出现的行为模式**，一次性的大查询结果不进长期记忆。

## 系统评测

### Agent 系统怎么评估？

分两层：

- **过程层**：看链路正确性——意图命中率、工具选择准确率、路由命中率、迭代收敛率。过程层指标能发现"链路对但答案错"和"链路错但蒙对"的区别；

- **结果层**：看最终输出质量——任务完成率、LLM-as-Judge 多维打分、人工抽检。

只靠结果层评不出"链路对但答案错"和"链路错但蒙对"的区别——本项目的字段级评测（表命中/行召回/字段准确）就是把结果层往下拆了一层的实践。

### 什么是 LLM-as-Judge？

用大模型当裁判评估另一个大模型的输出质量。核心思路是让强模型按预设的评分维度和标准，对被评估模型的输出打分。

优势：比人工评估快、可规模化；比规则评估灵活，能处理开放式任务。

局限：

- **裁判偏差**：裁判模型可能对自己的输出风格有偏好；
- **位置偏差**：并列两个候选时，裁判对位置敏感；
- **标准不稳**：没有明确的 rubric 时，裁判打分波动大。

工程上要做的是：**明确的评分 rubric**（每个维度 1-5 分，有具体标准）、**多轮投票**（多个裁判或多次评分取平均）、**人工校准**（定期抽检校准裁判准确率）。

### 什么是 RAG 的评估指标？

分两层：

- **检索层**：召回率（该捞的捞没捞到）、精确率（捞上来的有多少有用）、MRR（平均倒数排名，相关结果排第几）、NDCG（归一化折损累计增益，考虑位置权重的排序质量）。

- **生成层**：忠实度（答案是否忠于检索内容，有没有编造）、相关性（是否回答了问题）、完整性（关键信息有没有遗漏）。RAGAS 是常用的 RAG 评估框架。

常见的坑是只评生成层：答案错了分不清是"没检索到"还是"检索到了但模型没用好"，两层分开评才能定位优化方向。

### 什么是 Bad Case 归因？

Bad Case 归因是**对每个失败样本定位错误发生在哪个环节**，而不是只统计"错了多少个"。

本项目的做法：每个失败样本按四项指标（表命中/行召回/字段准确/EX）拆解：

- 表命中率满分但 EX 失败 → 错在过滤条件或 JOIN；
- 行召回满分但字段准确失败 → 错在聚合或字段选择；
- 表命中就失败 → 错在 Schema Linking。

归因后才能针对性优化——比如发现表命中率低，就要回到 Schema 检索环节做召回优化；发现字段准确率低，就要回到 SQL 生成环节做 Prompt 优化或补充相似 SQL 示例。不归因只看错误总数，容易陷入"哪错改哪"的局部修复，治标不治本。

### Bad Case 治理流程是什么样的？

不是发现一个 Bad Case 就改一个，而是走"收集 → 归因 → 批量聚类 → 根因修复 → 回归验证"的闭环：

1. **收集**：来自线上用户反馈、人工抽检、评测集三类渠道。每条 Bad Case 都要带上用户原始问题、生成的 SQL、执行结果、期望结果、错误类型标签；
2. **归因**：按四项指标定位错在哪个环节，并标注错误根因（Schema 漏召回、字段口径混淆、Join 路径错、过滤条件错、聚合方式错等）；
3. **批量聚类**：把同根因的 Bad Case 聚到一起，找出"同一类问题反复出现"的模式。比如发现"时间字段混淆"的 Bad Case 占了 30%，说明这类问题不是个别样本问题，而是系统性的召回或口径设计缺陷；
4. **根因修复**：针对聚类的根因做系统性优化，而不是逐个样本打补丁。比如根因是"支付时间字段口径不清晰"，就在语义层里把 `pay_time` 的业务口径、和 `create_time` 的区别写得更明确；根因是"Schema 漏召回"，就调整召回的 Embedding 模型或补充同义词；
5. **回归验证**：修复后把历史 Bad Case 重新跑一遍，确认同类问题不再出现，同时跑全量评测集，确认修复没有引入新的回归问题。

这套流程的关键是"**先聚类再修复**"——逐个样本打补丁会让系统越来越脆弱，根因修复才能让系统越改越稳。

## RAG 与向量检索

### RAG 的概念与必要性

#### 什么是 RAG？为什么需要 RAG？

RAG（Retrieval-Augmented Generation，检索增强生成）= **检索系统 + 大模型生成**。先从外部知识库检索相关内容，再把检索结果作为上下文交给大模型生成答案。

需要 RAG 的根本原因是**大模型的三点局限**：

- **知识截止**：模型的知识停留在训练数据截止日期，无法回答新出现的业务知识；

- **缺乏私域知识**：企业内部文档、业务规范、数据库 Schema 不在训练语料里，模型不知道；

- **幻觉**：模型对不知道的内容会"一本正经地胡说八道"，生成的答案无法溯源、无法验证。

RAG 把"模型必须记住所有知识"转变为"模型只需要会查、会读、会总结"——知识放在外部可维护的存储里，模型按需检索，答案有据可查。

#### RAG 与微调的区别？

- **RAG**：不改模型参数，通过外部检索注入知识。成本低、知识可实时更新、答案可溯源；适合知识频繁变化、需要引用来源的场景。

- **微调（Fine-tuning）**：把知识/风格训进模型参数。适合改变模型的行为风格、输出格式、领域术语理解；但知识更新要重新训练，且容易**灾难性遗忘**（微调时新数据覆盖旧参数，模型把预训练学到的通用能力"学忘了"——比如只在客服数据上微调后，模型连正常的通用问答都变差）。

实际工程中两者不互斥：**知识类问题用 RAG，行为类问题用微调**。本项目全部用 RAG 路线（Schema 检索、知识库检索、记忆检索、Few-shot 检索），因为 ChatBI 的知识（表结构、口径、业务文档）更新频率高，不适合固化进参数。

### RAG 的完整链路

#### RAG 的完整流程是什么？

```text
离线（索引构建）：
文档加载 → 清洗 → 切分（父子块）→ Embedding 编码 → 写入向量库（稠密+稀疏双索引）

在线（检索生成）：
用户 Query → 查询改写 → 双路召回（稠密+BM25）→ RRF 融合 → Rerank 精排
→ 父块上下文恢复 → 组装 Prompt → LLM 生成 → 引用溯源
```

本项目的特点：父子块切分（子块召回、父块补上下文）、稠密 + BM25 混合检索 + RRF 融合 + Rerank、内容哈希增量入库、每一层都有降级路径。

#### 文档切分策略有哪些？怎么选？

- **固定长度切分**：按字符数/token 数硬切。简单但会切断语义完整的段落；

- **递归切分**：按段落 → 句子 → 短语的优先级递归切，尽量在语义边界断开。是通用场景默认选择；

- **语义切分**：用 Embedding 相似度找语义转折点。效果最好但成本最高；

- **父子块切分（本项目）**：两级切分——父块保留完整段落语义，子块做细粒度精确召回，召回子块后取回父块恢复上下文。**解决"切小块召回准但上下文残缺，切大块上下文全但召回糙"的矛盾**。

切分参数（chunk_size / overlap）的权衡：块太大→向量语义稀释、召回不精确；块太小→上下文不完整、答案碎片化。overlap 防止关键信息恰好落在两个块的边界上被切断。

### 分块（Chunking）专题

#### 分块过大和过小各自存在什么问题？

分块大小直接影响检索质量和生成效果：

- **分块过大**：**语义稀释**——一个块里包含多个话题，Embedding 向量被多种语义平均化，与具体问题的相似度下降；**噪声引入**——召回时大量无关内容一起进上下文，浪费 token 还干扰模型；**检索精度下降**——粒度粗，即使块内含正确答案，模型也难从冗余信息中提取关键事实。

- **分块过小**：**信息密度低**——单个块语义不完整，模型只看一个块不足以回答；**需召回多块拼接**——拼接可能引入冲突信息，增加重排和生成压力；**语义断裂**——关键信息被切开分散在多个小块，检索只命中一部分，回答片面；**上下文开销增加**——多块拼进 Prompt 占用更多窗口。

#### 常见的 Chunking 方案有哪些？

- **Character（固定大小分块）**：按固定字符数分割，可设重叠字符保持连贯。最简单但会切断语义；

- **Recursive（递归分块）**：按不同分隔符（段落 → 换行 → 空格）递归分割直到块足够小。LangChain 默认方案，通用场景的基线选择；

- **Token（固定 Token 分块）**：按 token 数量分块（tiktoken 等分词器），与模型窗口直接对齐；

- **Document（分隔符分块）**：用文档格式特征分块，如 Markdown 标题、代码的类和函数边界；

- **Semantic（语义分块）**：计算句子间 Embedding 距离，按主题转折点分块。听起来高级，但实践中效果不稳定、成本高；

- **Agentic（大模型分块）**：用 LLM 决策分块边界。效果最好但每篇文档都要调模型，成本最高。

**实践结论：Recursive + Document 配合适当的 chunk_size 与 overlap，是性价比最高且最不容易出错的基线方案**；本项目在此之上叠加父子块二级结构，兼顾召回精度与上下文完整性。

#### 如何设计一个好的 Chunking 方案？

两阶段做法：

1. **基于规则的初切分**：利用文档格式特征（章节标题、段落换行、列表项、表格边界）作为切分点；表格、代码块视为独立 Chunk 避免中途截断；

2. **语义连贯的调整**：初切分后检查相邻块连贯性——某块过短且与前后段落语义紧密相关（如上一块以冒号结尾）则合并；跨页段落、跨页表格合并为同一 Chunk；最终在语义完整前提下控制长度（如不超过 512 字），确保每个 Chunk 都是自含意义的独立段落。

### 检索原理

#### Embedding 的原理是什么？

Embedding 模型把文本映射为高维向量（如 bge-m3 是 1024 维），语义相近的文本在向量空间中距离相近。检索时用 cosine 相似度或点积计算 query 与文档向量的距离，取最近邻。

主流是**双塔结构**：query 和文档分别独立编码。好处是文档向量可以离线预计算、建索引，在线检索只需要编码一次 query + 一次 ANN 查询，百万级语料毫秒级返回；代价是 query 和文档没有交互，精度有限——这是后面需要 Rerank 的原因。

#### 你了解哪些 Embedding 模型？如何选择？

主流模型：

- **bge 系列（BAAI）**：应用最广泛的开源模型之一，支持中英文，v1/v1.5/m3 多版本。bge-m3 支持 100+ 语言、8K tokens 输入、稠密+稀疏双输出——本项目选型；

- **GTE 系列（阿里）**：针对中文和多语言场景优化，性价比高；

- **E5 系列（Microsoft）**："query: / passage:" 指令格式训练，多语言泛化强；

- **conan-embedding（腾讯）**：C-MTEB 榜单表现突出，核心在高质量负样本构建。

选型角度（按本项目实践的优先级）：**语言支持**（中文效果）→ **输入长度限制**（超过会截断丢信息，bge-m3 支持 8K）→ **特定领域表现**（通用模型在垂直领域不如专用模型，必要时微调）→ **向量维度**（维度与现有索引 schema 绑定，换模型维度变了要重建索引）→ **存储与延迟成本**。MTEB 排行榜可参考，但公开 benchmark 在垂直业务里不一定成立，要以自己业务数据实测为准。

#### Embedding 模型的缺陷是什么？

核心缺陷是**把一段文本压缩成固定维度向量后丢失细粒度信息**：

- **长文本向量稀释**：不同主题、不同事实的信息混在一起被平均掉，查询只关心某个细节时抓不住——这是分块和向量索引文本要保持简洁的根本原因；

- **精确匹配能力弱**：对关键词、数字、实体名这类精确信息不敏感，"语义大致相似但关键信息不对"——这是必须混合 BM25 的原因；

- **单向量表达有限**：不适合多意图、多主题或需要局部对齐的任务；

- **对 Query 表述敏感**：同一意思换个说法，检索结果可能波动较大——这是查询改写存在的意义。

#### 向量检索为什么快？ANN 和 HNSW 是什么？

暴力计算 query 与所有文档的相似度是 O(N)，百万级语料无法接受。实际用 **ANN（近似最近邻）**：牺牲少量精度换取数量级的速度提升。

HNSW（分层可导航小世界图）是主流 ANN 索引：把向量组织成多层图，上层稀疏下层稠密，查询时从上层快速定位大致区域、逐层下沉精细搜索，复杂度降到 O(log N)。两个关键参数：M（每节点最大连接数，影响召回率和内存）、efConstruction（建索引时的搜索宽度，影响索引质量和构建耗时）。

#### 常见的向量索引算法有哪些？

- **IndexFlatL2（暴力检索）**：计算 query 与所有向量的 L2 距离，精度最高但开销大，只适用小规模数据或作为 ground truth 基准；

- **IVF（倒排文件）**：用 K-means 把向量聚成多个簇，查询时先找最近的簇再在簇内搜索——通过缩小范围提速，召回率受簇质量影响；

- **HNSW**：多层图结构（类似概率跳表），效率和精度平衡最好，是当前主流——本项目 Milvus 的稠密索引；

- **DiskANN**：基于磁盘的索引，轻量索引结构放内存、原始数据和图结构放磁盘，解决超大规模向量的内存瓶颈。

#### 什么是混合检索？为什么要混合？

混合检索 = **稠密向量检索（语义）+ 稀疏关键词检索（BM25）**，两路结果融合。

- **稠密检索**擅长语义泛化：用户说"卖得最好"，能召回"销售额排名"；

- **BM25** 擅长精确匹配：表名、字段名、枚举值这类"一字之差就错"的术语。

真实 Query 通常同时包含精准术语和模糊口语，单一路线都有硬伤。这也是本项目 Schema 检索在开放域达到 97.0% 表命中率的工程基础。

#### RRF 融合的原理？相比分数加权有什么优势？

稠密向量的分数（余弦相似度 0-1）和 BM25 的分数（无上界）**量纲不同**，直接加权需要归一化且对分布敏感——某一路分数整体偏高就会压制另一路。

RRF（Reciprocal Rank Fusion）只用排名，不用分数：

```text
RRF_score(d) = Σ 1/(k + rank_i(d))    # k=60 平滑常数
```

一个文档在两路检索中排名都靠前，融合排名就靠前。不依赖分数量纲、不需要归一化、任何一路检索器替换都不影响融合逻辑——工程上更稳定，是业界融合检索的标准做法之一。

#### Rerank 的原理？和 Embedding 有什么区别？

Embedding 是双塔粗排（分别编码，快但精度有限）；Rerank 是交叉编码精排（query 和候选文档拼在一起进模型，模型能看到两者的完整交互，慢但准）。

工程分工：双塔从全量语料召回 Top-N（快，覆盖优先），Rerank 对 Top-N 重排（准，质量优先）。Rerank 无法对全量语料使用（无法预计算），只能用在粗排后的几十个候选上——所以链路顺序必须是 召回 → 融合 → Rerank，不能反。

### 向量数据库

#### 向量数据库怎么选型？

主流选项对比：

| 向量库 | 特点 | 适用 |
|---|---|---|
| Milvus | 功能全（稠密+稀疏+标量过滤+分区键）、分布式 | 生产环境、多租户 |
| Milvus Lite | 本地文件、零依赖 | 原型验证 |
| pgvector | PostgreSQL 插件 | 向量规模小、已有 PG |
| Elasticsearch | 搜索引擎加向量 | 已有 ES 栈、混合检索 |
| Qdrant / Weaviate | 轻量专用向量库 | 中小规模 |

本项目的选型实践：Milvus Lite + standalone 双模式，通过连接地址形态自动切换（本地文件路径→Lite，TCP 地址→完整版），一套代码覆盖原型到生产。真实踩坑：Lite 不支持部分管理 RPC（需补丁跳过）、分词器只支持 jieba 不支持 chinese。

### RAG 的评估与优化

#### RAG 系统怎么评估好坏？

分两层评：

- **检索层**：召回率（该捞的捞没捞到）和精确率（捞上来的有多少有用）。本项目 Schema 检索的表命中率 97.0% 就是检索层指标；

- **生成层**：最终答案质量——忠实度（答案是否忠于检索内容，有没有编造）、相关性（是否回答了问题）、完整性。

常见的坑是只评生成层：答案错了分不清是"没检索到"还是"检索到了但模型没用好"，两层分开评才能定位优化方向。

#### RAG 常见的失败模式有哪些？怎么优化？

- **检索不到（漏召回）**：query 与文档表述差异大 → 加查询改写、混合检索、扩大 Top-K；

- **检索到了但排不到前面**：语义相近的干扰项多 → 加 Rerank、优化索引文本（向量索引保持简洁防语义稀释）；

- **检索到了但模型没用**：上下文太长关键信息被淹没 → 精简注入、关键内容放上下文头尾（Lost in the Middle 现象）；

- **模型编造检索外的内容**：忠实度问题 → Prompt 约束"仅基于给定资料回答"+ 引用溯源要求。

#### 了解 GraphRAG / Agentic RAG 吗？

- **GraphRAG**：用知识图谱组织文档实体和关系，检索时沿图谱游走。适合跨文档的多跳推理，代价是建图成本高。本项目 Schema 的"表间关联关系"本质就是一个小型图谱（表是节点、外键是边）；

- **Agentic RAG**：把检索从"一次性动作"变成"Agent 可多次调用的工具"，模型根据中间结果决定再检索什么。本项目的 ReAct 循环 + `recall_context` 回忆就是这个思路——检索内化为 Agent 的工具能力，而不是固定的前置步骤。

### 检索质量与 Top-K 设计

#### 稀疏检索、密集检索、混合检索各有什么问题？

- **稀疏检索（BM25 等）**：语义表达能力有限，无法建模同义词和上下文；对词面形式依赖强，表达有差异就召回不足；分词质量直接影响效果。

- **密集检索（向量）**：精确匹配能力较弱（专有名词、编号容易匹配不准）；可解释性差；效果依赖 Embedding 模型质量；计算和存储成本高；可能出现**语义漂移**——结果语义相关但不精确，偏离原始意图。

- **混合检索**：系统复杂度高（两套索引）；融合策略设计难（分数难以统一）；计算开销增加；两路结果分布差异可能影响排序稳定性——本项目用 RRF（只用排名不用分数）解决融合难题，用单存储引擎（Milvus 同时维护稠密+稀疏）解决两套系统的运维问题。

#### 如何提高检索的质量？

按链路环节拆：

- **查询优化**：Query 改写、多轮上下文融合、Query 扩展，减少歧义（本项目的 QueryRewriter 指代消解 + 省略补全）；

- **数据与索引优化**：合理分块控制粒度、语义去重与清洗减少噪声、元数据增强（页码/章节/业务标签）支持过滤检索；

- **检索策略优化**：按任务选稀疏/密集/混合，多路召回 + 融合提升覆盖；

- **排序优化**：召回后加 Rerank 精排，做更细粒度的匹配；

- **模型优化**：选高质量或领域适配的 Embedding 模型，根本改善语义表示。

#### Top-K 过大和过小分别有什么影响？

- **Top-K 过小**：召回率下降——相关但排名靠后的块被截断，关键信息遗漏；回答片面；容错能力差，排序稍有偏差就直接答错。

- **Top-K 过大**：噪声引入——弱相关内容干扰模型判断；上下文压力增大，token 成本上升；Rerank 压力增加；多个来源的矛盾信息同时召回，模型需要自行取舍，容易产生幻觉。

#### 如何根据业务场景选择合适的 Top-K？

核心策略是按容错倾向选择：**优先保证召回率时取大 K，优先保证准确率时取小 K**。

- **取大 K（召回率优先）**：遗漏代价远大于噪声代价的场景。如法律判例检索、医学文献检索，漏一条关键先例可能影响决策，K 可到 20-30——后续还有重排和生成环节做二次筛选，多召回的噪声可以被下游过滤，但漏掉的信息无法凭空恢复。

- **取小 K（准确率优先）**：噪声干扰代价大的场景。如 FAQ 应答（召回 3-5 条最匹配的即可，多了只会让模型困惑）、实时快速问答。

本项目的实践：知识库检索 Top-6、Few-shot SQL 示例 Top-3、记忆召回按类型各取 Top-K 再融合——**召回阶段放大 K 保覆盖，精排阶段收敛保精确**，具体数值是按 Bad Case 归因调出来的，不是拍的。

## 工具调用与协议

### 工具调用的概念与原理

#### 什么是工具调用（Function Calling / Tool Use）？

大模型本身只会"说"——输出文本。工具调用让模型能"做"：模型在生成时输出一个**结构化的调用意图**（调哪个工具、传什么参数），由外部系统真正执行，执行结果再回传给模型继续生成。

核心理解：**模型从不直接执行任何操作**。它只负责"决定调用什么"，执行完全由外部完成。这个边界既是能力来源（模型可以操作真实世界），也是安全设计的起点（所有执行都可以被拦截审查）。

#### Tool Calling、Function Call、MCP、Skill 是什么关系？

四者是不同层级的概念，从低到高依次是：**Function Call / MCP → Tool Calling → Skills**。

- **Tool Calling**：最上层的宽泛概念，指模型自主决定调用外部工具完成任务的整套机制，是这个领域的总称；

- **Function Call**：Tool Calling 的一种具体实现协议，由各模型厂商各自定义，模型输出函数名和参数 JSON，各厂商格式互不通用；

- **MCP**：Tool Calling 的另一种实现协议，标准化了服务发现和调用规范——解耦模型厂商和工具实现，所有模型通过同一协议调同一批工具；

- **Skills**：Tool Calling 之上的更高层封装。一个 Skill 内部可以组织多个工具的调用顺序，同时注入领域知识、业务规则和输出规范。**Tool Calling 解决"调哪个函数"，Skills 解决"怎么干好这件事"。**

#### 工程上 Tool Calling 怎么做？（四层架构）

Tool Calling 的本质是**模型决定调用意图，宿主系统决定能不能执行**。普通函数调用是程序写死的，谁调哪个函数、传什么参数都由开发者控制；Tool Calling 是模型自主输出工具名和参数，所以必须加一层校验和调度。工程上一般有四层：

- **工具注册层**：定义每个工具的名称、描述、参数 Schema，注册到可调用工具列表。模型只看到这一层的声明，看不到执行细节；

- **参数 Schema 层**：模型输出候选调用后，服务端先做白名单校验和参数格式校验。参数对不上或工具不在白名单里，直接拦截；

- **执行器层**：校验通过后才真正执行，包含超时控制、幂等控制、错误包装。执行结果统一格式化后回传给模型；

- **审计日志层**：每次调用记录工具名、输入参数、输出结果、耗时、成败状态，组成完整调用链路，方便排查和回放。

本项目的工具注册表就按这四层组织：ToolDefinition 注册 → input_schema 校验 → handler 执行（超时/降级）→ 调用日志 + 审计。

#### Function Calling 的完整工作流程是什么？

```text
1. 注册工具：把工具的名称、描述、参数 JSON Schema 告诉模型
2. 模型决策：根据用户问题决定是否调工具、调哪个、参数是什么
3. 结构化输出：模型输出 tool_call（工具名 + 参数 JSON）
4. 外部执行：系统解析 tool_call，校验参数，真正执行
5. 结果回传：执行结果作为 tool 消息追加到上下文
6. 继续生成：模型基于结果继续推理或给出最终答案
```

本项目的 ReAct 循环就是这个流程的多次迭代版本：每一轮模型决定 tool 还是 final，直到信息足够。

#### 工具的 JSON Schema 定义包含什么？

```json
{
  "name": "execute_sql_guarded",
  "description": "带三重保障的 SQL 执行：静态校验 → 自修复 → 合理性检查",
  "input_schema": {
    "type": "object",
    "properties": {
      "sql": {"type": "string", "description": "待执行的 SELECT SQL"},
      "query": {"type": "string", "description": "用户原始问题（可选）"}
    },
    "required": ["sql"]
  }
}
```

三个要点：**name** 是调用标识；**description** 是模型选择工具的主要依据（写得不好模型就不会选或乱选）；**input_schema** 约束参数结构（类型、必填项），是参数校验的依据。

### 工具设计与执行治理

#### 好的工具设计有哪些原则？

- **单一职责**：一个工具只做一件事（execute_sql 就执行 SQL，不要又执行又分析）——职责越单一，模型越容易选对；

- **描述即文档**：description 要写清"什么时候用、什么时候不用、参数含义"——模型选工具几乎只看描述；

- **参数自解释**：参数名和描述要让模型不看代码就能填对；

- **幂等优先**：查询类工具天然幂等；写操作要设计成可安全重试；

- **错误可理解**：返回的错误信息要让模型能据此自我修正（本项目 SQL 自修复就依赖结构化的错误反馈）。

#### 参数推断是怎么做的？

模型决定调工具后，参数来源有三种：用户问题直接给出（"查前 10 名"→ limit=10）、对话历史补全（指代消解后的实体）、工具默认值。本项目的 MCPToolRouter 在调用前有 LLM 重排 + 参数推断两步；参数缺失或非法时按 JSON Schema 校验，失败返回明确错误让模型补全，而不是带着残缺参数硬执行。

#### Agent 线上频繁选错工具，如何排查？

排查要按"**先看工具定义，再看路由，再看提示词，再回放执行链路**"的顺序——工具选错很多时候不是模型本身有问题，而是前面的候选构造、描述边界或上下文输入已经把它带偏了：

1. **先看 tool description 和 schema 设计**：工具描述是否清晰、边界是否重叠、参数设计能否区分场景。两个工具功能写得很像，模型本身就很容易选错；

2. **再看路由层**：是不是一次性给模型喂了太多候选工具，导致候选之间噪声竞争。候选集过大、路由过粗，即使模型能力没问题也容易误选——这就是本项目用 LLM 重排把候选收敛到 Top-K 的原因；

3. **再看 prompt 和 few-shot 示例**：提示词里有没有错误引导，few-shot 样例是否把相似场景映射到了错误工具上，最近是否改过 system prompt——很多线上误调用其实是 Prompt 层面的分布被改坏了；

4. **最后回放 trace**：看模型在选工具之前到底看到了哪些上下文——候选工具集合、历史记忆、用户输入、中间状态。判断历史记忆有没有污染当前决策、用户输入本身是否有歧义；

5. **检查执行前有没有二次校验**：没有二次校验机制，模型一旦第一次选偏，错误会直放大到执行层。

**兜底措施**：短期加负样本示例和更严格的 Schema 约束；长期如果两个工具语义持续接近，考虑合并成一个工具走内部参数路由。

#### 工具执行失败怎么处理？

分层处理：

1. **参数错误**（JSON Schema 校验失败）：直接返回错误给模型，让它修正参数重试；

2. **执行错误**（如 SQL 语法错误）：错误信息连同上下文反馈给模型自修复（本项目 SQL Guard 的执行反馈修复，最多 2 轮）；

3. **超时/不可用**：超时终止 + 降级路径（外部工具失败降级仅内部工具）；

4. **反复失败**：达到重试上限后放弃该工具，把失败事实告诉模型，让它换路径或如实告知用户——**不允许无限重试**。

#### 工具数量膨胀了怎么办？

工具一多，模型选错工具的概率显著上升（几十个工具的描述塞满上下文，互相干扰）。解法：

- **分组/命名空间**：按域分组（database:query、kb:search、memory:get），本项目外部工具用 `server:tool` 命名空间隔离；

- **检索式工具选择**：工具发现后不让模型从全量里选，而是先用 LLM/检索对候选工具打分取 Top-K（本项目的 LLMReranker 对工具描述与 Query 打 0-10 分）——本质是把"工具选择"做成"粗筛 + 精排"，和检索链路的召回 → Rerank 是同一个思想；

- **Skills 流程约束**：工具的组合使用规则沉淀为 Skill，模型按 SOP 调用而不是自由发挥。

#### 工具调用的安全怎么做？

- **权限前置**：四级角色控制工具可见性，敏感工具按角色暴露；

- **执行前校验**：SQL 只读 AST 校验在执行前拦截写操作和多语句注入；

- **超时与资源治理**：每个工具有超时上限，子进程超时 kill；

- **审计日志**：谁、什么时候、调了什么工具、参数是什么，全部留痕。

### MCP 协议

#### 什么是 MCP？和 Function Calling 什么关系？

MCP（Model Context Protocol）是 Anthropic 推出的开放协议，定义大模型与外部工具/数据源通信的统一规范——AI 世界的 USB-C 接口。Function Calling 是模型的内部能力（决定"想做什么"），MCP 是外部通信协议（解决"怎么连通去做"）：模型通过 Function Calling 决定调用，通过 MCP 把调用请求发给远端工具服务器。

#### MCP 的架构和生命周期？

三个角色：**Host**（宿主应用，运行 AI）、**Client**（协议转换层，维护与 Server 的连接）、**Server**（功能提供层，暴露工具）。

生命周期：initialize（握手交换能力）→ initialized（通知就绪）→ tools/list（发现工具）→ tools/call（调用）→ 关闭回收。传输方式：stdio（本地子进程）和 Streamable HTTP（远程服务化，Mcp-Session-Id 管理会话）。

#### MCP 执行工具调用的完整流程是什么？（给一个案例）

以"用户在 Agent 里问：帮我查一下 Olist 本月销售额"为例，完整链路：

1. 数据库侧把查询能力封装为 MCP Server（含只读账号、超时、行数限制），对外暴露 `query_olist_db` 工具；

2. Agent（Host）启动时通过 Client 连接 MCP Server，initialize 握手 + tools/list 发现工具；

3. 用户提问，Host 把问题交给模型，模型判断需要调用 `query_olist_db`；

4. 模型生成调用参数（SQL），Client 发起 `tools/call` 请求；

5. Server 执行真实查询（执行前过只读校验），返回结构化结果；

6. Host 把结果喂回模型，模型整理成自然语言答复用户。

注意这个流程里**模型从不直接发请求**——模型只提出调用意图，真正发请求的是 Host 里的 Client，MCP Server 只按协议暴露工具和返回结果。这就是"脑"（决策）和"手"（执行）的分离。

#### MCP 相比 Function Call 的优势是什么？

MCP 的优势不在单次调用更强，而在于**适合工具数量多、调用链路复杂、需要长期维护的系统**：

- **统一接入**：不同工具按同样方式接入，模型侧不需要针对每个工具单独适配，降低集成成本；

- **扩展性**：工具变多时，维护一份 Function Call 列表会越来越复杂，MCP 的规范化接入更适合大规模工具生态；

- **解耦**：模型不需要关心工具内部实现，只按统一协议使用，系统更灵活、更容易迭代；

- **多工具协作**：复杂任务往往需要多个工具连续配合，MCP 的会话和生命周期管理更适合多轮交互场景；

- **统一治理**：工具发现、调用规范、返回格式、权限审计都能在协议层统一处理。

### Skills

#### 什么是 Agent Skills？有什么作用？

Skills 是**面向 Agent 的能力封装方式**：把领域知识、执行流程、工具使用方法和输出规范组织成标准化模块，让模型在不修改底层架构的情况下稳定完成复杂任务。通常以结构化目录组织，`SKILL.md` 作为核心入口，向 Agent 说明这个技能"能做什么、怎么做、在什么场景下使用"。

三个核心特性：

- **按需加载**：Skills 不是一次性全部注入上下文，而是**渐进式披露**——只在任务匹配时才加载对应内容，减少 token 消耗和无关信息干扰；

- **即插即用**：Skills 是轻量级可复用的能力插件，可以在不同 Agent 之间共享复用，不需要改动 Agent 核心逻辑；

- **封装经验**：Skills 不只是封装工具接口，更重要的是把**专家经验、标准流程、业务规则和最佳实践**一起封装——模型学到的不只是"调用什么工具"，而是"如何系统性完成一类任务"。

#### Skills 和 Tool 的区别？

- **Tool 是原子能力**：查库、读文件、发请求这种最底层的单一操作，模型拿到后需要自己判断如何组合使用；

- **Skill 是把 Tool 和流程策略包装成的稳定能力模块**：一组 Tool 加上任务边界、输入输出约束和错误处理逻辑，包装成完整任务单元。

只暴露 Tool 会导致模型每次都从头组合，稳定性差；做成 Skill 后模型在更高层级调用能力，系统也更容易做版本管理和效果评估。复用粒度不同：Tool 复用的是单个操作，Skill 复用的是完整任务。

#### Skills 和 Prompts 有什么区别？分别什么时候用？

**Prompt 是一次性的任务指令，Skill 是持久化的能力封装**：

| 维度 | Prompt | Skill |
|---|---|---|
| 使用周期 | 一次性输入，随对话结束失效 | 长期保存、反复调用 |
| 任务复杂度 | 简单直接、边界清晰的任务 | 复杂多步骤、流程明确的任务 |
| Token 消耗 | 每次对话重复输入完整要求 | 按需加载、渐进式披露，更省 |
| 稳定性 | 表述每次不同，结果易波动 | 流程固定，重复任务输出一致 |

**用 Prompt 的场景**：一次性任务、简单指令、探索性任务、快速验证想法。
**用 Skill 的场景**：重复性工作流、需要固化专业知识（业务规则/SOP）、多步骤协调任务、跨项目复用、对 token 成本敏感的复杂高频任务。

#### Skills 的渐进式披露（Progressive Disclosure）是什么？

Skills 节省 token 的核心机制，分三层：

1. **元数据层**：Agent 启动时只加载每个 Skill 的 name 和 description——系统上下文里只有一份简短的技能目录，告诉模型"当前有哪些能力可用"；

2. **指令层**：用户请求与某个 Skill 匹配时，才读取该 Skill 的核心说明文件（SKILL.md），把操作流程、执行步骤和注意事项放入上下文；

3. **资源外部化**：大量参考资料、模板、Schema 等静态资源默认不进上下文，只有 SKILL.md 明确要求时才按需读取；脚本类资源不读源码，直接执行只接收运行结果。

本项目的 Skill 落地：`skills/` 目录 JSON 文件 + 运行时检索匹配注入 + 自进化引擎沉淀新规则为 Skill——人工编写的 SOP 是种子，自进化抽取的规则是增量。

## Agent 基础概念

### Agent 的概念

#### 什么是 Agent？

**简洁回答的 Agent 公式：**Agent = 大模型（大脑规划）+ Tool 工具调用（手脚）+ 记忆系统（记忆）+ 反馈循环（学习）

如果一个系统能做到**规划、记忆、工具调用和自我修正**，就能称为 Agent。

- **大模型：**担任 Agent 的大脑，负责感知理解、推理和生成规划；

- **Tool 工具调用：**感官和四肢，负责检索、执行 SQL、调用 API；

- **记忆系统：**负责长短期上下文记忆，保证会话连贯性和个性化；

- **反馈循环：**对以上步骤进行反思和修正，是自我优化的核心。

#### Agent 的分类

Agent 从结构上可以分为三类，核心区别在于**任务是由一个智能体完成，还是多个智能体协作完成**：

- **单智能体系统（Single Agent）**：一个 Agent 独立完成整个任务流程。结构简单、实现成本低，适合流程清晰、复杂度不高的任务；复杂场景下容易出现能力瓶颈。

- **多智能体系统（Multi-Agent）**：多个 Agent 协同完成任务，不同 Agent 承担不同角色（规划、执行、校验）。通过任务分工提升复杂问题处理能力，但系统复杂度更高，需要解决通信和协调问题。

- **混合系统（Hybrid Agent）**：一个主 Agent 控制流程，关键环节调用子 Agent 协作。主 Agent 负责决策，子 Agent 负责执行——本项目的 Supervisor + 专职节点就是这种形态，结构清晰且扩展性好，实际应用中最常见。

#### 谈谈你对 Agent 的理解

Agent 本质上是**以大模型为核心的自主执行系统**，和传统 AI 最大的区别在于不只是"回答问题"，而是能够**围绕目标完成一整套任务流程**。

大模型出现之前，机器智能主要有两条路径：基于规则的方法（依赖专家经验，扩展性差）和基于强化学习的方法（训练成本高、通用性有限）。大模型在推理、规划、工具调用上的能力突破，让它可以作为"大脑"构建 Agent，使系统具备从理解需求到执行任务的闭环能力。

从能力上看，Agent 核心是三点：**能思考**（CoT 任务拆解和多步推理）、**能记忆**（保持上下文和经验）、**能行动**（调用工具真正完成任务）。

从人机协作角度看，Agent 最大的意义是改变了人和 AI 的关系：早期人主导（SaaS+AI），然后 AI 辅助（Copilot），现在走向 AI 主导（Agent）——人只需要给目标，AI 负责规划和执行，人更多做监督和反馈。它不是简单的技术升级，而是一次交互范式的变化。

### Agent 的范式

#### Agent 有哪些范式？

Agent 常见范式主要包括 **ReAct、Plan-and-Execute 和 Reflection**：

- **ReAct 范式**：ReAct 是 Reasoning 和 Acting 的结合，核心是**推理和行动交替进行**。Agent 先基于当前上下文思考下一步做什么，再调用工具执行，根据工具返回的 Observation 继续推理，形成 `Reasoning → Acting → Observation` 的闭环循环，直到任务完成或触发终止条件。

- **Plan-and-Execute 范式**：**先规划后执行**。Agent 先根据用户目标生成完整步骤计划，再按计划逐步执行。适合目标明确、步骤相对清晰的复杂任务。

- **Reflection 范式**：Agent 的**自我评估和纠错机制**。完成子任务或整体任务后再调用模型评估执行过程和结果是否符合预期，不符合就重试、调整策略或重新执行。通常不单独作为完整流程，而是作为增强模块叠加在 ReAct 或 Plan-and-Execute 之上。

#### 不同 Agent 范式各有什么优缺点？

**ReAct 范式**：

- **优点**：推理、行动、观察交替进行，Agent 可以根据每一步 Observation 调整策略，适合搜索、问答、数据查询等动态任务；执行轨迹清晰，每一步为什么调用工具都可追踪，便于调试和解释。

- **缺点**：每轮都可能调用模型和工具，链路长、延迟和成本高；它是局部贪心策略，容易只根据当前结果做判断，在复杂长任务中可能走弯路、陷入死循环或迷失整体目标——本项目用签名去重 + 迭代上限两个机制专门防这两点。

**Plan-and-Execute 范式**：

- **优点**：先生成完整计划再按步骤执行，任务拆解清楚、路径稳定，方便人工审核。适合报告生成、数据处理流程等目标明确的场景。

- **缺点**：计划在执行前一次性生成，对中间变化适应能力不强。某一步失败或环境变化，后续步骤可能不再适用，需要重新规划，否则容易一错到底。

**Reflection 范式**：

- **优点**：能对结果自我评估和纠错，降低错误率、提升鲁棒性，适合对正确性要求高的任务。

- **缺点**：每次反思都需要额外调用模型，成本和耗时增加；反思质量依赖评估标准和模型能力，没有明确判断标准时可能出现无效反思，甚至把正确结果误判为错误。

#### 三种 Agent 范式如何选择？

按任务特征判断：

- **选 ReAct**：实时交互、动态不确定、需要边执行边观察的任务，比如查数据库、排查问题。核心是边想边做、灵活调整——本项目的复合工具查询走 ReAct；

- **选 Plan-and-Execute**：目标明确、步骤清晰的复杂任务，比如跨模块分析、报告生成——本项目的 Plan with SOTA 就是这个范式；

- **叠加 Reflection**：对结果正确性要求高的任务，在 ReAct 或 Plan-and-Execute 之上叠加质量审查——本项目的 Reflection + Advisor 就是 ReAct 之上的增强。

### Agent 的四大能力

**Planning 规划、Tools 工具调用、Memory 记忆、Reflection 反思。**先逐个说清每个能力解决什么问题：

- **Planning（规划）**：把"用户的一个大目标"拆成"一串可执行的小步骤"。没有规划能力，模型面对"分析一下 11 月销售额为什么下降"这种复杂目标只能硬答；有了规划，它知道先拆假设、再逐条取证、最后归因。

- **Tools（工具调用）**：让模型从"只会说"变成"能做事"。模型本身不能查数据库、不能读文件，工具是它的手脚——它负责决定"调什么、传什么参数"，执行由系统完成。

- **Memory（记忆）**：弥补大模型"无状态"的天生缺陷。短期记忆保证这轮对话接得上，长期记忆保证跨会话的偏好和事实还记得。

- **Reflection（反思）**：对产出做自我审查和纠错。没有反思的系统是"一条道走到黑"——第一次答错就错了；有反思的系统能识别低质量产出并重试。

对应到本项目：规划 = SchemaLinker IR + 根因假设拆解 + ReAct 循环 + Plan with SOTA；记忆 = 三级分层记忆 + Redis 会话快照；工具 = MCP 工具集（SQL 执行、知识库检索、记忆检索、上下文召回）；反思 = Reflection + Advisor 定向重试。

### Workflow 和 Agent 的区别？各自适合什么场景？

**核心区别是"流程由谁决定"：**

- **Workflow**：步骤由开发者预先编排死，模型只在某个节点内干活。类比"流水线"——工序固定，工人（模型）只负责自己那一站。优点是稳定、可预测、可审计；缺点是流程外的需求处理不了。

- **Agent**：下一步做什么由模型自己根据当前情况决定。类比"自由员工"——给他目标，他自己想办法。优点是灵活、能处理开放任务；缺点是不可预测——同一个任务两次执行路径可能不同，错了也难复盘。

**场景选择：**对准确性、可审计性要求高的场景（问数、财务、合规）适合 Workflow 为主——每一步都可预期、每个数字可复核；开放性探索任务（调研、头脑风暴）适合 Agent。

本项目主链路是 **Agentic Workflow 的混合形态**：问数流程固定为 Schema Linking → 路由 → 编译/生成 → 守卫 → 执行（Workflow 骨架保稳定），但每个节点内部保留模型的自主能力（Schema Linking 的抽取、自修复的改写都是模型自主完成的）。为什么这么选：问数场景里"同一个问题今天和明天答案必须一致"是硬要求，纯 Agent 的自由度在这个场景是缺点而不是优点。

### 多 Agent 协作有哪些常见模式？

五种常见模式，按"协作发生在什么环节"理解：

- **路由分发（Supervisor）**：一个"前台"Agent 负责接待，判断问题类型后转给对应的专职处理。适合问题类型差异大、单一 Agent 什么都做不好的场景。

- **循环迭代（ReAct）**：单个 Agent 在"思考 → 调工具 → 看结果 → 再思考"中自主推进。适合步骤数不确定、要根据中间结果定下一步的探索性任务。

- **任务拆解并行（Coordinator / Orchestrator-Worker）**：一个协调者把大任务拆成互不依赖的子任务，派给多个 Worker 同时干，最后汇总。适合子任务彼此独立、串行纯粹浪费时间的场景。

- **评审对抗（Reflection / Critic）**：一个干活的、一个挑刺的。干活的产出答案，挑刺的按质量标准审查，不合格打回重做。适合对正确性要求高、一次生成不靠谱的场景。

- **强弱模型分工**：贵的好模型只做高价值决策（规划、诊断），便宜的快模型做执行。本质是成本分级——好钢用在刀刃上。

本项目五种都有落地：Supervisor 快速路由、ReAct 复合查询、Coordinator 跨模块并行、Reflection + Advisor 质量审查、Plan with SOTA / Advisor 的强弱分工，可按场景举例。

### 多 Agent 系统怎么做稳定性兜底？

核心原则是**每个增强组件都假设自己会挂**：Advisor 失败降级普通重试、外部 MCP 失败降级内部工具、混合检索失败降级稠密检索、Rerank 失败回退 RRF。系统的底线能力不依赖任何一个增强组件，组件的价值是"在的时候更好"，而不是"不在就崩"。

### 单 Agent 和多 Agent 怎么选？什么时候用多 Agent？

**选择标准是看任务是否需要"角色分工"。**单 Agent 能搞定的不要硬上多 Agent——多 Agent 的协调成本（通信、状态同步、结果汇总）是真的，不是多几个节点这么简单。

用单 Agent 的场景：任务链路清晰、步骤少、一个模型能从头做到尾。比如简单的查表问答，一个 Agent 调一次工具就够了，不需要拆成"理解 Agent + 检索 Agent + 生成 Agent"——拆了反而增加通信开销和出错点。

用多 Agent 的场景：

- **任务里有明显不同角色**：比如"规划者"和"执行者"分工，规划需要强推理能力，执行需要工具调用能力——两种能力可以配不同模型分级成本；

- **子任务彼此独立可并行**：跨模块查询（同时查业务数据 + 知识库 + 记忆），串行是纯浪费，并行能把总耗时从"子任务之和"降为"最慢子任务的耗时"；

- **需要对抗审查提升质量**：一个产出、一个审查，适合对正确性要求高的场景；

- **能力需要解耦复用**：专职 Worker 可以跨场景复用，新增业务只加一个 Worker 不改主链路。

本项目是混合系统（Supervisor + 专职节点）：主链路固定由 Workflow 骨架保证稳定，专职节点按需分流处理复杂任务——既不是纯单 Agent 也不是全链路多 Agent，是按问题复杂度分层。

### Agent 系统的上下文管理为什么难？

因为上下文是稀缺资源且每轮都要重新组织：塞太多 token 成本和延迟爆炸、关键信息被稀释；塞太少模型"失忆"。难点在三个平衡：**完整性 vs 成本**（自动压缩 + 动态上下文）、**相关性 vs 噪声**（每轮按需检索注入而不是固定拼接）、**结构正确性 vs 激进裁剪**（切分点回溯防拆 tool 对、system 永不压缩）。

### Agent 系统怎么评测？

分两层：**过程层**看链路正确性（意图命中率、工具选择准确率、路由命中率、迭代收敛率）；**结果层**看最终输出质量（任务完成率、LLM-as-Judge 多维打分、人工抽检）。只靠结果层评不出"链路对但答案错"和"链路错但蒙对"的区别——本项目的字段级评测（表命中/行召回/字段准确）就是把结果层往下拆了一层的实践。

### Agent 系统怎么控制？

Agent 的控制机制是工程化的重点，主要从四个维度：

- **流程控制**：用 Workflow 骨架固定主流程（Schema Linking → 路由 → 生成 → 守卫 → 执行 → 汇总），不让模型自由决定步骤顺序——问数场景的稳定性优先于灵活性；

- **迭代控制**：ReAct 循环带签名去重（防重复调用烧钱）和迭代上限（默认 5 轮，到达强制总结输出，防无限循环）；

- **成本控制**：路由分流让简单问题走快速路径、强弱模型分级（诊断给 SOTA、执行给 flash）、上下文瘦身（压缩 + 截断 + Schema 收敛）；

- **安全控制**：执行前校验（SQL 只读 AST 校验）、超时 kill、权限前置、审计日志留痕。

这些控制机制的本质是：**信任模型的能力，但不信任模型的自控力**——模型可以决定"调什么工具、传什么参数"，但"能调几次""能不能执行""花多少钱"由系统说了算。

### 怎么解决 Agent 的幻觉问题？

Agent 的幻觉主要来自三类，应对方式也不同：

- **知识型幻觉**（模型不知道但编造）：用 RAG 注入真实知识，Prompt 约束"仅基于给定资料回答"+ 引用溯源要求。本项目 Schema 检索、Few-shot 示例、记忆召回都是在做这件事；

- **推理型幻觉**（模型推理跳跃或编造因果）：根因分析要求"每个结论背后都有可复核的取证 SQL 和数据"，不允许模型凭空说"因为 X 所以 Y"——必须拿出数据证据；

- **执行型幻觉**（模型编造工具调用结果）：工具结果以 tool_result 消息形式回传，模型看到的是真实执行结果而非自己编造的内容；SQL Guard 的结果合理性检查（空结果、比率越界告警）进一步兜底。

核心思路是**让模型基于证据说话，而不是基于概率说话**——这是可信 Agent 和"嘴硬 Agent"的关键区别。

## 自进化

### 系统怎么实现自我进化？

靠的是"**评测驱动 → Bad Case 治理 → 知识沉淀 → 回归验证**"的闭环，而不是靠人工逐条调 Prompt：

- **评测驱动**：每次发版前跑全量评测集（Spider + 自建业务集），按四项指标定位短板环节；
- **Bad Case 治理**：对失败样本归因、聚类、根因修复，而不是逐个打补丁；
- **知识沉淀**：修复经验沉淀为语义层规则、Few-shot 示例、Schema 描述补充，写进知识库复用；
- **回归验证**：修复后跑回归，确认同类问题不再出现，且没引入新的回归。

闭环的关键是"**知识可复用**"——每次修复都让系统的知识库更丰富，下次遇到同类问题能直接命中已有规则或示例，而不是靠模型重新试错。这让系统的准确率随时间单调上升，而不是在某个水平上下波动。

### Few-shot 示例库怎么维护？

Few-shot 示例不是人工手写一批就固定，而是**从线上高质量问答中自动挖掘 + 人工审核入库**：

- **挖掘**：对线上成功问答做评分（用户满意度、结果合理性、SQL 复杂度），高分样本作为候选；
- **聚类**：按 SQL 模式聚类（单表过滤、多表 JOIN、窗口函数、嵌套子查询等），每个模式只留 2-3 个代表性样本，避免重复；
- **审核**：人工审核候选样本的 SQL 正确性、业务口径准确性，确认无误后入库；
- **检索注入**：新问题来时，按 SQL 模式和业务域召回最相似的 1-3 个示例注入 Prompt，而不是全量塞进去。

这套机制让示例库随业务演进自动更新，不需要人工定期重写。而且聚类后去重，保证每个 SQL 模式都有代表性样本，不会让某类简单查询的示例占满 Prompt。

### 语义层怎么持续更新？

语义层不是一次建好就不变，而是**随 Bad Case 治理持续补充**：

- **口径补充**：每发现一个"字段口径混淆"类 Bad Case，就把该字段的业务说明写得更明确。比如 `amount` 被误用为实付金额，就在描述里加"下单金额，非实付，实付看 `pay_amount`"；
- **同义词补充**：每发现一个"Schema 漏召回"类 Bad Case，就分析是哪个业务术语没命中，在字段标签里补充同义词。比如"营收"没命中 `revenue`，就给 `revenue` 加上"营收、收入"等同义词；
- **JOIN 路径补充**：每发现一个"JOIN 路径错"类 Bad Case，就在表关系图里补充正确的 JOIN 路径说明，避免模型下次走错；
- **枚举值补充**：每发现一个"过滤条件错"类 Bad Case，就检查是不是枚举值没维护，比如"已支付"对应 `status=2` 没写清楚。

每次补充都走"**Bad Case → 归因 → 语义层补充 → 回归验证**"的流程，让语义层随业务演进越来越完整。这也解释了为什么语义层是 Text2SQL 系统的核心资产——它沉淀了所有历史错误的经验。

### 怎么避免"过拟合"评测集？

评测集准确率上去了，但线上效果没改善——这是典型的过拟合评测集。避免方法：

- **评测集和线上分布对齐**：定期从线上问答里抽样补充进评测集，保证评测集的 Query 分布、SQL 复杂度、业务域覆盖和线上一致；
- **留出测试集**：评测集分"训练集"（可以用来调 Prompt、补示例）和"留出测试集"（只评不改），用留出测试集监控真实泛化效果；
- **线上指标监控**：除了离线评测，还要监控线上指标（用户满意度、二次提问率、人工接管率），线上指标才是最终判断标准。

过拟合的本质是"在评测集上做文章，而不是在系统上做文章"——只要评测集和线上分布对齐，且留出独立的测试集，就能及时发现过拟合。

### 怎么衡量系统进化效果？

不只看准确率，而是看"**单位 Bad Case 治理成本**"和"**同类问题复发率**"：

- **同类问题复发率**：某个根因修复后，同类 Bad Case 还出现多少。复发率低说明根因修复有效，复发率高说明修复没到位；
- **单位治理成本**：治理一个 Bad Case 需要多少人力（归因、修复、验证）。随系统进化，治理成本应该下降，因为语义层和示例库越来越丰富，很多问题能直接命中已有规则；
- **准确率随版本变化曲线**：不只看最终准确率，看每个版本准确率的提升幅度。健康系统的准确率随版本单调上升，且提升幅度递减（边际收益递减是正常的，说明快到上限了）。

这三个指标比单纯看准确率更能反映"系统在进化"还是"系统在原地打转"。

# 大模型与系统设计基础

> 本章节整理面试中常被追问的大模型基础八股，覆盖幻觉、推理、微调、上下文等核心概念，是 Agent / RAG / Text2SQL 各类系统选型与调优的底层支撑。

## 大模型基础概念

### 什么是大模型，和传统小模型有什么本质区别？

大模型（LLM，Large Language Model）是基于 Transformer 架构、在海量语料上通过自监督学习训练得到的语言模型。与传统小模型的本质区别有三点：

- **涌现能力（Emergent Ability）**：参数规模越过某个阈值后，模型会出现小模型不具备的能力，如 In-Context Learning、Chain-of-Thought 推理、指令遵循。这种能力不是"量变到质变"，而是架构 + 规模 + 数据共同作用的结果；
- **统一范式**：传统小模型是"一个任务一个模型"（分类一个、NER 一个、翻译一个），大模型是"一个模型解所有任务"，通过 Prompt + Few-shot 就能适配下游任务，降低了工程边际成本；
- **概率本质未变**：大模型本质仍是"给定上文预测下一个 token 的概率分布"，和 GPT-2 在数学形式上没区别，只是参数量和训练数据量的指数级提升让它看起来像"懂了语义"。

面试时要强调：**大模型不是魔法，它依然是概率模型，所以会幻觉、会过拟合 Prompt、会对输入顺序敏感**。理解这点才能解释为什么要做 RAG、要做 Reflection、要做 Schema 约束。

### GPT 和 BERT 的区别是什么？为什么现在大模型都用 Decoder-only？

这是区分候选人是否懂架构的经典问题。核心区别在 **架构方向**：

- **BERT 是 Encoder-only**：双向注意力，能看到整句话的上下文，适合理解类任务（分类、NER、句子相似度）。训练方式是 MLM（Masked Language Model），预测被遮盖的词；
- **GPT 是 Decoder-only**：单向（自回归）注意力，只能看上文预测下文，适合生成类任务。训练方式是 CLM（Causal Language Model），逐 token 预测；
- **T5 是 Encoder-Decoder**：两头都要，Encoder 编码输入，Decoder 自回归生成输出，适合翻译、摘要这类 Seq2Seq 任务。

为什么现在主流大模型（GPT-4、Llama、Qwen、DeepSeek）都用 Decoder-only：

1. **训练效率高**：Decoder-only 的下一个 token 预测任务可以并行计算（一次前向得到所有位置的 loss），训练吞吐量大；
2. **Scaling Law 友好**：研究表明在同等参数量下，Decoder-only 在长文本生成和 In-Context Learning 上表现更好，且能力随规模线性增长更稳定；
3. **推理简单**：自回归生成只需维护 KV Cache，流式输出天然支持，适合对话场景；
4. **统一为生成**：把"理解"也转化为"生成"——分类任务变成"输出 yes/no"，NER 变成"输出实体列表"，统一范式降低了工程复杂度。

### 大模型的上下文窗口（Context Window）是什么？为什么越长越好但也越难？

上下文窗口指模型一次前向能处理的最大 token 数。早期 GPT-2 是 1024，GPT-3 是 2K，GPT-4 能到 128K，Claude 能到 200K，Gemini 能到 1M。窗口越长的好处：

- **长文档处理**：RAG 时可以塞更多 chunk，减少信息遗漏；能直接读整篇论文、整个代码库；
- **多轮对话**：保留更完整的对话历史，不需要频繁做上下文压缩；
- **Few-shot**：可以放更多示例，提升 In-Context Learning 效果。

但长窗口也带来三类问题：

- **计算开销二次增长**：Transformer 的注意力计算是 O(n²)，窗口翻 4 倍计算量翻 16 倍，对显存和推理延迟压力极大；
- **Lost in the Middle**：研究表明模型对窗口中间的内容记忆最差，首尾最强。RAG 把关键信息放中间容易"被忽略"，这也是为什么需要 Rerank 把最相关的放前面；
- **信息稀释**：塞太多不相关内容会稀释关键信息的注意力权重，导致模型"抓不住重点"，反而效果变差。

所以**长窗口不等于无限塞内容**，RAG 的 Rerank、压缩、动态召回依然必要。这也是为什么 AskData 项目要控制给到 Coder 大模型的 Schema 图大小——不是窗口放不下，而是放太多会稀释注意力。

### 什么是大模型的幻觉（Hallucination）？为什么会幻觉？

幻觉指大模型**生成看似合理但事实上错误或编造的内容**。比如问"林黛玉倒拔垂杨柳的典故"，模型可能一本正经地编出一段来历。幻觉的根因有三个：

- **概率采样的本质**：大模型是"给定上文预测下一个 token 的概率分布"，再按概率采样。当训练数据里没见过这个知识，模型就按"最像的下文"生成，看起来通顺但事实错误；
- **训练数据本身有错**：互联网语料里有大量错误信息、小说杜撰、过时知识，模型把它们都学进去了；
- **知识截止**：模型训练有截止日期，之后的新知识模型完全不知道，但又会硬编一个答案。

缓解幻觉的常见手段：

- **RAG**：给模型外挂知识库，让它"基于参考资料回答"，从源头约束事实正确性；
- **置信度引导**：让模型输出置信度，低置信度的答案触发澄清或拒答；
- **Reflection / Self-Check**：让模型自我检查生成结果，发现矛盾就重写；
- **Few-shot 示例**：在 Prompt 里给出"不知道就说不知道"的示例，引导模型学会拒答；
- **微调**：用"拒答"样本微调，让模型在知识边界外主动说不知道。

**面试要点**：AskData 项目里幻觉的危害是"生成语法对但语义错的 SQL"，比如把"客户余额"误生成"账户余额"。缓解手段就是 Schema 检索约束 + SQL Guard 校验 + Reflection 自修复。

### 大模型的推理能力从哪来？CoT 为什么有效？

推理能力指模型能做**多步逻辑推理**（数学题、规划、因果推断）的能力。这能力的来源有两种解释：

- **观点一：模型内部就有隐式推理**：训练时见过大量"先解释再给答案"的语料（如 Stack Overflow、教科书），模型内部形成了"推理回路"，只是不显式表达。CoT 只是把这个隐式过程"显式化"，让模型一步步输出中间步骤；
- **观点二：CoT 增加了计算量**：Transformer 每一层都是固定计算，多输出几个 token 等于多算几层，给模型更多"思考步数"。这和人类的"在草稿纸上算"类似。

CoT 有效的核心机制：

- **分解复杂问题**：把"一步推理"拆成"多步简单推理"，每步出错概率降低，整体准确率上升；
- **激活相关知识**：输出中间步骤时，会激活模型参数里相关的知识通路，提升最终答案的正确率；
- **降低采样风险**：直接采样最终答案，一个 token 错就全错；CoT 每步只预测一个简单 token，错误率被分散。

AskData 项目里 CoT 四元组就是这个原理的应用：**不直接生成 SQL，而是先规划"在哪个库、查哪个表、做什么操作、输出什么"四步**，每步都是简单决策，整体准确率比直接生成 SQL 高。

### 什么是 In-Context Learning？和微调有什么区别？

In-Context Learning（ICL，上下文学习）指模型**不改参数，只在 Prompt 里给几个示例，就能学会当前任务**。GPT-3 论文首次展示了这个能力——给模型 2-3 个翻译示例，它就能翻译新句子。

ICL 和微调的核心区别：

- **改不改参数**：微调会更新模型权重，ICL 不改任何参数，只是把示例塞进 Prompt；
- **持久性**：微调的能力是永久的（下次还能用），ICL 的能力是临时的（换一个会话示例就没了）；
- **成本**：微调需要数据集 + 算力 + 训练时间，ICL 只需要几个示例文本，零成本；
- **能力上限**：微调能学到深层行为模式（如"永远拒答"），ICL 只能学到浅层模式（如"照着这个格式输出"）。

ICL 有效的原理：示例在 Prompt 里形成了"局部任务分布"，模型按这个分布生成——本质是"条件概率采样"，模型把示例当作上文，下一个 token 的概率分布就偏向示例的风格。这也是为什么 Few-shot 在 RAG 和 Text2SQL 里广泛使用——零成本就能显著提升输出稳定性和格式一致性。

### 什么是大模型的指令微调（Instruction Tuning）？为什么需要？

指令微调指用"（指令，输出）"格式的数据集对预训练模型做 SFT，让模型学会**按人类指令的格式和意图输出**。

预训练模型只会"续写上文"——给它"今天天气很好，我打算"，它续写"出门散步"。但用户要的是"我问今天天气，你直接回答天气情况"，不是续写。指令微调就是让模型学会"看到指令，输出符合指令的答案"。

指令微调的核心作用：

- **行为对齐**：从"续写机器"变成"对话助手"——学会看到问句就给答案，而不是续写问句；
- **格式对齐**：学会输出 JSON、Markdown、代码块等结构化格式，便于下游解析；
- **拒答能力**：学会在不确定时说"我不知道"，而不是硬编；
- **安全对齐**：学会拒绝有害请求。

业界主流大模型（GPT-4、Llama-2-Chat、Qwen-Chat）都经历了"预训练 → 指令微调 → RLHF"三步。其中 **RLHF（Reinforcement Learning from Human Feedback，基于人类反馈的强化学习）** 的做法：先让标注员对模型的多个回答打分排序，训出一个"奖励模型"模拟人类偏好，再用强化学习让模型朝着奖励模型打高分的方向优化——解决的是"有用、诚实、无害"这类难以写成标注数据的对齐目标。**没有指令微调的模型是"半成品"，只能续写不能对话。**

### 大模型的温度（Temperature）和 Top-p 是什么？

这两个参数控制生成的随机性：

- **温度（Temperature）**：控制 softmax 输出的概率分布形状。温度 = 1 是原始分布；温度 < 1 让高概率 token 概率更高、低概率 token 概率更低（输出更确定、更保守）；温度 > 1 让分布更平均（输出更多样、更随机）。温度 = 0 退化为贪心解码（greedy）；
- **Top-p（核采样 Nucleus Sampling）**：只从累计概率前 p% 的 token 里采样。比如 Top-p = 0.9，就是把所有 token 按概率排序，累计概率到 0.9 之前的 token 作为候选池，其他抛弃。

调参经验：

- **事实性任务**（问答、SQL 生成）：温度调低（0-0.3），Top-p 调低（0.9），保证输出稳定、准确；
- **创意性任务**（写作、文案）：温度调高（0.7-1.0），Top-p 调高（0.95），输出更多样；
- **结构化输出**（JSON、代码）：温度 = 0，保证格式稳定，避免输出合法 JSON 概率太低。

AskData 项目里 SQL 生成用温度 = 0，就是为了让 SQL 输出尽可能确定——同一道题跑 100 次结果应该一致，方便评测和 Bad Case 复现。

## RAG 文档解析与分块

### 文档解析的作用是什么？解析不好会造成什么影响？

文档解析是将原始文件（PDF、Word、HTML）转化为可检索文本的第一步，直接决定后续检索与生成的质量。主要作用：

- **提取关键信息**：准确获取文档内的纯文本、结构化数据及上下文关联；
- **保留文档结构**：完整还原章节层级、表格和列表，帮助检索模块精准定位目标内容；
- **保障数据质量**：过滤识别误差和乱码噪音，为高精度召回提供干净的数据底座。

解析不佳会引发连锁反应：

- **召回不准**：布局错乱导致关键信息被切碎或丢失，向量表示偏离真实语义，相似度计算失真；
- **上下文断裂**：段落、表格、公式被打散后失去原有层级关系，模型生成时上下文不足；
- **噪声引入**：页眉页脚、水印、乱码进入检索库，被当作正常内容召回，干扰模型判断；
- **溯源失败**：无法定位到原文档的具体位置，用户无法核查事实，RAG 的可解释性失效。

**认知要点**：文档解析是 RAG 的"地基"——地基不稳，上层的 Embedding 模型再强、检索算法再花哨都救不回来。

### 不同格式的文档怎么解析？

多源异构是文档解析的难点，思路是按格式路由到专用解析模块。通用流程五步：

1. **格式识别与分发**：先识别文件类型，把 PDF、DOCX、图片、HTML 路由到对应解析模块；
2. **底层文本抽取**：电子版文档调解析库提取文本和排版信息；扫描件和图片走 OCR 识别文字，并还原段落、表格、公式结构；
3. **布局与结构化处理**：用布局分析或 NLP 还原文档层级，完成对标题、表格、列表的拆分和属性标注；
4. **数据清洗与切分**：剔除页眉页脚、水印等干扰，按自然段落或逻辑单元切分纯净文本；
5. **元数据标签附加**：为每个文本块绑定文档名、章节标题、页码等属性，为后续检索和溯源提供坐标。

不同格式的处理要点：

- **PDF**：最复杂，分文本型 PDF（直接提取）和扫描型 PDF（需 OCR）。表格识别是难点，要用专门的表格解析模型；
- **Word/DOCX**：相对好处理，有结构化标签（段落、标题、表格），用 python-docx 等库直接读；
- **HTML**：有 DOM 树，用 BeautifulSoup 解析，但要清洗掉导航栏、广告等噪声；
- **图片**：纯 OCR 场景，还要处理版面分析（区分正文、标题、表格、图注）。

### 为什么要分块（Chunking）？

分块要解决两个核心问题：

- **避免超上下文窗口**：长文档一次性塞给模型会超过上下文窗口限制，必须拆成块；
- **提高检索精准度**：把文档拆为语义单元，检索时只召回相关单元，而不是整篇文档——粒度越细，召回越精准。

切分策略的关键影响：

- **信息完整性**：粗暴或不合理的切分会破坏文档原有语义逻辑，造成关键信息遗漏或碎片化；
- **召回颗粒度**：文本块长度直接决定系统召回信息的数据量与精细程度——块太大召回粗糙，块太小召回稀疏；
- **进阶方案**：面对复杂场景，引入多级切分策略，兼顾宏观与微观的检索需求。

### RAG 分块越大和越小各有什么问题？

分块大小直接影响检索质量和生成效果。

**分块过大**：

- **语义稀释**：一个块里包含多个话题或过多信息，Embedding 向量被多种语义平均化，与具体问题的相似度下降，检索难以精准命中；
- **噪声引入**：召回时将大量无关内容一起带入上下文，既浪费 token 也干扰模型判断；
- **检索精度下降**：粒度太粗，即使块内包含正确答案，模型也难以从冗余信息中提取关键事实，容易遗漏或幻觉。

**分块过小**：

- **信息密度低**：单个块包含的语义信息太少，无法形成完整上下文，模型只看一个块不足以回答问题；
- **需召回多个块拼接**：为凑够完整信息要召回多个小块，拼接过程可能引入冲突或不相关片段，增加重排和生成压力；
- **语义断裂**：关键信息被切开分散在多个小块中，单个块语义不完整，检索可能只命中其中一部分，导致回答片面或错误；
- **上下文开销增加**：多个小块拼进 Prompt 占用更多上下文窗口，且块间缺乏逻辑关联，模型需要额外推理才能拼出完整答案。

### 常见的 Chunking 方案有哪些？

- **Character（固定大小分块）**：按固定字符数分割，可设置重叠字符保持上下文连贯；
- **Recursive（递归分块）**：LangChain 默认分割器，按不同分隔符递归分割（默认 `["\n\n", "\n", " ", ""]`），逐个遍历直到块足够小。可设置重叠；
- **Token（固定 Token 大小分块）**：和 Character 一样，但按 Token 数分割（Token 是模型处理文本的基本单位，中文约 1 字 ≈ 1 token，英文约 1 词 ≈ 0.75 token），常用分词器有 BPE（Byte Pair Encoding，字节对编码——反复合并语料中最高频的相邻字符对来构建词表的分词算法）、tiktoken（OpenAI 的 BPE 实现）；
- **Document（分隔符分块）**：用特定分隔符或规则分割，如 Markdown 标题符号、Python 代码的类和函数；
- **Semantic（语义分块）**：通过计算句子间 Embedding 距离，把相似主题或内容的句子分为一块；
- **Agentic（智能分块）**：最高级方案，通过 LLM 做决策，将文本分块为独立命题。

**实践建议**：一般只有图简单才会用 Character 和 Token，**常用基本还是 Recursive 和 Document，配合适当 ChunkSize 与 Overlap，往往是性价比最高且最不容易出错的基线方案**。Semantic 看起来高级但效果不稳定，Agentic 要调 LLM API 成本高。

### 怎么设计一个好的 Chunking 方案？

一般采用两阶段：先按规则切分，再做细化调整。

- **基于规则的切分**：利用文档格式特征（章节标题、段落换行、列表项、表格边界）作为切分点。检测到新章节或列表起始即结束当前 Chunk 开启新 Chunk。表格、代码块、图片整段视为独立 Chunk 避免截断；
- **语义连贯的调整**：规则初切后检查相邻 Chunk 的连贯性。某 Chunk 过短且与前后语义紧密相关（如上一 Chunk 以冒号结尾），可合并。跨页段落若下页非新章节，应与前页末尾合并；跨页表格需合成为一个整体 Chunk；
- **长度和平衡**：在保证语义完整前提下控制 Chunk 长度，适合向量检索和后续处理（如不超过 512 字或特定 Token 数）。过长按语义次级节点再拆，过短与相邻段落合并。最终每个 Chunk 都是自含意义且内容明确的独立段落。

## 向量化与存储

### 什么是向量化（Embedding）？有什么作用？

**向量化（Embedding）是将文本、图片等非结构化数据转化为高维空间中数值向量的过程。**核心作用是提取原始数据中的语义信息，使语义相近的内容在向量空间中距离更近，语义差异大的内容距离更远。

通过向量化，计算机就能用数学方法（如余弦相似度）量化计算两段内容的相关程度，从而实现语义搜索、文本分类、聚类分析和推荐系统等应用。在 RAG 系统中，向量化是将文档块存入向量库的关键一步，直接决定检索召回的质量。

### 你了解哪些 Embedding 模型？

- **bge 系列（BAAI）**：当前应用最广泛的 Embedding 模型之一，支持中英文，多版本（v1、v1.5、m3）。通过预训练、弱监督对比学习以及多任务指令微调逐步提升能力，在通用检索任务中表现稳定；
- **conan-embedding（腾讯）**：在 C-MTEB 榜单表现突出，核心在于高质量负样本构建和优化策略设计，包括动态硬负样本挖掘与多任务损失平衡；
- **E5 系列（Microsoft）**：采用 "query: / passage:" 指令格式训练，强调统一检索与匹配任务，在多语言和跨任务场景具有较强泛化能力；
- **GTE 系列（阿里）**：针对中文和多语言场景优化，在检索与相似度任务表现较好，性价比高；
- **Qwen-Embedding（阿里）**：支持多语言和长文本（最大 32K token），适合需要处理长文档的场景。

### 怎么选择合适的 Embedding 模型？

从五个角度考虑：

1. **语言支持和性能**：确保 Embedding 模型支持所需语言。多语言模型如 bge-m3 支持 100+ 语言，适合多语言场景。部分模型在中文表现好但低资源语言表现差，需评估所有目标语言的准确性；
2. **处理长文本的能力**：关注模型对输入 tokens 长度的限制，超过会截断丢信息。BERT 及变体通常最多 512 tokens，需要更细粒度分块；bge-m3、Jina 等支持 8K tokens，适合长文本；
3. **特定领域表现**：通用模型在医学、法律、金融等垂直领域效果不如专用模型，可能需要专门训练的模型捕捉领域术语；
4. **存储和内存需求**：高维向量占用更多存储空间，大模型占用更多内存，不适用于资源受限环境；
5. **模型响应时间**：实时应用中处理速度很关键，GPU 上运行才能达到最佳性能。

可以参考 Hugging Face 上的 **MTEB** 排行榜，覆盖 8 类任务、58 个数据集、112 种语言。但只能作参考——公开 benchmark 在垂直领域不一定成立，仍需结合业务特点综合比较。通用模型在业务数据上表现不满足需求时，可通过微调让模型学习特定领域词汇和概念。

### 常见的向量索引算法有哪些？

- **IndexFlatL2（暴力检索）**：直接对所有向量做精确搜索，计算每个查询向量与所有向量的 L2 距离。精度最高但计算开销最大，适合小数据集或作为基线；
- **IVF（倒排文件索引）**：用 K-means 等聚类技术将整个数据集划分为多个簇，每个向量分配到一个簇。查询时先识别最近簇，再在簇内搜索，通过缩小搜索范围提升效率；
- **HNSW（分层导航小世界图）**：构建多层图结构，类似概率跳表。每一层的节点连接到当前层和下层节点。查询时从最顶层预定义节点开始，逐步向下移动直到找到距离最小的节点。在效率和精度之间取得良好平衡，是当前最主流的向量索引算法；
- **DiskANN（磁盘向量索引）**：基于磁盘的高性能向量近邻搜索算法，解决大规模向量数据检索的内存消耗问题。轻量级索引结构置于内存，海量原始数据和图结构存放在磁盘，在保持高召回率和低时延的同时显著降低内存占用。

**HNSW 为什么快**：核心思想是"跳表式分层导航"。最上层是稀疏图（节点少，跨度大），底层是密集图（节点多，跨度小）。查询时从顶层开始大步前进快速接近目标，逐层下降在小范围精细搜索，类似"先走高速再下国道"。查询复杂度从 O(n) 降到 O(log n)，但内存占用大（要存多层图的边）。

**IVF 和 HNSW 怎么选**：IVF 适合大规模数据、对召回率要求不极端的场景，内存友好；HNSW 适合对召回率和延迟要求都高的场景，但内存占用大。生产环境百万级以下数据推荐 HNSW，千万级以上数据考虑 IVF + 量化压缩或 DiskANN。

### 如何选择合适的向量数据库？

常见向量数据库：

- **Milvus**：适合大规模分布式向量检索场景，具备高扩展性，支持 HNSW、IVF、DiskANN 等多种索引；
- **Elasticsearch（ES）**：在支持向量检索的同时兼顾全文检索能力，适合混合检索场景（向量 + BM25）；
- **Faiss**：Meta 开源的向量检索库，偏向高性能本地向量相似度计算，适用于离线或单机场景，不是完整数据库；
- **Chroma**：轻量易用，适合快速构建原型和中小规模应用；
- **Qdrant**：Rust 写的，性能好，支持丰富的过滤条件，适合对性能和过滤有要求的场景。

选择时主要考虑：

- **数据规模和速度需求**：大规模数据和高并发查询场景选 Milvus；快速原型选 Chroma；
- **持久性和可靠性**：是否需要高可用、备份、故障转移；
- **易用性和社区支持**：学习曲线、文档完整性、社区活跃度；
- **成本**：许可、硬件、运营和维护的总成本；
- **特性**：是否需要多模态搜索、元数据过滤等；
- **安全性**：是否符合安全和合规要求。

### RAG 检索为什么需要多路召回？

单一向量检索存在明显短板：向量相似不等于语义相关，且对专有名词、型号、代码等精确匹配场景表现差。多路召回通过组合不同检索算法弥补各自缺陷：

- **向量检索（Embedding）**：擅长语义相似（"怎么扩容" ↔ "水平扩展方案"），但弱于精确字面匹配；
- **关键词检索（BM25）**：基于 TF-IDF 思想，擅长精确词、缩写、型号匹配，但对同义/近义无能为力；
- **混合检索（Hybrid）**：同时执行两路，用 RRF（Reciprocal Rank Fusion，倒数排名融合）或线性加权合并排序，兼顾语义和字面匹配。

**RRF 融合公式**：`score = Σ 1/(k + rank_i)`，其中 k 通常取 60。RRF 的优势是无需归一化分数，对两路检索的分数尺度不敏感，工程实现简单稳定。

**为什么不用加权融合**：向量相似度是 0-1 的余弦值，BM25 是无上界的 TF-IDF 分数，两者尺度不一致，加权融合前需做归一化（min-max 或 softmax），调参成本高且容易抖动。RRF 只用排名信息避开尺度问题，鲁棒性更好。

### Rerank 重排器的作用是什么？和召回有什么区别？

多路召回会返回 Top-K（如 50-100）候选文档，但排序质量参差，直接塞给 LLM 会导致上下文冗余、噪声多。Rerank 对 Top-K 做精排，最终保留 Top-N（如 5-10）喂给生成。

**召回 vs 重排的区别**：

| 维度 | 召回（Retriever） | 重排（Reranker） |
|------|------------------|-----------------|
| 模型 | 双塔/单塔双塔 Bi-Encoder | 交叉编码器 Cross-Encoder |
| 输入 | Query 和 Doc 分别编码 | Query 和 Doc 拼接共同编码 |
| 速度 | 快，可离线索引 | 慢，每对都要前向一次 |
| 数量 | 处理全库百万级 | 只处理召回的几十条 |
| 精度 | 召回率高，精度一般 | 精度高 |

**Cross-Encoder 为什么准**：Bi-Encoder 是 Query 和 Doc 各自过一个 BERT，最后算余弦相似度，两者在编码阶段没有交互，只能靠最后点积做浅层匹配。Cross-Encoder 把 `[CLS] Query [SEP] Doc [SEP]` 拼一起过 BERT，注意力层让 Query 的每个 token 都能 attend 到 Doc 的 token，做深层交互，精度远高于双塔。但每对 Query-Doc 都要前向一次，无法离线预计算，只能用于少量候选的精排。

**常见 Rerank 模型**：bge-reranker、Cohere Rerank、Jina Reranker、bge-reranker-v2-m3。业务上可先用通用模型做基线，再基于业务 bad case 微调。

### 怎么提升 RAG 的召回率？

从四个方向优化：

1. **查询改写（Query Rewriting）**：
   - **Query Decomposition**：把复杂问题拆成子问题，分别检索再合并。如"对比 A 和 B 的性能"拆成"A 性能如何""B 性能如何"；
   - **HyDE（Hypothetical Document Embeddings）**：让 LLM 先生成一个假设性答案文档，用这个伪文档去做向量检索。因为"答案"和"答案"的语义距离往往比"问题"和"答案"更近，能提升召回；
   - **Step-back Prompting**：先让 LLM 抽象出更宽泛的背景问题检索，再回答具体问题。

2. **多路召回 + Rerank**：上面已讲，核心是互补召回。

3. **元数据过滤（Metadata Filtering）**：给 chunk 打上时间、来源、作者、章节等元数据标签，检索时先按元数据预过滤（如"只查 2024 年后的文档"），再在子集上做向量检索，减少噪声。

4. **chunk 级别调优**：
   - **动态分块**：按语义边界（段落、标题）分而非固定长度；
   - **父子分块（Parent-Child）**：用小 chunk 做检索（精准匹配），命中后返回其所在的大 chunk（上下文更完整），兼顾召回和上下文完整性；
   - **滑动窗口重叠**：相邻 chunk 保留 10-20% 重叠，避免句子被硬切断。

### RAG 的生成阶段有哪些优化技巧？

检索拿回上下文后，生成阶段也有讲究：

1. **上下文压缩（Context Compression）**：长文档检索回来先做摘要或抽取关键句，再喂给 LLM，避免 token 超限和 lost-in-the-middle；
2. **上下文重排（Context Reorder）**：把最相关的 chunk 放在 prompt 开头和结尾（模型对首尾位置敏感），中等相关的放中间；
3. **引用溯源（Citation）**：要求 LLM 在答案中标注引用来源 `[doc_id]`，便于用户验证和减少幻觉；
4. **答案置信度估计**：让 LLM 自评，或用检索分数+生成 logprobs 综合判断，低置信度走兜底话术"暂未找到相关资料"；
5. **流式输出**：LLM 流式返回，改善首字时延体验。

### 什么是 GraphRAG？和传统 RAG 有什么区别？

GraphRAG 是微软提出的基于知识图谱的 RAG 范式，核心是用图结构替代（或补充）纯向量检索。

**传统 RAG 的痛点**：
- 只能回答"文档里写了什么"，无法回答跨文档的全局性问题（如"整个数据集的主要主题是什么"）；
- chunk 之间孤立，缺乏关联推理。

**GraphRAG 流程**：
1. **实体抽取**：用 LLM 从文档抽取实体（人、地、机构）和关系，构建知识图谱；
2. **社区检测**：用图算法（如 Leiden）把图划分为社区，每个社区用 LLM 生成社区摘要；
3. **查询时**：根据问题定位相关社区或实体，用社区摘要+图遍历得到上下文，再让 LLM 生成答案。

**优势**：能回答全局性、跨文档的问题，支持多跳推理。
**劣势**：构建成本高（大量 LLM 调用做实体抽取和摘要），更新成本高（新文档要重新抽实体更新图）。

适用场景：需要跨文档全局分析、多跳推理的垂直领域（如情报分析、合规审计）。通用问答场景仍以向量 RAG 为主。

### RAG 和微调怎么选？什么场景该用哪个？

这是一个高频面试题，核心是理解两者的能力边界：

| 维度 | RAG | 微调（SFT） |
|------|-----|------------|
| 知识更新 | 实时，改知识库即可 | 需重新训练，周期长 |
| 知识量级 | 海量，受限于向量库 | 受限于模型容量和训练数据 |
| 幻觉控制 | 强，有引用可溯源 | 弱，知识内化进权重难追溯 |
| 领域适配 | 中，依赖 prompt 引导 | 强，风格/术语深度内化 |
| 推理成本 | 高，每次要带上下文 | 低，知识在权重里 |
| 延迟 | 高（检索+生成两阶段） | 低（单阶段生成） |

**选型建议**：
- **知识频繁变化、需要溯源**：选 RAG（如客服知识库、法规查询）；
- **风格/格式/术语稳定但需内化**：选微调（如代码生成、特定领域问答）；
- **二者结合**：先用微调让模型学会领域术语和回答风格，再用 RAG 注入实时知识。这是生产环境最常见的组合方案。

### RAG 常见 Bad Case 怎么诊断和优化？

用诊断链思路定位问题环节：

1. **召回环节**：
   - 症状：答案跑题、信息缺失；
   - 诊断：打印召回的 Top-K chunk，人工核对正确答案是否在召回里。若不在，问题在召回，去优化 embedding 模型、查询改写、分块策略；
   - 若在召回里但答案仍错，问题在生成。

2. **重排环节**：
   - 症状：正确文档被排到后面，没进入最终 Top-N；
   - 诊断：对比召回分数和 rerank 分数排序，看正确文档的排名变化；
   - 优化：换 rerank 模型或微调。

3. **生成环节**：
   - 症状：文档里有答案但 LLM 没用上，或用错了；
   - 诊断：检查 prompt 里塞的上下文是否包含答案、答案位置是否在 lost-in-the-middle 盲区；
   - 优化：上下文重排、压缩、加引用提示。

4. **LLM 能力**：
   - 症状：上下文正确但推理能力不足（如需要多步数学计算）；
   - 优化：换更大模型或加 CoT 提示。

## Function Call 与工具调用深度

### 什么是 Function Call？大模型怎么知道要调用函数？

Function Call（函数调用）是让大模型**在回答问题时主动决定调用某个外部函数**的能力。比如问"北京今天天气"，模型不直接编一个答案，而是输出"调用 get_weather 函数，参数 city='北京'"，外部系统执行这个函数拿到真实天气，再让模型基于真实数据回答。

模型怎么知道要调用函数：

1. **系统告诉模型有哪些函数**：在 Prompt 里给模型一份"函数清单"——每个函数的名称、功能描述、参数结构（JSON Schema）。模型据此判断"用户的问题能不能用这些函数解决"；
2. **模型输出结构化调用指令**：如果决定调用，模型不输出自然语言，而是输出一个 JSON 格式的调用指令（函数名、参数值）；
3. **外部系统执行并回传结果**：外部系统解析这个 JSON，执行对应函数，把执行结果以 `tool_result` 消息形式回传给模型；
4. **模型基于结果生成最终答复**：模型看到真实结果，生成最终自然语言答复。

**注意**：模型本身不执行函数，它只是"决策调用什么、传什么参数"，真正执行的是外部系统。这是工程上常被误解的点——"大模型调用函数"严格说是"大模型提议调用函数，外部系统代为执行"。

### 大模型怎么获得 Function Call 能力？

模型不是天生就会 Function Call，而是通过**SFT 监督微调**学会"什么时候调用、调用什么、怎么传参"。

SFT 训练数据格式：

```
{
  "input": "用户的问题 + 函数清单",
  "output": "调用函数的 JSON 或直接文本答案"
}
```

每条样本教会模型两件事：

- **意图识别**：这个问题是直接回答还是需要调用工具？训练样本里既要有"该调用"的正例，也要有"不该调用"的负例（避免模型什么都想调函数）；
- **参数提取与格式化**：从用户输入里提取参数，按预定义 Schema 生成合法 JSON。

训练步骤：

1. **数据集构建**：覆盖真实场景，包含各种函数类型、参数组合、是否需要调用的判断样本；
2. **基础模型选择**：选指令理解能力强的预训练模型（Llama、Qwen 等）；
3. **数据格式组织**：用户输入 + 函数描述拼成 Prompt，期望输出作为目标；
4. **SFT 训练**：全参数微调或 LoRA，让模型学到"自然语言 → 结构化调用"的映射。

所以 **Function Call 能力的本质是 SFT 学会的结构化输出能力**——模型本来就会输出 JSON（指令微调阶段学过），SFT 只是让它学会"在合适时机输出调用 JSON 而不是自然语言"。

### Function Call 在落地中有什么问题？

落地时主要四类坑：

- **依赖精准的函数定义**：函数描述模糊或参数说明不清，模型就误调用、漏调用。必填项没标清楚，模型会漏填或乱填。解法是函数描述像写 API 文档一样严谨，参数 Schema 用严格 JSON Schema 约束；
- **性能损耗**：相比纯文本生成，多了"模型决策 → 函数执行 → 结果回传 → 再生成"环节，延迟增加。外部 API 调用本身就是慢点，用户等待时间显著拉长；
- **复杂决策能力有限**：多函数联动场景（"查奶茶店是否营业，若营业帮我预约明天 3 点"）需要先查后判再预约，模型容易逻辑断裂。隐含需求（"想喝奶茶，明天有空"暗示要预约）模型识别不出；
- **安全风险**：模型可能越权调用高危函数（删数据），或被恶意参数注入（SQL 注入式攻击）。解法是函数执行层做白名单校验、参数清洗、权限隔离。

AskData 项目里 SQL 执行就是一个高危函数，安全控制是：SQL Guard 先做 AST 校验（只允许 SELECT，禁写禁删），再执行；权限上数据库连接用只读账号，即使 SQL 漏过校验也写不了数据。

### 怎么提升模型调用 Function Call 的能力？

从数据、Prompt、Schema、工程四方面入手：

- **高质量训练数据**：覆盖更多真实场景，尤其"该调用 vs 不该调用"的对比样本，提升意图识别准确率；
- **函数描述优化**：description 要清晰具体、无歧义，参数说明要标清楚类型、必填、枚举值。好的描述比换更强模型还管用；
- **Prompt 设计**：在系统提示里明确工具使用规则（什么时候调、优先级、不调用的兜底），减少误调用；
- **Schema 严格约束**：用严格 JSON Schema 约束参数类型、必填项、枚举值，降低模型生成错误参数的概率；
- **结果校验与重试**：工程上对模型输出做格式校验（JSON 合法性、参数完整性），不合法触发重试或修正；
- **Tool Routing（工具路由）**：工具多时先做一层筛选或分类，缩小模型选择范围。比如 AskData 项目先把问题分到"订单域 / 支付域 / 商品域"，再让模型在域内选表，而不是全库选。

核心认知：**Function Call 不是"会用就会用"，要靠数据、约束、工程三件套才能稳定**。

### Tool Calling、Function Call、MCP、Skill 的关系是什么？

这四个概念经常被混在一起说，理清关系：

- **Function Call**：大模型输出结构化调用指令（函数名 + 参数 JSON）的能力，是最底层的机制；
- **Tool Calling**：Function Call 的工程化叫法，指模型调用外部工具完成任务的整个过程。Function Call 是"模型输出指令"，Tool Calling 是"模型输出指令 + 外部执行 + 结果回传 + 模型整合"的完整链路；
- **MCP（Model Context Protocol）**：Anthropic 提出的**标准协议**，定义了"应用如何把工具、资源、提示模板暴露给模型"的统一接口。Function Call 是模型侧能力，MCP 是工具侧标准——MCP 让不同工具按统一协议暴露，模型（或应用）按统一协议调用，避免"每个工具自己定义一套接口格式"的混乱；
- **Skill**：OpenAI/Claude 的概念，指"模型可复用的能力单元"，本质是一组打包好的工具 + Prompt 模板 + 使用说明。Skill 比 Function Call 更高层——一个 Skill 可能包含多个函数，模型按需"激活"对应 Skill。

层次关系：**Function Call（机制） → Tool Calling（链路） → MCP（协议） → Skill（能力包）**。本项目 MCP 实现就是按 MCP 协议把内部工具（SQL 执行、Schema 查询、记忆检索）暴露给 Agent，让 Agent 用统一接口调用。

### MCP 的核心组件有哪些？

MCP 架构由 Host、Client、Server 三类组件组成：

- **Host（宿主）**：整个流程的控制中心，是用户直接交互的入口（Claude Desktop、IDE、Agent 应用）。负责接收用户输入、调度模型、选择工具、返回最终结果；
- **Client（客户端）**：Host 和 Server 之间的通信桥梁，通常嵌入在 Host 内部。一个 Client 对应一个 Server，负责能力发现、消息收发、请求转发；
- **Server（服务端）**：能力提供方，把外部工具、资源、提示模板按 MCP 协议暴露出来。接收 Client 请求，执行操作，返回结果。

典型工作流程：用户在 Host 提需求 → Host 判断需要哪些能力 → Client 连接对应 Server 发现可用工具 → 模型选择工具并生成参数 → Client 发起 `tools/call` → Server 执行真实逻辑 → Server 返回结果 → Host 把结果喂给模型 → 模型整合成自然语言答复。

**关键认知**：MCP 不是"模型直接调函数"，而是"模型提出调用意图，真正发请求的是 Host 里的 Client，Server 按协议执行"。这种分层让工具和模型解耦——换模型不用改工具，换工具不用改模型，只要都遵循 MCP 协议就能互通。

### MCP 的工具调用流程具体是怎样的？

完整流程：

**前置条件**：工具暴露 API + 用户配置好密钥。

1. **用户提问** → Host 把问题交给模型；
2. **模型判断**：模型看到用户问题 + 可用工具清单，决定是否需要工具；
3. **能力发现**：Client 向 MCP Server 查询有哪些工具（`tools/list` 请求）；
4. **工具选择与参数生成**：模型选定工具并生成参数 JSON；
5. **调用执行**：Client 发起 `tools/call`，Server 按参数执行真实逻辑（如查数据库、调外部 API）；
6. **结果返回**：Server 把执行结果返回给 Client；
7. **结果回传**：Host 把结果以 `tool_result` 消息形式喂给模型；
8. **最终答复**：模型基于真实结果生成自然语言答复用户。

**和直接 Function Call 的区别**：MCP 多了"协议层"——Server 按 MCP 标准暴露工具，Client 按标准调用，双方不用关心对方是哪家厂商、什么语言。这就像 USB-C 接口，设备只要符合标准就能互联。

### Skill 的渐进式披露是什么意思？

Skill 机制的核心思想是"**渐进式披露（Progressive Disclosure）**"——不让模型一开始就看到所有能力（避免上下文爆炸），而是按需"激活"对应能力包。

具体做法：

- **能力索引**：系统提示里只放"能力清单"（有哪些 Skill、各自干啥），不放具体工具和 Prompt 模板。每个 Skill 描述只用一两句话，节省 token；
- **按需激活**：模型判断当前任务需要哪个 Skill，主动"激活"该 Skill，系统才把对应的工具清单、使用说明、参数 Schema 注入到上下文；
- **执行后清理**：Skill 执行完，相关工具和说明从上下文移除（或压缩成结果摘要），不长期占用窗口。

好处：

- **上下文经济**：不用一开始就把所有工具塞满窗口，token 省下来给关键信息；
- **决策聚焦**：模型每次只看到与当前任务相关的工具，选择更准；
- **能力可扩展**：新增 Skill 只改能力清单，不重新塞所有工具到系统提示。

本项目 MCP 实现也体现了这个思想——Schema 工具、SQL 执行工具、记忆工具按需调用，不是一开始全注入 Prompt。

## Text2SQL

### Text2SQL 的核心难点是什么？

Text2SQL 把自然语言转成 SQL，看似是"翻译"任务，实则面临三大难点：

1. **Schema 理解**：用户问"上个月销量前十的商品"，模型要知道"销量"对应哪张表的哪个字段，"上个月"对应什么日期过滤条件。数据库 schema 复杂时（几百张表、上千字段），这一步极易出错。

2. **SQL 语义复杂**：
   - **多表 JOIN**：要理清表间外键关系和 JOIN 路径；
   - **嵌套子查询**：多层嵌套逻辑难以从自然语言推导；
   - **聚合与分组**：GROUP BY、HAVING、窗口函数的语义边界模糊；
   - **多义性**：自然语言"每个部门的平均薪资"——是按部门分组算平均，还是算每个部门每个人的平均？需上下文消歧。

3. **数据库方言差异**：MySQL、PostgreSQL、ClickHouse、Hive 的函数和语法差异大，模型在不同方言间迁移成本高。

### Text2SQL 有哪些主流方案？怎么选？

从"确定性"到"灵活性"分三档：

1. **基于规则/模板**：
   - 做法：预先定义 SQL 模板，用槽位填充的方式生成 SQL；
   - 优势：100% 可控，无幻觉，适合固定报表场景；
   - 劣势：泛化差，自然语言稍有变化就匹配不上模板；
   - 适用：BI 固定看板、报表查询。

2. **LLM 直接生成（Prompt-based）**：
   - 做法：把 schema 和用户问题塞 prompt，让 LLM 直接生成 SQL；
   - 优势：泛化好，能处理复杂自然语言；
   - 劣势：幻觉风险，复杂 SQL 易错；
   - 适用：schema 简单、对准确率要求不极端的 demo 场景。

3. **语义层 + Agent（生产级方案）**：
   - 做法：不直接让 LLM 生成裸 SQL，而是先定义"语义层"（Semantic Layer）——把表和字段抽象成业务实体和指标（如"订单数"是一个语义实体，绑定了 SQL 片段），LLM 基于语义层组装查询而非手写 SQL；
   - 优势：把 schema 复杂度封装起来，LLM 只做意图识别和指标组合，确定性大幅提升；支持权限管控、指标口径统一；
   - 劣势：前期需投入建设语义层；
   - 适用：生产级 BI 自助分析、数据平台。

### Schema Linking 是什么？为什么是 Text2SQL 的关键？

Schema Linking 指把自然语言中的实体映射到数据库 schema 的具体表/字段的过程，是 Text2SQL 的第一步也是最容易出错的一步。

**为什么难**：
- 数据库字段命名不规范（如 `amt` 表示 amount，`c_id` 表示 customer_id）；
- 用户语言和字段名差异大（用户说"销售额"，字段叫 `order_amount`）；
- 同名字段在不同表语义不同（如 `name` 在 `user` 表是人名，在 `product` 表是商品名）。

**优化手段**：
1. **Schema 注释**：给每个表和字段加上中文注释和示例值，让 LLM 在 prompt 里能理解字段含义；
2. **Schema 剪枝**：不把全部 schema 塞给 LLM（几百张表会超 token 且噪声大），用向量检索先选出和问题相关的表，再让 LLM 在子集上做 linking；
3. **Few-shot 示例**：给几个"问题-schema-SQL"的示例引导；
4. **实体词典**：维护"业务术语-字段"映射词典，预处理阶段做实体识别和替换。

### Text2SQL 怎么用执行反馈做 Self-correction？

单次生成 SQL 容易出错，生产系统普遍采用"生成-执行-反馈-修复"的闭环：

1. **生成**：LLM 产出 SQL；
2. **执行**：在数据库试执行（可限流或只跑 EXPLAIN）；
3. **反馈收集**：
   - **语法错误**：数据库报错信息直接回传；
   - **运行时错误**：除零、类型不匹配、空表等；
   - **结果异常**：行数为 0、行数过多、NULL 值占比高——可能 SQL 逻辑有问题；
4. **修复**：把原 SQL、报错信息、schema 一起塞 prompt，让 LLM 修正后再执行，循环 2-3 次直到成功或放弃。

**要点**：
- **限制重试次数**：避免死循环，通常 2-3 次；
- **给 LLM 错误信息要可读**：原始数据库报错信息要清洗成 LLM 易理解的描述；
- **记录 bad case**：修复失败或修复成功的案例都要沉淀，用于后续 few-shot 或微调。

### Text2SQL 的评测怎么做？BIRD 和 Spider 基准有什么区别？

**评测维度**（诊断链）：
1. **表命中率（Table Recall）**：召回的相关表是否包含正确 SQL 所需的全部表；
2. **字段命中率（Column Recall）**：相关字段是否全部召回；
3. **SQL 语法准确率**：生成的 SQL 能否成功执行；
4. **执行准确率（Execution Accuracy, EX）**：执行结果和 gold answer 的结果集合是否一致——这是最重要的指标，因为同一查询可以有多个等价 SQL。

**Spider vs BIRD**：

| 维度 | Spider | BIRD |
|------|--------|------|
| 数据 | 人工构造的干净数据 | 真实脏数据（含空值、异常、大表） |
| Schema | 简单，字段语义清晰 | 复杂，字段需结合业务理解 |
| 评测 | 主要看 EX | 看 EX + 值匹配（valid efficiency score） |
| 难度 | 基础能力 | 接近生产 |
| 外部知识 | 不需要 | 需要业务领域知识才能答对 |

**结论**：Spider 适合测模型基础 SQL 能力，BIRD 更贴近生产。做内部评测建议仿照 BIRD 构造业务真实查询，并加上表命中/字段命中等中间指标便于归因。

### Text2SQL 生产系统怎么保证准确率？

单靠 LLM 无法达到生产级准确率，需要多层兜底：

1. **Schema 层**：语义层封装 + schema 剪枝 + 字段注释；
2. **召回层**：向量检索召回相关表和历史相似查询（few-shot）；
3. **生成层**：LLM 生成 SQL + few-shot 引导；
4. **校验层**：语法校验 + 执行校验 + 结果合理性校验（行数、空值）；
5. **修复层**：Self-correction 闭环 2-3 次；
6. **兜底层**：修复失败返回"无法理解，请补充信息"或转人工，绝不返回错误数据；
7. **缓存层**：高频查询缓存结果，直接命中不走向 LLM；
8. **监控层**：线上查询日志 + 用户反馈打分 + bad case 沉淀，持续优化。

### Text2SQL 在 NexusMind 里的架构设计？

NexusMind 的数据问答模块采用"语义层 + Agent + 多轮校验"架构：

- **语义层（Semantic Layer）**：用 Cube.js 或自研语义层把数仓表封装成业务指标和维度，LLM 只和语义层交互，不直接碰底层表；
- **意图识别 Agent**：判断用户意图（是查数据还是闲聊），分流到 Text2SQL 流程或对话流程；
- **Schema Linking 模块**：向量检索召回相关语义实体，配合实体词典做消歧；
- **SQL 生成模块**：LLM 基于语义层组装查询，输出标准化的 MDX/SQL；
- **执行与校验模块**：执行 + 结果合理性校验 + Self-correction 闭环；
- **可视化模块**：结果自动选型（表格/柱图/折线），前端渲染。

这种架构把"语言理解"和"查询生成"解耦：LLM 只负责语义理解和指标组装，确定性由语义层和执行校验兜底，准确率和可维护性都优于纯 LLM 方案。

## 系统架构与工程实践

### 大模型应用的整体架构分层是怎样的？

生产级 LLM 应用通常分四层：

1. **基础设施层**：
   - 模型服务：vLLM、TGI、SGLang 等推理框架；
   - GPU 集群：A100/H100，推理卡或训练卡；
   - 向量数据库：Milvus、Qdrant；
   - 缓存：Redis（会话缓存）、CDN（模型缓存）。

2. **能力层**：
   - 模型网关：统一路由、限流、计费、多模型 fallback；
   - Prompt 管理：版本化、AB 测试；
   - RAG 管线：文档解析、分块、索引、检索、重排；
   - Agent 框架：工具注册、任务编排、记忆管理。

3. **应用层**：
   - 业务 Agent：客服 Agent、数据分析 Agent、写作 Agent 等；
   - 工作流编排：LangGraph、Dify、自研编排；
   - 多模态接入：语音、图像、文档。

4. **交互层**：
   - 前端：对话 UI、流式渲染、可视化图表；
   - 接入渠道：Web、App、IM、API。

### 大模型推理服务怎么优化延迟和吞吐？

延迟（单请求时延）和吞吐（QPS）往往需要权衡：

1. **批处理（Continuous Batching）**：
   - 静态批处理要等凑齐一批再算，延迟高；
   - 动态批处理（Continuous Batching）请求来一个进一个，到达 token 级别动态组批，vLLM 的核心特性；
   - 牺牲单请求一点延迟换大幅吞吐提升。

2. **KV Cache 优化**：
   - **先理解 KV Cache 是什么**：自回归生成时，每生成一个新 token 都要和所有历史 token 做注意力计算；KV Cache 把每个历史 token 已经算过的 Key/Value 张量缓存下来，新 token 只需算自己的 Query 再与缓存的 K/V 做注意力，避免每步重算整段历史——这是自回归推理能跑起来的基础优化。KV Cache 的代价是**占显存**：上下文越长、并发越高，缓存越大，所以显存管理成了推理框架的核心战场；
   - **PagedAttention（vLLM）**：把 KV Cache 像操作系统的内存分页一样按"页"分配管理，减少显存碎片，提升显存利用率；
   - **Prefix Caching**：相同前缀（如固定的系统 prompt）的 KV Cache 跨请求复用，减少重复计算。

3. **量化（Quantization）**：
   - **INT8/INT4 量化**：把 FP16 权重压成低比特，显存减半、推理加速；
   - **GPTQ/AWQ/GGUF**：不同的量化算法，精度/速度权衡不同；
   - 量化会损失一点精度，需评测业务影响。

4. **投机解码（Speculative Decoding）**：
   - 用小模型先快速生成 draft token，大模型并行校验，校验通过的 token 一次产出多个；
   - 适合对延迟敏感、模型可分级的场景。

5. **模型蒸馏与 MoE**：
   - **蒸馏（Knowledge Distillation）**：用大模型生成的答案作为"教材"训练小模型，让小模型模仿大模型的输出分布，部署成本大幅降低但保留大部分能力；
   - **MoE（Mixture of Experts，混合专家）**：把模型的前馈层换成多个"专家"子网络，每个 token 只路由给其中两三个专家计算（如 Mixtral 是 8 选 2）——总参数量很大（知识容量大），但每次前向只激活一小部分（计算量小），用"参数多、计算省"换取容量与推理成本的平衡。

### Agent 的记忆系统怎么设计？

Agent 记忆分短期和长期：

1. **短期记忆（Working Memory）**：
   - 当前对话上下文，放在 prompt 里；
   - 问题：上下文长了 token 膨胀，注意力分散，成本上升；
   - 优化：滑动窗口保留最近 N 轮，超出的摘要压缩。

2. **长期记忆（Long-term Memory）**：
   - 跨会话持久化，常见做法是"记忆库 + 检索"：
     - 把过往对话或事实抽成条目存向量库；
     - 每轮对话开始时，用当前 query 检索相关记忆条目塞 prompt；
   - 记忆条目结构：`{content, timestamp, importance, tags}`；
   - 记忆更新：每轮结束后让 LLM 抽取值得记住的事实写入记忆库，低重要性条目定期淘汰。

3. **记忆管理的坑**：
   - **记忆污染**：错误信息写入记忆库会持续误导后续对话，需要置信度阈值和人工审核；
   - **检索召回差**：记忆条目质量参差，召回不准会引入噪声；
   - **时效性**：旧记忆可能过时，需要带时间戳并定期失效。

### 如何评估一个大模型应用的好坏？

分四层评估：

1. **模型层**：
   - 通用 benchmark：MMLU、CEval、GSM8K 等；
   - 领域 benchmark：医学、法律、代码等垂直评测；
   - 作用：选型参考，但不完全代表业务效果。

2. **能力层**：
   - 针对应用拆解出具体能力维度（如意图识别准确率、SQL 生成准确率、文档抽取 F1）；
   - 每个维度构造评测集，自动化跑指标；
   - 作用：定位短板，指导优化。

3. **端到端任务层**：
   - 用真实业务任务做评测集，人工标注 gold answer；
   - 指标：准确率、完成率、用户满意度；
   - 作用：衡量应用整体效果。

4. **线上监控层**：
   - 用户反馈（点赞/点踩）、人工抽检、bad case 沉淀；
   - A/B 测试对比不同 prompt/模型/参数；
   - 作用：持续监控线上质量，驱动迭代。

### 大模型应用的成本怎么控制？

成本主要来自 GPU 推理和 API 调用，控制手段：

1. **模型分级**：简单任务用小模型/便宜模型，复杂任务才用大模型，路由层分流；
2. **缓存**：
   - **结果缓存**：相同 query 直接返回历史结果；
   - **语义缓存**：query 向量相似度高的复用历史结果（注意准确率风险）；
   - **Prompt 缓存**：相同 prefix 的 KV Cache 复用（如系统 prompt）；
3. **上下文压缩**：长上下文先摘要再送 LLM，减少 token；
4. **量化部署**：自部署用 INT8/INT4 量化，显存和算力成本降一半以上；
5. **批处理**：离线任务攒批，实时任务用 Continuous Batching 提升吞吐；
6. **Prompt 优化**：精简 prompt、few-shot 选最有效的样本而非堆量。

### 大模型应用上线要做哪些保障？

1. **安全护栏**：
   - 输入侧：敏感词过滤、prompt injection 检测、越狱防御；
   - 输出侧：内容安全审核（涉政、涉黄、暴力）、PII 脱敏；
2. **幻觉控制**：
   - RAG 溯源、置信度兜底、关键事实强制校验；
3. **可观测性**：
   - 全链路日志：输入、prompt、检索结果、LLM 输出、耗时；
   - 监控大盘：QPS、延迟、错误率、token 成本、用户满意度；
   - 告警：延迟飙升、错误率突增、成本异常；
4. **降级与熔断**：
   - 模型 fallback：大模型超时切小模型；
   - 功能降级：RAG 失败走纯生成，Text2SQL 失败走模板兜底；
5. **灰度发布**：小流量验证再全量，配套 AB 实验框架。
