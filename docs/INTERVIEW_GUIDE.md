# NexusMind 面试指南

---

## 一、面试话术

### 1.1 一分钟电梯介绍

> 我做了一个对话式 BI 智能体 NexusMind。用户用自然语言问"最近三个月各品类销售额"，系统自动生成 SQL 查双库返回结果；问"为什么 11 月销售额暴增"，走根因分析规划链拆解假设并并行取证给归因报告；问"数据质量有没有问题"，跑 7 条对账规则出告警。核心是语义层——14 个指标、18 个维度、6 类复合计划，NL 先编译成中间表示再确定性生成 SQL，不靠 LLM 即兴写。域内 15 题端到端 EX 100%，Spider 20 个跨域数据库 99 题 EX 81.8%，在 zero-shot 设定下高于 GPT-4 zero-shot 的 60-75%。技术栈是 LangGraph 多智能体 + FastAPI + React，双 SQLite 真实数据集，20,000 行代码，34 项回归测试。

### 1.2 三分钟深度介绍

> NexusMind 是一个面向企业数据分析场景的 ChatBI Agent。它不是通用聊天机器人，而是"语义层 + 意图路由 + SQL 守卫自修复 + 根因分析规划链 + 数据质量对账 + 字段级评测闭环"的组合系统。
>
> **数据层**用两个真实数据集：Olist 巴西电商（14,747 订单，8.9MB，9 张表）和 Chinook 数字媒体（984KB，11 张表），通过 SQLite ATTACH 实现跨库查询。数据里内置了真实业务异常——黑五大促、家具差评率偏高、卖家延迟发货。
>
> **核心引擎**是 ChatBI 12 模块，最重要的三个：一是语义层 MetricPlanCompiler，把"各品类销售额排名"这种自然语言先解析成 {metrics, dimensions, filters, sort, limit} 的中间表示，再确定性编译成带正确 JOIN 的 SQL，指标口径由代码而非 prompt 保证。二是 SQL 守卫，用 sqlglot 做 AST 语法校验，执行失败自动反馈错误给 LLM 重试，还有结果合理性检查（空结果归因、LIMIT 截断检测、NULL 列占比告警）。三是根因分析规划链，"为什么 11 月暴增"这种问题先让 SOTA 模型拆成 3-4 个假设，再并行执行证据 SQL 取证，最后生成带置信度的归因报告。
>
> **评测做了四套**：域内 15 题 EX 100%、复合专项 12 题 100%、域内泛化 10 题 80%、Spider 全 20 库 99 题 EX 81.8%。Spider 评测用四项核心指标——执行准确率 81.8%、表命中率 97%、行召回率 0.851、字段准确率 0.898——构成"选对表→查全行→值准确→整体对"的完整评测链路。12/20 库满分，包括 8 表复杂 schema 的 dog_kennels。
>
> **工程亮点**最值得说的是评测驱动数据治理：跑四维度评测时发现 RAG 上下文里全是乱码（hex 全是 0x3f），排查到底不是提取代码的 bug 而是 PDF 生成时就丢了中文，重新生成后按文件哈希跨 PostgreSQL 三张表 + Milvus 集合清理脏数据，端到端复测确认干净。这个经历让我深刻理解了"评测不只是打分，还能驱动数据治理"。

### 1.3 主动引导话术

面试中可以用这些问题主动引导话题方向：

- "我对 NL2SQL 的评测体系做了比较深入的研究，可以展开聊聊吗？"——引导到四套评测和 Spider 指标

## 二、项目介绍

### 2.1 一句话定位

对话式 BI（ChatBI）：用户问"最近三个月各品类销售额"它生成 SQL 查双库，问"为什么 11 月销售额暴增"它走根因分析规划链拆解假设并并行取证，问"数据质量有没有问题"它跑 7 条对账规则出告警报告。

### 2.2 架构设计

```
用户提问
  │
  ▼
SchemaLinker（NL → IR：解析指标、维度、过滤、排序、LIMIT）
  │
  ▼
路由决策 ──┬── 语义编译（单指标 + 维度一致 → 确定性 SQL）
           ├── 复合计划（6 类复合指标 → 模板编译）
           ├── LLM fallback（未命中指标 → LLM 自由生成）
           └── 根因分析（为什么/对比/异动 → 假设拆解 → 并行取证）
  │
  ▼
AST 校验（sqlglot 语法检查）
  │
  ▼
SQL 守卫（执行 → 自修复 → 结果合理性检查）
  │
  ▼
双 SQLite 执行（Olist + Chinook，ATTACH 跨库）
  │
  ▼
字段级评测 + 全链路追踪 + 数据质量对账
```

### 2.6 Spider 四项核心指标

| 指标 | 值 | 说明 |
|---|---|---|
| EX（执行准确率） | 81/99（81.8%） | Agent SQL 与 Gold SQL 执行结果集一致（Jaccard≥0.8） |
| SL（表命中率） | 96/99（97.0%） | Agent SQL 引用的表名集合与 Gold SQL 完全一致 |
| 行召回率（Field Recall） | 0.851 | Gold 结果行中 85.1% 出现在 Agent 结果中（按 key 列对齐） |
| 字段准确率（Cell Accuracy） | 0.898 | 匹配行中 89.8% 的单元格值正确 |

评测链路：选对表（SL 97%）→ 查全行（Recall 0.851）→ 值准确（Accuracy 0.898）→ 整体对（EX 81.8%）。

业界对比：Spider test 集 SOTA 约 86-91%（GPT-4 + few-shot + 自我一致性），GPT-4 zero-shot 约 60-75%。本系统 81.8% 在 zero-shot 设定下处于合理偏上水平。

### 2.7 优化历程

V1 Baseline EX 20.0% → V2 Schema 检索 26.7% → V3 SQL 契约 40.0% → V4 语义层 46.7% → V5 复合计划 100%（域内 15 题）→ V5.1 Spider 全库 81.8%（跨域 99 题）。

## 三、项目相关问题

### 架构设计类

**Q1：为什么用语义层而不是直接让 LLM 生成 SQL？**

纯 NL2SQL 有三个问题：一是指标口径不稳定，"回头客户数"每次 LLM 可能用 customer_id（每订单唯一）或 customer_unique_id（回头客共享），语义混淆反复出现。二是 JOIN 路径不可控，LLM 可能拼出语法对但逻辑错的 JOIN。三是不可审计，你不知道 LLM 为什么这么写。语义层把指标口径固化为代码，编译器保证 JOIN 正确，IR 中间记录记录了路由原因和降级理由。我的 Spider 评测也验证了这一点：域内 15 题用语义层 EX 100%，Spider 99 题不用语义层直接 LLM 直出 EX 81.8%，差距就是语义层的价值。

**Q2：路由决策怎么做的？为什么需要四条路径？**

路由依据是 SchemaLinker 解析出的 IR。如果 IR 里指标命中语义层且维度一致，走确定性编译——这条路不经过 LLM，指标口径由代码保证。如果命中 6 个复合计划之一（比如"支付方式统计"需要同时算金额和数量两个指标），走模板编译。如果 IR 里有"为什么""对比""异动"关键词，走根因分析规划链。以上都不命中，降级到 LLM fallback。四条路径的设计原则是"能确定的不用概率"——确定性路径的 EX 是 100%，LLM fallback 路径的 EX 明显更低。

**Q3：复合指标计划和单指标编译有什么区别？**

单指标编译是"各品类销售额"——一个指标（销售额）+ 一个维度（品类），编译器直接拼 JOIN + GROUP BY + SUM。复合计划是"支付方式统计"——需要同时算每种支付方式的金额和订单数两个指标，还需要计算占比这种派生指标。复合计划用预定义的 SQL 模板，模板里已经写好 JOIN 逻辑和 CASE WHEN 分支，NL 只需要填参数（比如时间范围、筛选条件）。6 个复合计划覆盖了支付方式统计、跨库对比、品类差评拆解、流派收入效率、卖家延迟率、流派收入驱动这些高频复杂分析场景。

**Q4：LangGraph 多智能体编排的具体节点是什么？**

LangGraph StateGraph 的核心节点是 Supervisor 路由分发。根据意图走不同分支：ReAct 循环处理复合查询（"查下单到哪了顺便看看还剩多少红包"会接力调用三个工具），Coordinator 处理跨模块复合查询（业务+政策+历史≥2类时 SOTA 拆解子任务并行派发），Synthesize 做答案合成和转人工预判，Reflection 审视回答质量不达标时咨询 Advisor 拿改进方向再重试。还有 ContextStore 做动态上下文——超长工具结果存档后 Agent 可通过 recall_context 工具按关键词回忆，截断从"丢信息"变成"延迟加载"。

### 技术选型类

**Q5：为什么用 sqlglot 而不是自己写 SQL 解析器？**

sqlglot 是 Python 生态最成熟的 SQL 解析器，支持 20+ 方言的 AST 解析和转换。我用它做三件事：一是 AST 语法校验，检查表名/列名是否存在、CTE 别名是否合法、ORDER BY 是否引用了输出别名；二是组件提取，从 Gold SQL 和 Agent SQL 中提取 FROM/SELECT/WHERE 等子句做匹配率统计；三是方言转换，确保生成的 SQL 是 SQLite 方言。自己写解析器投入产出比太低，而且 sqlglot 的 AST 可以做更复杂的事情比如 SQL 重写和等价转换。

**Q6：为什么用 SQLite 而不是 PostgreSQL 做数据层？**

两个考虑：一是面试项目要能一键跑起来，SQLite 零配置零依赖，git clone 完直接能用。二是 Spider 基准本身就是 SQLite，用 SQLite 可以无缝对接 Spider 评测。但我的架构层做了抽象，SQLGuardPipeline 的执行接口是 `execute_sql_guarded(sql, db_path)`，换成 PostgreSQL 只需要改连接层。实际上项目里 PostgreSQL 也有用——用于文档元数据、对话历史这些需要持久化的场景。

**Q7：DeepSeek v4-flash 的效果够用吗？为什么不用 GPT-4？**

DeepSeek v4-flash 在 Spider 上 zero-shot EX 81.8%，对比 GPT-4 zero-shot 的 60-75%（学术界报告），表现合理偏上。用 flash 而不是 pro 是有意为之——我想验证"弱模型 + 强工程"的思路：语义层把指标口径固化成代码、SQL 守卫做自修复兜底、Schema 三级检索收敛上下文，这些工程手段可以弥补模型能力的不足。域内 15 题 EX 100% 就是这个思路的证明。如果换 GPT-4 预期 Spider 会更高，但那更多是模型能力的体现而不是系统设计的价值。

**Q8：Milvus 为什么用双模式（Lite + standalone）？**

开发用 Milvus Lite（单文件模式，零部署），生产用 standalone（gRPC 异步）。但 Milvus Lite 不支持 `wait_for_creating_index` 这种异步 gRPC 调用，会报 `AllocTimestamp not implemented`。我的处理是检测 uri 是否为本地文件路径，是则跳过 index 等待。还有一个 pymilvus 升级后的 bug：删除操作的返回值从 dict 变成了 int，我的清理逻辑之前在 `result["delete_count"]` 上取值会报错，改成直接判断 int。

### 评测深度类

**Q9：为什么从 9 个指标精简到 4 个？**

最初算了 9 个指标，但发现其中 5 个要么有误导性要么是冗余的。EM（组件匹配率）37.4% 看着低但其实是假象——LLM 用不同别名写法、不同 JOIN 语法、不同 WHERE 谓词排列，语义完全等价但字符串级精确比对就是不过，EX 81.8% 而 EM 37.4% 差了 44 题全是这种情况，Spider 社区自己也早就不用 EM 了。Executability 100% 当然好但它是 binary 基线检查，到了 100% 后没有区分度。Avg Jaccard、Exact Match、Zero Match 三个全是从 EX 的 Jaccard 计算里派生的——均值、J=1.0 子集、J=0.0 尾部——不是独立维度。精简后 4 个指标形成一条完整评测链路：选对表（SL）→ 查全行（Recall）→ 值准确（Accuracy）→ 整体对（EX），叙事更清晰。

**Q10：行召回率和字段准确率怎么算的？**

先从 Gold SQL 和 Agent SQL 的结果中各选一个 key 列（通常是主维度列如 customer_state、country）。然后按 key 列值对齐两个结果集——如果某个 key 值在 Gold 和 Agent 结果中都有，就算一行匹配。行召回率 = 匹配行数 / Gold 总行数，衡量"该查到的行查到了多少"。字段准确率 = 匹配行中正确单元格值 / 匹配行总单元格数（数值列容差 0.5），衡量"查到的行里每个格子对不对"。这两个指标把 EX 的 pass/fail 二元判断拆开了——EX fail 的题，你看召回率和准确率就知道是"少查了几行"还是"值算错了"。

**Q11：Spider 评测的 18 个失败案例怎么分类的？**

三类。类型 A（9 题）：行召回 R=0 + 字段准确 A=0，结果集完全错位，主因是 SELECT 列序倒了（Gold 是 `(count, name)` Agent 是 `(name, count)`）和 flight_2 数据脏值（AirportCode 尾部空格导致精确匹配返回空、Agent 用 TRIM 返回非空）。类型 B（4 题）：行召回 R=0 + 字段准确 A=1.0，key 列对齐后无交集行，Agent 返回的 key 值和 Gold 不重叠。类型 C（5 题）：行召回 R=1.0 + 字段准确 A=1.0 但 EX 仍失败，行和字段都对但 Agent 返回了多余行或排序方向不同。这个分类的价值是告诉我不应该笼统说"失败了"，不同类型的失败有不同的改进方向——列序问题改排序归一化，脏值问题改数据清洗，多余行问题改 LIMIT 约束。

**Q12：为什么 Spider 评测不用你的语义层和 SQL 守卫？**

Spider 的 20 个数据库是完全不同的领域——航班、大学、电视节目、网球——我的语义层是为 Olist 电商和 Chinook 数字媒体定制的 14 个指标，在 Spider 上没有对应。这恰好是评测的意义：Spider 测的是"脱离语义层后，LLM 直出 SQL 的裸能力"。这让我能区分"系统设计带来的提升"和"LLM 自身能力"——域内 100% 里有语义层的贡献，Spider 81.8% 是 LLM 的 baseline。如果面试官问"你的系统在陌生领域表现如何"，Spider 81.8% 就是答案。

### 工程实践类

**Q13：评测驱动数据治理是什么？**

跑四维度评测（Relevance/Accuracy/Completeness/Safety）时发现 RAG 上下文里混着乱码（全是 `???`）。第一反应是提取代码的 bug，但 byte 级检查发现 hex 全是 0x3f——这些 `???` 不是编码丢失，是入库前 PDF 生成时就丢了中文。确认根因后，重新生成了一份正常 PDF，然后按文件哈希跨 PostgreSQL 三张表（文档元数据、分块、对话历史）+ Milvus 集合清理脏数据，再端到端复测确认干净。顺手还修了一个 pymilvus 升级导致的删除计数 bug（返回值从 dict 变成了 int）。这个经历让我理解了"评测不只是打分，还能驱动数据治理"——如果没跑评测，这个脏数据问题永远不会被发现。

**Q14：你提到调了一天 bug 的路由仲裁，能具体讲讲吗？**

做外卖客服场景时踩了四个坑，都是黄金测试集跑出来的。第一是 Plan Mode 劫持——"帮我查一下订单"里的"帮我"触发了规划分支，查单请求被拆成任务列表但永远不调订单工具。修复是外卖意图优先短路到 Plan Mode 之前。第二是 requires_human 被 LangGraph 静默丢弃——转人工标志确实生成了（日志可见），但 AgentState TypedDict 里没定义这个字段，LangGraph 直接丢掉未声明的 key，API 永远返回 false。这种"日志对但结果错"的 bug 最坑。第三是规则满置信被投票稀释——规则正则完全命中"食物不新鲜"（confidence=1.0），但权重只有 0.3，加权后 0.3 低于 0.4 阈值。第四是正则优先级——"订单 WM20260822002 超时了"同时命中"订单"和"超时"，规则字典必须按意图特异性排序。这些 bug 的共性是：多通道融合的仲裁规则，比单一通道的准确率更重要。

**Q15：自进化闭环怎么保证质量？**

双阈值设计。后台任务每 5 分钟查 Bad Case 库，低分样本交给 LLM 分析原因抽取通用规则。高置信度（≥0.85）自动 accept，低置信度 pending 等人工看。已处理 ID 持久化到文件，重启不重复跑。面试官如果问"万一 LLM 抽出来的规则是幻觉怎么办"，答案就是宁可少自动、不多幻觉——0.85 的阈值设得很高，宁可让大部分规则走人工审核。而且规则抽出来后不是直接生效，还要经过 Bad Case 闭环验证：用新规则重跑失败案例，字段级评测确认修复了才回写 Few-shot 知识库。

**Q16：SQL 守卫的自修复具体怎么做的？**

三重保障。第一层静态校验：sqlglot AST 检查表名存在性（含 CTE 别名排除）、SQLite 方言函数黑名单（比如 LEFT() 在 SQLite 不存在）、禁止写操作。第二层 LLM 自修复：如果执行报错，把错误信息 + Schema 反馈给模型重新生成，最多 2 轮。实测 `LEFT(customer_state, 2)` 方言错误 1 轮自动修复为 `substr(customer_state, 1, 2)`。第三层结果合理性检查：空结果归因提示、TopN 与 LIMIT 一致性检查、NULL 列占比≥50% 告警、比率列>100% 越界检测。第三层很重要——SQL 可能语法对、能执行、但返回空结果或截断结果，这种"静默错误"光看执行成功与否发现不了。

### 开放性问题

**Q17：这个项目你最大的收获是什么？**

两个。第一是"评测驱动迭代"的方法论。从 V1 的 20% 到 V5 的 100%，每一步提升都来自评测发现的失败模式：V2 加 Schema 检索是因为 baseline 连表名都选不对，V3 加 SQL 契约是因为 LLM 随意加 LIMIT 截断结果，V4 加语义层是因为回头客口径反复混淆，V5 加复合计划是因为多指标查询 LLM fallback 总失败。如果没有评测，我不知道该改什么。第二是"多通道融合的仲裁规则比单一通道准确率更重要"。这个认知来自路由 bug 的调试——三路融合意图识别（规则+LLM+历史）看着很美，但实际跑起来规则满置信被投票稀释、Plan Mode 劫持外卖意图、LangGraph 静默丢字段，每个仲裁规则都对应一个真实 bad case。

**Q18：如果给你更多时间，你会怎么改进？**

三个方向。一是 Spider EX 从 81.8% 提升到 86%+：当前 18 个失败案例里 5 个是列序问题（改排序归一化即可）、3 个是 flight_2 脏值（加 TRIM 预处理）、3 个是过度工程化日期解析（prompt 加"不要对日期列做 substr 拆解"指令）。这些是低垂果实，预期可以到 86-88%。二是语义层泛化：当前 14 个指标是硬编码的，如果能把指标定义做成配置文件或从数据库 schema 自动推断，就能在 Spider 等陌生领域也用上语义层。三是多轮交互：当前是单轮 text2sql，如果加上"用户问完销售额后追问'那和上个月比呢'"这种多轮对话，需要做指代消解和上下文管理。

**Q19：和市面上的 ChatBI 产品比，你的优势在哪？**

和 WrenAI 比，我做了复合指标计划——WrenAI 的语义层只支持单指标编译，我的 6 个复合计划可以处理多指标+派生比率+跨库对比这种复杂场景。和 Vanna 比，我不只是 RAG + LLM 生成，我有确定性编译路径——命中的指标不走 LLM，口径由代码保证。和 DB-GPT 比，我有字段级评测闭环——不只是 EX pass/fail，还能区分"少查了几行"还是"值算错了"。和这些产品最大的区别是：我的评测是四套独立的，域内满分不等于跨域满分，Spider 81.8% 是诚实的泛化能力数字。

**Q20：项目中最难的部分是什么？**

不是写代码，是调 bug。特别是两个"日志对但结果错"的 bug。一个是 requires_human 被 LangGraph 静默丢弃——转人工标志确实生成了，日志里清清楚楚有 `requires_human=True`，但 AgentState TypedDict 里没定义这个字段，LangGraph 直接丢掉未声明的 key，API 返回的永远是 false。你不查返回值根本发现不了。另一个是意图识别阈值 bug——三路融合里 LLM 通道权重 0.5 × 置信度 1.0 = 0.5，但整体阈值设了 0.6，这意味着 LLM 单独判定永远过不了。这两个 bug 的共性是"设计上看起来合理，但实际跑起来数学不对"。跑测试集之前完全发现不了，因为单题手动测的时候 LLM 和规则偶尔都判对，只有全量跑才能暴露概率层面的问题。
