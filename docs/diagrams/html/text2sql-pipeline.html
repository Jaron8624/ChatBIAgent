Text2SQL：两阶段编译 + 四层路由

核心思想："能确定的不交给概率"——已治理指标走确定性编译，只有开放问题才交给 LLM 概率生成
第一阶段：理解（NL → IR）
输入

自然语言问题

"最近三个月各品类销售额排名"

→
SchemaLinker

三级 Schema 检索 + 要素抽取

数据域 → 表（含已验证 JOIN）→ 字段，三级收敛出最小充分 Schema；抽取指标 / 维度 / 过滤 / 排序 / LIMIT

→
结构化中间表示 IR（可审查）
{ metrics: [sales_revenue],
  dimensions: [product_category],
  filters: [last_3_months],
  sort: revenue_desc }
▼ 按 IR 置信度与结构做路由决策（决策理由写入 IR，可审计）
第二阶段：生成（IR → SQL），四层路由
① semantic_compile 语义层编译

单一已治理指标

MetricPlanCompiler 按指标定义（事实表/聚合/JOIN 路径）确定性组装 SQL——毫秒级、零 LLM 成本、口径由代码保证

② composite_plan 复合指标计划

多指标 + 派生比率

确定性 SQL 模板（共 6 类）——分子分母同口径的聚合结构固化在模板里，不靠两个独立 SQL 拼接

③ root_cause 根因分析

"为什么"类问题

假设拆解 → 并行取证查询 → 证据归因，每条结论背后有可复核的取证 SQL

④ llm_fallback 开放域兜底

未治理 / 陌生 Schema

DDL + 外键 + 每表 3 行样本构造 Prompt 交给 LLM 生成——Spider 开放域 zero-shot 靠这条路

▼ 无论哪条路产出的 SQL
统一出口

SQL Guard 三层防护

AST 静态校验 → 执行自修复（≤2 轮）→ 结果合理性检查
四条路径的 SQL 都强制经过同一个守卫

→
产出

可信 SQL + 执行结果 + 口径说明 + 全链路 Trace 留痕（IR / 路由理由 / SQL / 告警可复核）

一句话总结：两阶段分离让中间结果可审查——IR 错是"理解"的问题，SQL 错是"生成"的问题，归因才有抓手；"不能编译"也是一种明确结果（如维度跨数据集直接降级 LLM），比强行生成一条错误 SQL 好得多。
