混合检索的两种存储组织方式

向量检索 + 关键词检索，放在一套系统里还是两套系统里？

✅ 单存储引擎（本项目方案）

应用层：一次 hybrid_search 请求
稠密向量 + 稀疏向量 两路 AnnSearchRequest
▼
Milvus（一套系统）
稠密：HNSW + COSINE ｜ 稀疏：SPARSE_INVERTED_INDEX + BM25（内置 Function 自动生成）｜ 融合：RRFRanker
优点：部署一个组件、无跨系统一致性问题、融合由引擎内完成
缺点：两路配置耦合，不能独立调优/扩缩容
适配场景：万级文档/记忆规模，运维简单的收益 >> 独立调优的收益

双存储引擎

应用层：分别查询 + 自行归并结果
一致性、归并逻辑都要自己维护
▼                  ▼
Milvus
只管稠密向量召回
Elasticsearch
只管 BM25 关键词召回
优点：两路独立优化、独立扩缩容（关键词压力大单独给 ES 加节点）
缺点：两套系统运维、双写一致性、结果归并逻辑自维护
适配场景：千万级以上语料、两路负载差异悬殊的大厂场景
选型结论：当前数据量（万级）选单存储引擎——Milvus 一站搞定稠密 + BM25 稀疏 + RRF 融合。另有零依赖降级方案：纯 Python 实现 BM25 + 字符 n-gram 向量 + RRF（无 Milvus 环境可用），接口保持一致，部署 Milvus 后可直接替换 dense 实现，上层逻辑不变。
