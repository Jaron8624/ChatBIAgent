为什么不能只靠 LLM 直接生成 SQL？

裸 LLM 的三大失效模式 vs NexusMind 的工程化解法

✗ 裸 LLM 生成 SQL

1
指标口径漂移
同一个"销售额"，这次聚合 price，下次可能聚合 payment_value——口径每次都可能不同，今天和明天的答案对不上。
2
JOIN 路径失控
多表关联时模型自由选择路径，可能漏关联、错关联或重复计数——订单和支付是一对多，直接 JOIN 会让订单量虚增。
3
静默错误
SQL 能执行但结果是错的：空结果、比率超 100%、TopN 忘记 LIMIT——没有任何报错信号，最危险。
VS

✓ NexusMind 的解法

1
语义层确定性编译
14 指标 × 18 维度的口径固化为代码，命中已治理指标走编译器而非模型——同一个 Plan 永远生成同一条 SQL，口径可审计。
2
已验证 JOIN 关系图
Schema 三级检索直接给出验证过的 JOIN 子句，不让模型看到外键后自己猜——从根上杜绝连错表、漏关联。
3
SQL Guard 三层防护
静态校验 + 执行自修复 + 结果合理性检查，静默错误被逐一捕捉；告警随结果展示，绝不盲改业务口径。
SQL GUARD 三层防线 · 每层防一类完全不同的故障
① 静态校验（执行前）
sqlglot AST 判定：只读约束 / 方言函数黑名单 / 表列存在性 / 多语句注入拦截
→
② 执行自修复（报错后）
错误信息 + Schema 反馈修复模型，≤2 轮；意图保持约束防越修越偏
→
③ 结果合理性（成功后）
空结果 / TopN 无 LIMIT 回送重试；NULL 占比 / 比率越界只告警不改口径
