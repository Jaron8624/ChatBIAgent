SQL Guard 三层防护

模型生成的 SQL 不能信任到直接执行——三层防线分别覆盖危险操作、执行失败、静默错误三类完全不同的故障模式
输入

模型生成的 SQL

来自语义层编译或 LLM fallback

→
第 1 层 · 执行之前

静态校验（SQLValidator）

sqlglot AST 语句类型判定：INSERT/UPDATE/DELETE/DROP/ALTER/CREATE/TRUNCATE/PRAGMA/ATTACH 一律拦截；多语句注入（SELECT…; DROP…）同样拦截

方言函数黑名单（SQLite 禁 LEFT()）+ 表/列存在性校验

为什么 AST 不用正则：正则会误伤 REPLACE() 函数和含 "update" 的字符串字面量；AST 只认真正的语句节点

→
试执行

真实落库执行

通过静态校验的 SQL 在数据库真实执行
语法对 ≠ 能跑通（类型错误等执行期才暴露）

→
第 3 层 · 执行成功之后

结果合理性检查

可修复失败（回送模型重试）：空结果、用户问 TopN 但 SQL 无 LIMIT

只告警不改 SQL：行数过大未 LIMIT、列 NULL 占比 ≥50%、比率列 >100%——可能是真实业务现象，盲改口径会掩盖业务问题

↩ 第 2 层 · 执行自修复（最多 2 轮）：任何一层失败时，把【报错信息 / 校验诊断 + Schema 节选】反馈给修复模型重新生成 SQL——修复提示词内置方言规则（SQLite 用 strftime 不用 LEFT）与口径规则（比率要核对分子分母同口径、保持原查询意图不变），修复后的 SQL 重新从第 1 层开始过检。
真实修复案例

模型生成 LEFT(customer_state, 2)（SQLite 不支持）→ 静态校验命中方言黑名单 → 反馈修复 → 产出 substr(customer_state, 1, 2) → 重新过检 → 执行成功

兜底：越修越偏怎么办

轮次上限 2 轮，修不好如实把告警抛给上层展示，不无限循环；意图保持约束防止修复跑偏题

一句话总结：三层各防一类病——静态校验防危险、自修复防跑不通、合理性检查防"能跑但结果是错的"。实际事故里三类都真实出现过，少一层都不行。
