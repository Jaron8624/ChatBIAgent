# NexusMind介绍

# 项目介绍

**写在前面**

**项目目标：**本项目简单来说就是一个语义驱动的多智能体 ChatBI 系统：用户用自然语言提问，系统把问题解析为可审查的结构化中间表示（IR），对已治理的业务指标走语义层确定性编译生成 SQL，对复杂问题走多智能体协作规划，最终给出可信的查询结果、异动归因与可复核的执行链路。

**项目来源：**本项目是作者在校期间独立完成并持续打磨的个人项目，面向 2026 届秋招求职场景设计，核心架构与实现均为原创。项目选型刻意覆盖了 AI 应用岗最核心的几个技术方向：多智能体编排、RAG 检索、记忆系统、MCP 工具协议与 Text2SQL，并以真实公开数据集和学术评测基准做量化验证。

**项目内容：**本项目由两大核心部分组成

- **多智能体底座**：基于 LangGraph 的四种编排模式（Supervisor / ReAct / Coordinator / Reflection）、事件驱动的 Agent Loop、上下文管理三件套（模板组装 / 自动压缩 / 动态上下文回忆）、三级分层记忆与 Redis 会话快照、Milvus 稠密 + BM25 + RRF + Rerank 混合检索、统一工具注册与 LLM 重排路由、Monitor 在线监控与全链路 Trace 治理。底座负责"怎么理解问题、怎么调度能力、怎么记住上下文、怎么管好自己"。

- **ChatBI 核心引擎**：语义层确定性编译（NL → IR → SQL）、SQL Guard 三层防护、根因分析规划链、字段级评测闭环。引擎负责"怎么生成可信的 SQL、怎么保证每个数字可审计"。

**项目定位：**本项目是一个面向 B 端数据分析场景的 ChatBI Agent 项目。

Text2SQL / ChatBI 是许多互联网企业、国央企都希望真实落地的业务方向，市场上也有不少开源实现（Vanna、WrenAI、DB-GPT 等）。与"直接让大模型写 SQL"的 demo 级项目不同，本项目的核心原则是"能确定的，不交给概率"：通过语义层、SQL 守卫与评测闭环保证结果可信。该场景能够体现大模型、数据库、检索、Agent 和工程化能力的综合应用。

**希望这份文档能够给大家带来一些启发，也希望在持续迭代的过程中与大家共同成长！！！**

## 项目背景

在企业数据分析场景中，业务人员通常需要频繁进行数据查询、统计与整理。传统数据分析流程依赖固定报表、人工编写 SQL 或技术人员协助，存在**使用门槛较高、响应效率较低**的问题。而直接把自然语言交给大模型生成 SQL，又会带来**指标口径漂移、JOIN 路径失控、结果可执行却不可信**等新问题。

本项目的主要目的是利用大模型的意图理解能力与代码生成能力，结合语义层治理与 SQL 校验机制，实现自然语言驱动的可信数据查询与分析。**用户通过自然语言即可完成数据库查询、指标分析与异动归因，同时保证业务口径可审计、执行链路可复核。**

> 用户通过询问即可完成数据查询、归因分析的过程，无需写代码，且每一个数字的口径都可以追溯。
>
>

## 技术路线

本项目的技术路线分两条线：

- **多智能体底座线：**以 LangGraph StateGraph 为编排内核，按问题复杂度分流——简单意图走 Supervisor 快速路由，复合工具需求走事件驱动的 ReAct Agent Loop，跨模块任务由 Coordinator 拆解并行，Reflection + Advisor 做质量审查与定向重试；上下文管理分三层（模板组装 → Token 阈值自动压缩 → 动态上下文按需回忆），长对话不丢失、不撑爆；三级分层记忆（语义/情节/程序，Milvus 稠密 + BM25 + RRF 召回，相似度 × 时近性 × 重要性融合排序）+ Redis 会话快照保证多轮连贯；混合检索支撑知识库与 Schema 召回；统一工具注册与 LLM 重排路由接入全部内部工具；Monitor 滑动窗口监控 p99 / 成功率并在线调整路由权重，配合全链路 Trace 与 Bad Case 采样形成治理闭环。

- **ChatBI 核心链路：**"两阶段编译 + 四层路由"的 Text2SQL 链路——**SchemaLinker 将自然语言解析为结构化 IR（指标/维度/过滤/排序），按置信度路由到语义层确定性编译（14 指标 × 18 维度）、6 类复合指标计划、根因分析规划链或 LLM fallback，最后由 SQL Guard 完成 AST 校验、执行自修复与结果合理性检查。**

> 两条线的关系：底座是通用 Agent 能力，ChatBI 引擎是垂直场景的可信保障。底座让系统"够聪明"，引擎让系统"够可信"。
>
>

# AI认知

## Agent项目的定位

求职准备中，现在很多同学都会问：

> 要不要学习 AI 相关内容？
> 后端和大模型应用开发是否可以同时准备？
>
>

**我的结论是：在掌握一门后端基础语言后，再去学习 AI 相关的内容，学历好的可以投递 AI 应用开发岗 / Agent 岗，学历相对弱势的依然投递后端岗，也有很大概率被调去做 AI 相关内容。**

我认为现在很多同学对于 AI 项目有一个误区：

> AI 项目并不等于调用 API。
>
>

单纯搭建聊天 Demo、接入模型接口、按照教程做 Agent 或者单独做一个 RAG 知识库，这些内容本身价值其实有限。因为 AI 一定需要结合具体业务场景，**真正重要的不是会不会调用模型，而是为什么要引入 AI、AI 解决了什么问题、如何和现有业务结合、AI 能力边界在哪里、如何约束输出结果，以及相比传统方案收益是什么。**

以本项目为例，ChatBI 的核心矛盾不是"模型会不会写 SQL"，而是"**写出的 SQL 口径对不对、结果信不信得过**"。因此项目的重点不在模型调用本身，而在语义层治理、SQL 校验、评测归因这些工程约束上——这些恰恰是企业落地时真正考察的能力。

现在很多公司真正开始考察的，其实是：

> 是否具备将 AI 能力落地到业务中的工程能力。
>
>

另外现在很多同学会做 RAG 知识库项目，但我个人认为：

> 单独一个 RAG 项目已经不太够了。
>
>

因为 RAG 本质上只是大模型的一种增强手段，它更适合作为企业知识库、数据分析或 Agent 记忆的一部分，而不是单独作为完整项目存在。**因此更推荐的方式，是将 RAG 融合到真实业务场景中。**本项目中的混合检索（稠密 + BM25 + RRF + Rerank）就是作为 ChatBI 的 Schema 检索与知识库子系统存在的。
