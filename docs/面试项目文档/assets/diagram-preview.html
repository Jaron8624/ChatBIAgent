01 · 意图识别与路由

用户开口第一句，系统怎么听懂他想要啥？

三路“翻译官”同时上阵：规则像老会计认死理，LLM 像机灵实习生会意会，历史模式像秘书记得你上次说过啥。最后按业务优先级拍板。

① 规则识别（秒判）

关键词命中就出结果，快、稳、不要钱

听到“为什么…下降/暴涨” → 直接判根因分析
＋

② LLM 识别（兜住怪话）

规则不认识的口语、绕弯子，交给模型理解

“帮我瞅瞅哪个品类拖了后腿” → 判根因分析
＋

③ 历史模式（多轮补全）

用户说“那上个月呢”，翻上一轮意图接着用

上轮在查销售额 → 这轮补全为“查上个月销售额”
仲裁规则：根因分析优先级最高 → 数据查询 → 知识问答 → 闲聊兜底
为什么不全让 LLM 判？→ 每次都调模型：慢、贵、还可能“今天判成 A 明天判成 B”
一句话记忆：规则管快的，LLM 管活的，历史管接话的，优先级管谁说了算。
02 · MCP 工具协议

Agent 想用工具，总不能把说明书全塞脑子里吧？

MCP 就像给工具装了个“标准插座”：Agent 不关心工具内部长啥样，只问三件事——你有啥工具？参数怎么填？调用结果是什么？

① 握手 initialize

先对暗号：报版本、交换能力，确认“咱俩能对话”

→

② 发现 tools/list

工具自报家门：名字、干什么、参数格式（JSON Schema）

retrieve_schema_context(问题) → 返回相关表和字段
→

③ 挑选 rerank

工具太多时先按问题筛一遍，只把最相关的给模型看

→

④ 调用 tools/call

填参数 → 服务端校验 → 执行 → 返回结构化结果

内部工具（查数据、编译指标）和外部工具（第三方服务）走同一套协议，新增工具不用改 Agent 主流程
好处：模型能力 ≠ 工具能力，插座标准化后，换模型、加工具互不耽误
一句话记忆：先握手、再发现、挑着用、调完拿结果——和点外卖一个流程。
03 · ReAct 取证循环

复杂问题一次猜不准？那就“边看边查，查完再想”

问题：“哪个品类差评率最高，为啥？”——表名、字段、过滤条件都不是一次能猜全的。ReAct 把它拆成循环：想一步 → 查一步 → 看结果 → 再想。

Thought 想一想

“我得先看看评价表长啥样、有没有品类字段”

→

Action 动手查

调用 Schema 检索工具 / 执行一条探查 SQL

→

Observation 看结果

“哦，差评在 reviews 表，品类要 Join 三张表才能拿到”

↺

循环 / 收手

信息够了就出最终 SQL 和结论，不够再来一轮

三道保险丝：调用签名去重（同一工具+同一参数不许重复调）· 最大迭代上限 · 结果太大先存档
分工：简单查询走确定性快路径秒出；只有多步取证的问题才进循环，不浪费算力
一句话记忆：像查案——先想线索，再去调监控，看完监控再决定下一步问谁。
04 · 多 Agent 协作

贵的模型想事儿，便宜的模型跑腿，还并行

一个“为什么华东销售额下滑”的问题要查四五样证据。让强模型拆任务，几个快模型/工具同时干，最后合到一起——这就是 Coordinator 模式。

① Coordinator 拆任务

拆成互不依赖的子问题，白名单限定谁能干活

拆成：查销售额趋势 / 查品类构成 / 查上次结论
→

② 并行执行

多个 Worker 同时开工，互不等待

data_worker 查数 · schema_worker 查表 · memory_worker 翻历史
→

③ 汇总 Synthesize

合并证据、标置信度、给可追溯的结论

成本分级：简单问题单 Agent 就够；只有“要凑多路证据”的复杂问题才上并行，不搞形式主义
降级设计：某个 Worker 失败不拖垮全局，拿着已有证据照样给结论，只是置信度标低一点
一句话记忆：项目经理拆活儿 → 组员并行干活 → 汇报时合并证据、注明“哪些查实了”。
05 · ContextStore 延迟加载

上下文塞不下？别扔，存仓库、给凭据、按需取

工具一跑吐出 5000 行数据，全塞进上下文会挤爆；直接砍尾巴，后面追问“刚才那批数据里…”就失忆了。ContextStore 的解法：存档案，发编号。

① 超预算就存档

长结果写进仓库，上下文里只留摘要 + 一个编号

上下文里只显示“订单明细已存档 ref_id=42”
→

② 模型继续干活

上下文干净，关键信息不被淹没

→

③ 要用再取回

recall_context 工具三种取法

full 全文 / tail 只看结尾 / grep 搜关键词
本质：把“截断丢信息”变成“图书馆存书”——书不在桌上，但书号在手，随时能借
一句话记忆：上下文是书桌，仓库是图书馆，ref_id 是借书卡。
06 · RAG 与 Schema 混合检索

子块负责“找得准”，父块负责“看得全”，双路检索防偏科

用户问“回头客按省份的订单趋势”。“回头客”是语义问题，customer_unique_id 是精确字段名——一条检索路只能顾一头，所以走两条再融合。

① 先切小块

文档切成小块入库，块越小定位越准

→

② 向量路 ×7

懂“意思”，抓同义改写

“复购”≈“回头客”能对上
＋

③ 关键词路 ×3

BM25 抓“字面”，保住表名字段名

customer_unique_id 一字不差命中
→

④ 融合＋升维

RRF 排名融合 → 子块换回父块 → 精排出最终证据

为什么要父块？命中的可能只是半句话“按 price 求和”，得换回整个段落才知道这是“销售额”的定义
为什么 ×7/×3？向量容易“差不多都对”，多召回几条宽进严出；关键词路命中就八九不离十，少而精
一句话记忆：小块定位、大块理解；语义抓改写、关键词抓名字；最后融合排座次。
07 · 三级分析记忆

Agent 的记性分三层，存的不是聊天记录，是“值得记的”

全存聊天记录又贵又没用。按信息类型分开存：口径要稳定、结论要可查、习惯要贴心——检索时按类别配额取，谁也别想挤占谁。

语义记忆：存“业务常识”存什么：指标口径、字段含义 · 例：“销售额 = 按订单明细 price 求和，不是 payment 表” · 特点：几乎不变，反复复用
情节记忆：存“发生过的事”存什么：每次分析的结论 · 例：“上周查过：华东 GMV 下滑主因是家具品类” · 特点：带时间戳，越新越有用
程序记忆：存“你的习惯”存什么：交互偏好 · 例：“这位用户爱按周看、先要结论、城市维度优先” · 特点：慢慢积累，让下次回答更对味
短期快照：存“正在进行的事”存什么：当前会话的指标、筛选条件、刚生成的 SQL · 特点：放 Redis，会话结束就过期，只为接住“那换上个月呢”
怎么用：回答前按配额检索三类记忆 → 相似度+新近度+重要度排序 → 融合进上下文，不搞“全量记忆回灌”
一句话记忆：语义=教科书，情节=工作日志，程序=你懂我，快照=便签纸。
08 · LangGraph 编排

四条路从上往下试：能确定的绝不掷骰子

一个问题进来，路由金字塔从顶往下问：能走确定性路径吗？不能才降级。每层的判断结果都记在案，事后能查“当时为什么走了这条路”。

第一优先：根因分析链问题带“为什么/异动/对比” → 进假设拆解 + 多路取证的分析模式
第二优先：NL→IR→SQL 确定性编译指标和维度都在语义层有定义 → 代码直接编译出 SQL，不劳 LLM 动手
第三优先：ReAct / 多 Agent问题要多步取证或并行拆解 → 进入工具循环或多 Worker 模式
兜底：LLM Fallback全都没命中 → 把检索到的 Schema 上下文喂给 LLM 直接生成
为什么用图而不是 if/else？路由关系显式画出来：状态、分支、降级、重试全都看得见、测得到、改得动
一句话记忆：确定的走编译，不确定的走 LLM，中间档位按复杂度递进，全程留痕。
09 · 在线质量门禁与监控

SQL 跑成功 ≠ 回答有价值：得盯速度、结果、用户脸色

线上问题不能等用户骂上门才发现。每次请求留一条 Trace，门禁先挡住明显有问题的 SQL，监控再盯指标，坏案例自动进修复流程。

① 每次请求留 Trace

意图、路由、SQL、耗时、结果长啥样，全记下来

→

② SQL Guard 事前拦截

危险语句、明显不合理的查询当场挡下或修复

→

③ 指标盯梢

滑动窗口算 p99 延迟、成功率、空结果率、慢查询占比

→

④ 坏案例进闭环

用户点踩 / 异常采样 → 进 Bad Case 修复流程

盲区提醒：SQL 语法对、也执行了，但结果为空或 LIMIT 拉了百万行——这不算成功，要当质量信号记下来
为什么看 p99 不看平均？平均值被大量快请求拉低，真正的卡顿全藏在最后 1% 里
一句话记忆：先留痕、再拦截、盯尾巴指标、坏例子送修——体检 + 门禁 + 售后三件套。
10 · 双层评测

结果错了别只扣分，得知道是“走错路”还是“算错数”

只看最终对错，失败就是一团浆糊。拆成两层：过程层看“中间哪步偏了”，结果层用四个指标把“错”分成三种错法。

过程层：查路径

意图判对没？路由走对没？Schema 选对表没？Guard 拦错没？

回答“从哪一步开始偏的”

结果层：验输出

四个指标像四道关卡，逐层收窄

表命中率 97% → 行召回 0.851 → 字段准确 0.898 → 整体 EX 81.8%
四指标的分工：选对表了吗（表命中率）→ 该有的行全了吗（行召回）→ 每个格子的数对吗（字段准确）→ 整体算过吗（EX）
失败三分类对症下药：缺行 → 补检索；值错 → 查口径；行值都对但 EX 挂 → 八成是多查了行或排序不同
一句话记忆：过程层找病灶，结果层量伤情，四个指标一层层缩小包围圈。
11 · SQL 安全门禁

LLM 生成 SQL 像实习生写报告：先过三道审，再放行

用户说“帮我删掉那些异常订单”——话能听，SQL 不能直接跑。安全不能指望模型“自觉”，要靠确定性规则一层层审。

① 写操作直接拦

DELETE / UPDATE / INSERT / DROP，只读场景一票否决

→

② 结构审（AST）

解析语法树：表存在吗？字段拼对吗？不是拿正则瞎蒙

→

③ 合理性审

结果为空？LIMIT 太大？行数异常？可疑就修或拦

→

④ 放行 + 留底

执行归执行，审计日志记下“谁、何时、跑了什么”

允许修复但要限次：自动修一两次可以，无限重试就是烧钱黑洞
为什么 AST 不用正则？正则只能看长相，AST 才懂结构——嵌套子查询里的违规表名，正则看不见
一句话记忆：先问能不能做，再看写得对不对，然后看合不合理，最后留个字据。
12 · 数据权限与审计

“能不能做这事”由后端说了算，模型只负责建议

模型可以说“我建议执行这条 SQL”，但批不批准是权限系统的事。把“懂业务”交给 LLM，把“守规矩”交给确定性代码，各司其职。

① 识别身份

从请求里拿到“你是谁、什么角色”

→

② RBAC 判定

角色 → 权限清单，动作 → 需要什么权限，查表即知

访客角色请求导出全量数据 → 直接拒
→

③ 危险动作二次确认

发一个带过期时间的确认 token，用户点头才算数

→

④ 执行 + 审计

谁、何时、对什么资源、做了什么、结果如何，全留痕

和 SQL Guard 的分工：Guard 管“这条 SQL 本身安不安全”，权限管“这个人做这事行不行”
一句话记忆：模型是顾问，权限是保安，顾问说得再好听，保安不放行就不进门。
13 · Bad Case 闭环

错题不是抄进错题本就完了，得订正、验算、才入册

把失败样本直接塞回 Prompt 等于让模型“背错题”。闭环的做法：先搞清错因，修好后必须“验算通过”才允许写进 Few-shot 知识库。

① 收集失败

评测挂了 / 用户点踩 / 监控采样，连上下文一起存档

→

② 归因去重

错在选表？Join？口径？同类问题只留一份，不重复入库

→

③ 修复候选

生成更正后的 SQL / 示例，标注“为什么原来错了”

→

④ 验算入库

回归验证通过才回写；过不了就转人工，宁缺毋滥

为什么严？错误答案一旦入库会被反复检索引用——污染知识库，越学越歪，还很难追溯是哪条引入的
实测节奏（有据可查）：11 个失败样本最终只回写 2 条——不是因为苛刻，是多数错误不在这层能修
一句话记忆：错题本不是剪贴簿，是订正本；入库前先验算，验不过就人工看。
14 · 多轮会话恢复

追问接得上，靠的不是记性好，是便签记得勤

“那和上个月比呢？”——要接住这句话，光有聊天记录不够，还得记得上一轮的指标、筛选条件、SQL 长什么样。这些结构化状态单独存。

① 存分析状态

指标、维度、筛选条件、SQL、摘要，结构化保存

→

② Redis 快照

会话级快速存取，设过期时间，不无限占内存

→

③ 历史压缩

老对话压缩成摘要，原文进档案，不全量回灌

→

④ 追问时恢复

继承上轮全部条件，只改“上个月”这个增量

状态过期 / 表结构变了 / 两边同时改 —— 这些边界情况都要处理，不然恢复的是“假状态”
为什么不全靠上下文窗口？窗口是聊天记录，不是数据库：找不快、放不多、一关就没了
一句话记忆：聊天记录管“说过啥”，结构化快照管“分析到哪了”，两本账分开记。
15 · MCP 部署与 Docker 拓扑

六个容器各干各的活，谁病了都看得见

整个系统拆成：API 服务、PostgreSQL（元数据）、Redis（缓存/快照）、Milvus（向量检索）、etcd + MinIO（Milvus 的后勤）。Docker Compose 一键拉起，各配健康检查。

用户界面

网页聊天入口，发请求、看图表

→

ChatBI 后端

编排、MCP 调用、SQL Guard、监控全在这层

→

存储后端

PG 存元数据 · Redis 存快照 · Milvus 存向量

→

Milvus 后勤

etcd 管元信息 · MinIO 存数据文件

Milvus 双模式：开发用 Lite（一个文件、零部署），生产用 standalone（配合 etcd/MinIO 服务化）
健康检查 + 启动顺序：依赖先起、服务后起，谁挂了重启谁，不用整套推倒重来
一句话记忆：开发图省事、生产讲稳妥；容器分得清，排障才不用大海捞针。
