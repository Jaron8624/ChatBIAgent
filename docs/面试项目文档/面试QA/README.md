# 面试 QA — NexusMind ChatBI 高频问题（背诵版 + 详细介绍）

> 基础 20 题见 `docs/INTERVIEW_GUIDE.md`，本篇覆盖深挖追问层。每题背诵版 30-60 秒，详细介绍用于理解。

---

## 一、架构与路由

### Q1. 一次提问的完整链路？

**背诵版**：问题先过三路意图识别（规则/LLM/历史），路由金字塔决定路径：根因类问题走规划取证链；数据类问题先走 NL→IR→SQL 语义编译，命中指标就确定性生成 SQL；未命中再降级到 LLM fallback；复合问题走 ReAct，跨模块问题由 Coordinator 并行拆解。所有 SQL 都要过 AST 校验和 SQL Guard，执行结果做合理性检查，全链路 Trace 落盘。

### Q2. 为什么语义层优先而不是直接 LLM 生成？

**背诵版**：三个原因。一是口径，"回头客"用 `customer_id` 还是 `customer_unique_id` 每次问 LLM 都可能不一样；二是 JOIN，LLM 能拼出语法对但逻辑错的关联；三是可审计，编译出的 SQL 可以对照 IR 检查。我的数据也支持：域内用语义层 15 题 EX 100%，Spider 不用语义层 99 题 81.8%，差值就是工程体系的收益。

### Q3. LangGraph 踩过什么坑？

**背诵版**：TypedDict 未声明的字段会被静默丢弃。当时转人工标志（现在的安全字段）日志里有值，但 API 永远返回 false，因为 AgentState 没定义这个 key，LangGraph 直接丢弃且不报错。修复是补全 State 定义并对关键字段做端到端断言。这种"日志对但结果错"的 bug 只能靠返回值校验发现。

## 二、NL2SQL 优化

### Q4. 你的 NL2SQL 具体做了哪些优化？

**背诵版**：分四层。第一层 SchemaLinker 把问题解析成 IR（指标/维度/过滤/排序/LIMIT），可检查可路由；第二层语义层 14 指标 18 维度确定性编译，6 类复合计划覆盖多指标和派生比率；第三层 Schema 三级检索收敛上下文加动态 Few-shot；第四层 SQL Guard 做只读校验、方言修复和结果合理性检查。V1 到 V5 域内 EX 从 20% 提到 100% 就是这四层逐步加出来的。

### Q5. SQL Guard 怎么设计？

**背诵版**：三层。静态层 sqlglot AST 解析，拒绝写操作、未知表列、SQLite 不兼容函数；执行层把数据库报错连同 Schema 反馈给 LLM 自修复，最多两轮，实测 `LEFT()` 方言错误一轮修复成 `substr()`；结果层查空结果归因、TopN 与 LIMIT 一致性、NULL 占比和比率越界。第三层最重要，SQL 语法对执行成功不代表结论可信。

### Q6. Schema 检索为什么重要？

**背诵版**：表列幻觉是 NL2SQL 的头号失败源。全量 DDL 塞给模型既贵又噪声大，我按 Domain→Table→Column 三级收敛，再把 DDL、业务定义和已验证 SQL 作为三语料混合检索，命中内容动态注入。Spider 评测验证了效果：表命中率 97%（96/99），20 个陌生库几乎不选错表。

## 三、评测体系

### Q7. 为什么从 9 个指标精简到 4 个？

**背诵版**：EM 组件匹配率 37.4% 看着低但是假象——LLM 写等价 SQL（别名、JOIN 写法、谓词顺序不同），字符串级比对就是不过，EX 81.8% 和 EM 37.4% 差的 44 题全是这种。Spider 社区也早不用 EM 了。可执行率到 100% 后没有区分度；Avg Jaccard、Exact/Zero Match 都是 EX 的派生统计。留下四项形成"选对表→查全行→值准确→整体对"的诊断链。

### Q8. 四套评测是什么关系？

**背诵版**：域内 15 题（100%）验证混合链路；复合专项 12 题（100%）单测 6 类计划识别和编译；泛化 10 题（80%）测全新表述；Spider 99 题（81.8%）测无语义层的开放域零样本能力。分开报告是为了区分系统收益和模型裸能力——域内 100% 有语义层贡献，Spider 81.8% 是 LLM baseline，两者不能混。

### Q9. 行召回率和字段准确率怎么算？

**背诵版**：先选 key 列（通常是主维度），按 key 值对齐 Gold 和 Agent 结果集。行召回率 = 匹配行/Gold 行数，衡量"该查到的查全没"；字段准确率 = 匹配行正确单元格/总单元格（数值容差 0.5），衡量"查到的行值对不对"。这两个指标把 EX 的 pass/fail 拆开了——EX 挂了看这两个就知道是少查了行还是算错了值。

## 四、工程与稳定性

### Q10. 上下文超限怎么办？

**背诵版**：工具结果两级截断控制注入大小，超长内容和压缩前 transcript 落盘 ContextStore 留 ref_id，模型用 recall_context 按 full/tail/grep 三模式取回。full 有 5 万字符上限防止回忆本身撑爆。核心思想是把信息损失从不可逆截断变成可控延迟加载。

### Q11. 记忆系统怎么设计？

**背诵版**：短期靠 Redis 检查点；长期分三级——语义记忆存指标口径偏好（如回头客单位）、情节记忆存上次分析结论、程序记忆存用户交互习惯。各类型独立检索配额，相似度+时近性+重要性融合排序。一次性 SQL 结果不会沉淀成长期记忆，避免污染。

### Q12. MCP 为什么要自研协议层？

**背诵版**：三个理由：官方 SDK 与项目 LangChain 栈有依赖冲突；自研可以逐层打日志调试；能完整控制 JSON-RPC 2.0 的生命周期（initialize→tools/list→tools/call）、stdio/HTTP 双传输和超时清理。ChatBI 的 12 个模块工具和外部服务共享同一接入契约，加工具不改主链路。

### Q13. 权限边界在哪做？

**背诵版**：不在 Prompt 里。三层：API 层 require_permission 做 RBAC 依赖注入；SQL 层 AST 校验强制只读；数据层只读连接。Prompt 只能影响模型行为，不能构成安全边界。

### Q14. 最深的坑是什么？

**背诵版**：两个"日志对但结果错"。一是 LangGraph 静默丢字段（Q3）；二是意图识别阈值——LLM 通道权重 0.5 × 满置信 1.0 = 0.5，但整体阈值设了 0.6，意味着 LLM 单独判定永远过不了，纯数学问题但单测全绿。共性是：多通道融合的仲裁规则比单通道准确率更重要，每个仲裁规则都要对应真实 bad case。

### Q15. 下一步怎么优化？

**背诵版**：三个方向。Spider 从 81.8% 提到 86%+：18 个失败里 5 个列序（排序归一化）、3 个脏值（TRIM 预处理）、3 个过度工程化日期解析（prompt 指令）都是低垂果实；语义层配置化：指标定义从硬编码改成配置或从 schema 推断，让陌生领域也能用上语义层；多轮分析：指代消解加分析状态复用，支持"那和上个月比呢"这类追问。
