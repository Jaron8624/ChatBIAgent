# 10 — 双层评测：既看"有没有走对路"，又看"答案对不对"

> 一句话记住它：光报一个总分是耍流氓——错了要知道错在哪一步；刷过原题的分数和裸考分数，分开报才诚实。

![双层评测闭环](../assets/10-evaluation-loop.png)

## 这到底是个啥？

考驾照的时候，考官不只看你最后有没有撞桩，还看你每个科目做得怎么样——倒库压线、坡道起步后溜，扣分项一目了然。AI 数据问答系统的评测也该这样：只报一个"准确率 85%"是远远不够的，那 15% 错在哪了？是没听懂问题、选错了表、漏了几行数据，还是数值算错了？不同的错对应完全不同的修法——就像发烧的原因可能是感冒也可能是别的大病，不能一句"不舒服"就完事。

所以评测分两层。过程层看"有没有走对路"：问题理解对没对、表选对了没、走的是标准流水线还是 AI 兜底；结果层看"查出来对不对"，而且不是笼统的"对/错"，而是拆到很细：列齐不齐、行全不全、每个数值准不准。这样一道题失败时能读出一句话诊断，比如"列全对、行也全、就是差评率的算法口径错了"——一眼知道去修哪。这个项目还坚持一个诚实原则：在自己治理过的题上考满分，和在一个从没见过的陌生题库上考八成，是两个完全不同的数字——前者是"复习过的模拟考"，后者是"裸考"，必须分开报，混在一起等于用刷题成绩冒真实力。

## 面试官会问啥？

### Q1: 你们域内测试全对，是不是过拟合到测试题上了？

**答：** 这个质疑合理，我分三层回答。第一，那部分满分不是"AI 答对了"，而是"口径治理对了"——标准答案早就写进系统里了，同一问法永远得到同一答案，这部分分数量的是治理覆盖率不是模型能力。第二，为了补泛化证据，我专门跑了两个考场：用全新说法问同样的口径（八成正确），以及一个从没见过的公开题库做零样本裸考（约八成）。第三，满分的正确用法是"回归基线"——以后任何改动打掉哪怕一道题都能立刻发现，而不是吹能力上限。诚实的总结是：治理覆盖内接近确定，覆盖外大约八成。

### Q2: 为什么不用"逐字比对生成的查询语句"来判分？

**答：** 因为同一个意思有很多种写法——先去重再计数和先分组再计数，结果一模一样，但字面完全不同；换个别名、调个列顺序，逐字比对全判错。这就像判作文不能拿范文逐字对。所以判分落在"执行结果"上：两边都真跑一遍，比对查出来的数据一不一样。这才是用户真正在乎的东西——没人在乎厨房里先放盐还是先放油，只在乎菜的味道。

### Q3: 一道题错了，你怎么定位是哪一步错的？

**答：** 靠两层咬合。结果层把"错"拆得很细：列层面看字段有没有缺漏，行层面看该查出来的行漏没漏，格子层面看每个数值准不准，数值比对还带容差。过程层则记录这道题走的每一步：理解对没对、表选对没对、走的哪条路。两层一对，错在哪就现形了——比如"表选对了、行也全了、就是某个比率算错"，那基本就是口径理解错（分子分母用错之类），修口径就行，不用瞎调模型。没有这套定位，调优就是闭眼开药。

### Q4: 满分的模拟考和八成的裸考，哪个才是真实水平？

**答：** 都是，但回答的是两个不同的问题。域内满分回答"我治理过的东西还稳不稳"，是回归工具；裸考八成回答"没治理过的东西能做到什么程度"，是能力边界探测器，而且它告诉你下一步该治理什么——比如失败集中在多表关联和嵌套子查询，那语义层就该往那个方向扩。一个评测体系的健康度，最终看它能不能告诉你下一步该做什么，而不是只给一个漂亮的分数。

### Q5: 有没有哪次评测分数暴跌过？怎么处理的？

**答：** 有，而且记录得清清楚楚。有一版改动后分数从四成七直接掉到两成七——接入了动态检索后，提示词组织方式变了，加上换了个轻量模型，输出不稳定。当时的处理是先归因再修：针对性修复后回升到四成，再一轮迭代追平历史最好值，但没超过，复杂查询仍是瓶颈。这段"跌落又爬起来"的完整记录我都留着——一段可审计的失败史，比一个漂亮数字更能证明评测体系真的在工作。另外还有一次首跑大跌，查出来是安检规则误拦了带前缀的表名，修完还把这些用例补进了回归集。

### Q6: 评测出来的坏例子，然后就束之高阁了吗？

**答：** 评测的终点不是分数，是修复和沉淀。失败样本自动进入一个"错题本"队列，后台任务会拿增强后的流水线重做一遍——还是那套"标准口径优先、多路资料辅助、安检兜底"的组合拳——重做结果再过一遍细粒度评测，行全了、数值准了、安检也过了，才算修复。修复后的查询语句还会回写成范例，成为系统下次遇到类似问题的"参考答案"。错一道题，修一道，还留下笔记，这才是闭环。

## 记忆口诀

过程看走没走对路，结果看菜的味道不看菜谱写法；列、行、格三级定位病灶；模拟考和裸考分开报；错题要修要留笔记，不是打完分就散场。
